## 目标与硬约束

- 已知最终费用的请求立即按冻结价格结算并返还差额；已确认零费用的请求立即原路释放。结果未知的请求尽早取证，无法取证时按已批准的 72 小时平台补偿政策处理。
- **正常请求不增加首字路径上的同步数据库操作、远程调用、锁等待或逐 token 工作；不改变现有预占、派发前标记和流式输出顺序。** 不把 Sub2API 查账、消费日志关联查询或监控上报放进请求首字路径。
- 正常完成的请求复用现有结算事务保存必要的终态信息，目标是不增加 SQL 往返数；额外的证据补写和重试仅发生在异常路径或后台。后台任务必须限并发、限批量、限查询耗时，并在数据库压力升高时退避。
- 账本只允许一次终态资金调整；返还原会员账户或钱包及原令牌，沿用预占时冻结的价格。真实费用超过预占时维持现行平台承担差额规则，不追扣其他来源。72 小时补偿后出现迟到凭证，只留审计，不追扣用户。

“不影响性能”以**无新增正常请求同步步骤**作为设计约束，以对照测试和灰度监测作为发布门槛；仅凭方案无法保证真实环境的延迟严格为零变化。任何可重复的首字或正常请求吞吐回退都阻止放量。

## 设计基线的链路与问题

以下记录 `922db66baa46c07b5f36cdce8191a52d9af519db` 的设计起点；持久游标和本地异常恢复现已实现，不能把此处历史限制当作最终代码或线上状态。

1. `service/membership_budget.go` 按可见输入、输出参数、份数、工具及保守倍率估算预占。无显式输出限制时的 1024 token 是计费估值，不是上游强制上限；不能把所有预占称为严格费用上界。
2. `model/membership_billing.go` 已在事务中选择会员或钱包并预留；`service/membership_dispatch.go` 在发送上游前持久标记派发。正常完成走现有结算，异常但有可信部分用量也应结算；发送后断线、缺少最终用量等情形保留暂占。
3. `service/kkai_runtime_jobs.go` 每分钟调度同步 Relay 核账。`model/membership_billing_reconcile.go` 只扫描创建满 72 小时的记录：唯一且匹配的消费日志用于结算，无日志按平台补偿全额释放，冲突留待审。消费日志在独立日志库；“查不到日志”不是“上游确认零费用”。
4. 当前每轮最多扫描 500 笔，并从最老记录重新开始。若前 500 笔持续冲突，后续到期记录可能饥饿。上游请求 ID 目前主要进入请求上下文和消费日志，没有随暂占记录持久关联；断流且拿不到响应头时更难核实。
5. 已有签名内部归属头携带 NewAPI 请求 ID。跨服务核账应复用该 ID，不能要求正常请求额外同步查账，也不能依赖一定收到上游响应头。

## 实施顺序

### P0：只读基线与核账队列可靠性

- 按 `scope/source/state` 汇总暂占笔数、金额和年龄；另统计最近 7 天正常请求的 `预占/实扣` 分布、P50/P95/P99、模型和流式类别、实际超额及平台补偿。历史异常积压单列，不能用它推断正常请求的高估比例。
- 核对核账任务的运行间隔、每轮扫描/结清/冲突/错误数、最老待处理年龄。区分“确认零费”“已结算”“无证据补偿”“凭证冲突”，记录笔数和额度，告警不得包含密钥或原始请求。
- 使扫描位置跨轮持久推进并在尾部回绕，冲突记录记录原因及下次复查时间，不能每分钟阻塞队首。优先利用现有账本与后台任务能力；如需新索引或字段，先验证写入开销和跨 SQLite/MySQL/PostgreSQL 的迁移。核账只在后台运行，查询批量与超时有界。

### P1：补齐已知结果的及时收尾

- 逐条检查普通成功、明确未派发、上游明确拒绝、可信部分用量、正常流结束、流中断和结算失败的收尾路径。已有即时结算/释放保持原样，仅修漏掉的终态。
- 区分三种证据：`final_usage`（按冻结报价结算）、`confirmed_zero`（释放）、`unknown`（保留暂占）。HTTP 错误、断线、缺少 usage、没有本地消费日志均不能单独算作 `confirmed_zero`。
- 正常请求所需的最终证据随现有账本结算事务落库，不增加结算前或首字前的单独写入。若结算失败，在异常路径尝试持久化可信用量以供后台重试；数据库完全不可用时保留暂占，待跨服务凭证或既有日志恢复。重试使用请求 ID 和终态约束保证幂等。

### P2：仅为未知结果建立跨服务核账

- 先确认 Sub2API 能否按已签名的 NewAPI 请求 ID 查询**最终**计费用量或明确零费用收据，以及收据覆盖率、产生延迟和保留期。返回身份、请求/渠道关联、最终状态、可按 NewAPI 冻结价格重算的用量、计费记录 ID 和时间；校验来源与一致性。仅“没有查到”不得释放。
- 对确实进入 `unknown` 的同步 Relay 暂占，在账本保存可用的上游请求 ID、证据引用与查询进度；无响应头时仍按原 NewAPI 请求 ID 查。复用 Sub2API 现有最终计费写入，不给正常请求增加派发前写入或等待。
- 请求传输实际停止后即把 `unknown` 纳入有界后台查询；进程崩溃留下的孤儿记录在已记录的派发截止时间后纳入。查到可信最终用量则结算，查到明确零费用则释放；暂未终结、查询失败或凭证冲突则退避重试并告警。若 Sub2API 无法提供可验证终态，该请求仍按现行 72 小时无证据平台补偿，不伪造零费用结论。
- 保留 72 小时作为最后兜底。只有收据覆盖率和最慢到达时间经过真实数据验证、且已明确更短时限的平台损失预算后，才另行评估缩短。异步任务不进入此规则。

### P3：用实测数据收紧预占金额

- 只移除已证明互斥或重复计算的保守费用，或让报价依据真实会传给上游且受校验的输出/工具上限；逐模型对照预占、实扣和平台超额。无显式上限的估值不得宣传为强制上界。
- 不按平均值或 P95 直接打折预占，不在首期引入渐进追加预占。后者需要解决流中途额度不足、并发抢额、上游中止与断流结算，只有前述措施仍无法达到目标时再设计。

## 性能与账务验收门槛

| 范围 | 必须验证的结果 |
| --- | --- |
| 正常请求首字 | 会员及钱包、流式及非流式的派发到首字路径没有新增同步 SQL/网络调用或逐 token 工作；同一上游模拟延迟、请求体和并发下，对照 P50/P95/P99 首字延迟及吞吐，不得出现超出基线波动的可重复回退。 |
| 正常请求完成 | 结算 SQL 往返数不增加；对照总耗时、数据库事务时长、锁等待与 CPU。后台运行和暂停两种负载都要测，避免后台争用影响正常请求。 |
| 及时释放 | 正常终态仍在请求收尾时结算；异常但有可信凭证的记录以每分钟后台轮询为初始目标，在凭证可用后 1 个调度周期内处理。任务停摆、超龄额度和冲突积压必须告警。 |
| 故障与并发 | 覆盖发送后断线、无 usage、拿不到响应头、日志库故障、主库短暂故障、进程崩溃、重复 worker、迟到凭证。每笔最多一次终态调整，资金来源/令牌原路处理，会员账本差额为零。 |
| 72 小时兜底 | 同步 Relay 无证据记录按批准的政策补偿；冲突不阻塞其他记录。逐日核对超过 72 小时的笔数与金额，无法自动处理的冲突单独列明，不把它们报成零。 |

先在隔离环境跑相同负载的基线与候选版本，再小流量观察正常请求的首字、总耗时、错误率和数据库锁等待。性能门槛或账务不变量不通过即停止放量并回滚；不能为了更早释放而绕过派发前预占。涉及账本字段/索引的改动须按项目显式 schema 合约单独验证和迁移，应用发布与业务数据补偿分开。

## 已完成的性能验收与剩余边界

完整候选 `cc99ff134` 的 64 格、12,800 次请求全部结清，但性能异常仍被保留。去除 PostgreSQL/MySQL 的多余租约写入后，`c6fc071f8` 的生产节拍对照仍出现积压争用，因此继续修复未变化冲突的重复延期及 aged 页内逐条状态查询。

最终 `fc46400f3` 按原冻结方法完成 12 格、2,400 次相关跟进（候选 1,600 次、历史同窗对照 800 次），SQL 错误、未结算与连接池等待均为零。501 条冲突积压的额外 SQL 从 203 条降到 4 条；压力与生产节拍下均未再出现超过冻结范围的双轮回退。生产节拍同窗仍保留首内容 P50 约 +0.092ms、完成 P95 约 +0.435ms、吞吐约 −1.87% 的差值，不把结果表述为绝对零开销。

结论支持进入受控业务验收。测试使用本机隔离 PostgreSQL 和固定上游，未覆盖真实鉴权、渠道分发、输入分词、Redis 与生产规模；最终源码只补验与修复相关场景，未重跑整个矩阵。线上返还、核账正确性和长期积压仍须以独立生产回执确认，不能由本地性能结果推断。P2 查询能力和 P3 金额优化仍需各自验收。

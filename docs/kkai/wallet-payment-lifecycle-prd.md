# 钱包充值订单生命周期 PRD

**2026-10-24 交互修订：** 主动确认结束成功后，在同一次用户操作内串行精确 acknowledge，成功直接回充值页，无需再点返回；失败保留 ended 与返回重试。自动超时仍保留超时提示和“返回充值”按钮。自动确认只作用于原身份、flow/revision 与原订单均仍一致的 ended 结果，实际收款、身份变化、另一当前流程和迟到旧响应不能自动清理。以下条款按此区分主动结束与自动超时。

**2026-10-23 生效修订：** 本文正文及 A01—A32 已按获用户确认的 [本站超时与废单规范](./wallet-payment-local-timeout-spec.md)统一：本站 30 分钟期限、本地结束／超时结果及显式“返回充值”、废单无续付／人工补单入口，晚到款仍按原单处理。本地操作结束与渠道可靠关闭分别表达。

日期：2026-10-23。状态：已确认的开发基线；当前本地实现、验证与渠道限制见 [实施记录](./wallet-payment-implementation.md)。下文“本轮只编写文档”等内容保留为设计阶段记录。

本稿基于 [钱包充值订单生命周期修复方案](./wallet-payment-lifecycle-plan.md)，将其资金安全约束转化为唯一推荐的产品方案。配套原型展示同一套页面在不同订单状态、角色和屏幕尺寸下的变化，不代表多套备选方向。

本文定义已确认的产品行为，配套 [开发总纲](./wallet-payment-development.md) 及分册负责实施规格；本轮只落地文档，不修改业务代码、不执行 schema 迁移、不查询或处理生产订单。文中金额、币种组合、充值点数、订单状态转换和支付结果均为设计示意，不代表真实价格、生产汇率或对截图订单的实际核实结果。

本轮依据用户纠正更新主流程：**钱包页直接承接购买后的当前订单，支付在外部新标签页打开；关闭支付标签页后，无需进入订单记录即可重新打开原支付页面或申请取消。** 这项明确要求取代前版默认同标签支付、先进入订单记录恢复的建议；订单记录保留为二级入口。

最新布局约束：**充值区采用互斥阶段。存在当前订单时，只显示订单详情和操作，隐藏充值与购买表单。本站创建后 30 分钟到期（已知渠道更早则取更早值），原位置显示“本次充值已超时”和主按钮“返回充值”；用户主动 end 成功后串行精确确认并直接恢复充值表单；确认失败保留“本次充值已结束”和“返回充值”重试。废单不提供续付、人工核实或补单入口，原记录及晚到款处理责任保留。真实渠道取消、已到账及可靠失败仍保留各自结果。** 当前订单与充值表单并存、到期自动跳回以及仅因渠道未关单永久锁定的旧要求均已作废。

## 1. 问题与目标

当前钱包充值存在三项用户直接感知的问题：关闭第三方支付页面后无法恢复原支付入口；已创建的未支付订单无法取消；旧订单长期显示 Pending，用户无法判断还可否支付。另有失败、未知状态被误显示成 Pending 的问题。

一期目标：

1. 用户购买后，钱包充值区由表单切换为当前订单详情；关闭外部支付标签页后，可在原位置恢复原订单、原金额和原支付会话，无需先进订单记录。
2. 用户可以结束本站充值操作；只有渠道可靠确认关闭后才显示渠道已取消。两种事实分别表达，不因渠道无关单能力永久锁住钱包。
3. 本站超时立即停止续付和人工补单，显示超时结果与主按钮“返回充值”，用户主动返回后恢复表单。老 pending 同样归为本站废单且仍可查看；已付款按原订单真实资金结果处理。
4. 支付中、取消中、已收款未到账有明确反馈，不诱导用户为同一笔充值重复付款。
5. 用户、客服和管理员对同一订单看到一致的资金事实、处理进度和下一步动作。

成功标准：付款入口可恢复，状态和动作可信，真实付款有可追踪的入账或异常处理结果；历史记录、付款证据和关闭事件保留。

## 2. 一期范围与边界

### 2.1 本期包含

- 钱包余额充值的新订单和已有未完成订单。
- 本人订单查询、期限内原会话继续支付、结束本站操作、按渠道能力取消、结果核实和本站到期处理。
- 钱包当前订单卡、外部新标签支付与原入口恢复、二级订单记录筛选、订单内展开详情、状态与币种金额显示。
- 管理员待核实队列、核实支付后的入账和存量订单处理进度。
- 用户关闭网页、返回钱包、跨设备登录和重复点击后的恢复体验。

### 2.2 本期边界

- 沿用现有钱包、订单记录、账户余额与账务链路；不新建独立订单中心，不重构会员或订阅流程。
- 一笔充值订单对应一个可付款会话。继续支付不延长期限、不创建第二个可付款会话；重新充值产生新订单号。
- 不将取消充值等同于退款；已到账订单不提供本功能范围内的取消或退款按钮。
- 当前充值流程尚未精确确认时禁止再次购买；主动 end 成功在同次操作内精确返回，本站到期后则点击返回。原单保留历史及资金处理责任，不能以新单代替旧单回执；已结束／超时废单不再自动恢复或提供补单。
- 不能根据账龄、关闭网页、浏览器回跳或用户点击“我已支付”认定实际付款结果。
- 不自动删除订单；历史业务数据处理与应用发布分开授权、执行和报告。

## 3. 用户与管理员故事

| 角色与场景 | 需要达成的结果 |
| --- | --- |
| 用户关闭了外部付款标签页 | 期限内回到钱包即可重开原单或结束本次充值；渠道取消按真实能力提供，无需进入记录列表 |
| 用户改变主意 | 可结束本站操作并在精确确认成功后直接返回充值；申请渠道取消时能看到真实进度和结果，不将两者混淆 |
| 用户看到很久以前的 Pending | 能看到本站已超时、保留只读记录；已确认收款的仍显示到账或到账核实，不再提供废单补单入口 |
| 用户已经付款但余额未增加 | 看到支付确认或到账核实进度，知道此笔不要重复支付 |
| 用户在手机和电脑之间切换 | 登录后仍可查询本人订单；恢复不依赖某个浏览器的本地存储 |
| 管理员处理旧订单 | 废单只读且无人工补单入口；真实晚到款有原单收据、幂等入账或异常处理责任 |
| 客服回应到账疑问 | 用户可提供订单号；客服能说明当前处理状态和所需信息，不索取支付 token 或密钥 |

## 4. 唯一推荐页面结构

### 4.1 钱包页

钱包主区使用**表单与当前订单互斥**的单一流程，不将订单卡与购买表单上下并列。空闲阶段可展示余额与充值表单；订单阶段主区仅一块订单详情，不在其上方堆叠独立余额卡或另一个充值模块。页面标题与二级“订单记录”入口保留。钱包与外部支付标签页并存，钱包自身不跳离。

| 阶段 | 充值区只显示什么 | 能否购买 |
| --- | --- | --- |
| 空闲 | 充值额度、付款方式、应付报价与购买按钮 | 可以提交一次购买 |
| 创建中 | 创建进度与当前提交反馈；结果不确定时继续核实 | 不显示表单或购买入口 |
| 当前订单 | 冻结详情、重新打开支付页面、结束本次充值、按能力取消、刷新结果 | 不显示表单或购买入口 |
| 支付／取消处理中、待核实 | 本次订单详情、进度及允许的核实／帮助操作；无已收款事实时可按后端能力结束本站操作 | 不直接返回表单；主动结束后串行精确返回，到期保留结果待用户返回。已收款到账核实优先，不按账龄作废 |
| 本站超时结果 | “本次充值已超时”、主按钮“返回充值”和查看原记录 | 本站截止后即保留结果；点击主按钮才恢复表单，原渠道关闭事实独立保存 |
| 主动结束 | 确认结束后串行精确返回，成功直接显示充值表单 | 不再开放原入口／人工补单；返回失败保留 ended 结果和“返回充值”重试 |
| 其他结果 | 已到账、用户主动取消或可靠失败的结果、查看记录和返回充值 | 点击“返回充值”后才恢复表单 |

主流程为：**空闲 → 创建中 → 当前订单 → 处理／结果 → 返回充值 → 空闲**。本站到期保留超时结果和“返回充值”；主动 end 成功在同次操作内串行精确返回，直接回表单，失败保留 ended 与重试。两者均不等待渠道可靠关单。关闭支付页、切换标签页、关闭记录弹层、刷新页面或查询失败本身均不能跳过当前阶段回到购买。

当前订单卡按顺序展示：

1. “当前充值订单”与完整状态、简短处理说明。
2. 应付金额及币种、充值额度、付款方式。
3. 可复制的订单号、创建时间、本站有效截止时间及其来源；创建时间缺失时显示状态暂不可用，不伪造期限。
4. 待付款且能力允许时，主按钮“重新打开支付页面”，提供“结束本次充值”、按能力“取消订单”和“刷新结果”。其他状态按下表替换动作，卡片仍保留。
5. 行内展开的取消确认、详情或客服说明；不再要求打开订单记录才执行当前订单操作。

恢复与多单规则：

- 提交购买即退出表单并进入创建中；创建成功后，服务端已保存的该订单立即成为当前订单，再打开外部支付标签页。可靠确认没有形成订单／会话的创建失败也先显示失败结果，再由用户返回充值。
- 服务端记录本次当前流程，重新进入钱包或换设备时优先恢复它；存在当前流程时不能用选择另一记录来清除它。浏览器最后订单号不是阶段依据。
- 无本次当前流程时，聚焦用户最近操作的可处理未完成订单；兼容旧数据时只选择可靠可继续处理的对象。旧待核实历史保留在记录，不无差别自动绑定为新的当前阶段。
- 同时有多笔未完成订单时，只展开一个当前订单，其余通过“另有 {n} 笔未完成订单 · 查看其他订单”进入二级记录。计数按本人、当前租户和真实可处理状态统计，排除本地已结束／已超时废单，已确认收款未到账的责任继续保留。
- 切标签页、关闭外部支付页、关闭订单记录或刷新钱包不会清除未完成的当前订单。
- 达到本站有效截止后，钱包保留“本次充值已超时”、主按钮“返回充值”和查看原记录，用户点击后精确确认再恢复表单。主动 end 成功在同次操作内串行精确确认并直接回表单，确认失败保留 ended 和返回重试。均不自动创建新单。是否已关闭渠道会话另按可信证据记录，不是返回的先决条件；旧查询响应不得覆盖随后建立的新当前流程。
- 当前订单转为已到账、用户主动取消已可靠关闭，或支付失败且无可付款会话时，在原位置保留结果与“查看订单记录”“返回充值”。这些路径仍由用户明确返回后恢复表单并重新确认新报价，不立即创建新单。
- 尚未结束且未到期的当前操作不能通过收起卡片、切换历史或关闭支付标签页恢复购买。创建结果未知可按后端能力结束本站操作；达到本站截止也可进入超时结果，主动 end 成功在同次操作内精确返回，超时保留结果待用户点击返回。已确认收款的到账核实责任优先，不以结束或账龄隐藏。
- 没有当前流程、没有需恢复的可处理未完成订单时显示空闲表单；恢复查询期间只显示“正在恢复订单”，不能先展示可购买表单，也不能把暂时查询失败当作没有订单。首次恢复读取最多等待20秒，超时进入可重试的失败状态，不解锁购买或丢弃已知订单。
- 管理员本人钱包的当前卡和其余订单数仍仅代表本人；全平台管理入口不替换本人当前订单。

### 4.2 订单记录

订单记录是查询其他订单与历史的二级入口，不能作为当前支付恢复和取消的必经步骤。桌面使用宽订单记录弹层；手机使用全屏弹层，保留清楚的返回与关闭入口。两者使用同一信息层次和操作逻辑。

从上到下依次为：

1. 标题“订单记录”，必要的范围说明与关闭按钮。
2. 状态筛选：**全部／待付款／处理中／待核实／已完成／已关闭**。
3. 订单号搜索与“刷新结果”。
4. 分页订单列表；订单卡片内展开详情和操作确认，不打开第二层弹窗。
5. 分页与结果数量。

每条订单默认展示：状态、订单号、创建时间、充值额度、应付金额及币种、付款方式和当前可用操作。详情展开后展示截止时间、订单时间线、付款核实结果及可供用户理解的处理原因。

金额示例“应付 CNY 100.00、充值 100 点”仅用于说明两个字段的视觉区分；实际产品使用订单冻结的计价单位、最小货币单位和币种，不从示意数据推断价格、汇率或实际收款。

管理员从管理入口打开同一结构的全平台视图，标题明确为“全平台充值订单”；显示用户信息、待核实原因和核实操作。普通用户不能切换到管理员视图。全平台视图的筛选数量不与本人钱包当前订单及其他订单数混算。

### 4.3 同一流程内的详情与确认

- 钱包当前订单卡和记录卡均可点击“查看详情”在本订单下展开，不遮挡订单上下文。
- 点击“取消订单”在当前所在卡片展开确认区，提供“确认取消”和“返回订单”；钱包中不必先进记录再确认。
- 点击“结束本次充值”展开本地结束确认，说明原支付页可能仍可付款及晚到款处理；本人仍有效的历史单也可结束，但不替换或清除当前另一单。
- 钱包当前卡已展示冻结金额、币种和有效期，“重新打开支付页面”可直接请求恢复并在外部新标签页打开原会话。记录列表的“继续支付”仍在订单内确认这些信息，确认后在外部新标签页打开。
- 操作失败、等待核实和联系客服说明在该订单内反馈，使用页面状态消息辅助提示，不依赖瞬时 toast 承载唯一信息。
- 可通过钱包中的订单号定位参数恢复服务端认定的本人当前订单；历史订单在记录中定位并展开详情。定位不能覆盖本次未完成阶段，也不能将独立历史待核实单自动绑定为当前流程。订单号不是访问凭证。

## 5. 状态、筛选与动作矩阵

状态名称、可用动作、有效期和简短原因均由后端返回。前端不根据原始 status 字符串或本地计时猜测资金结果；操作接口仍须重新校验权限与状态。

| 用户看到的状态 | 筛选归属 | 用户动作 | 展示要求 |
| --- | --- | --- | --- |
| 正在创建／核实创建结果 | 处理中 | 刷新结果；创建请求已结束但结果未知时可按能力结束本站操作 | 创建提交期间禁重复操作；不确认原会话可付款就不续付；结束／到期后不再重放创建 |
| 待付款 | 待付款 | 继续支付、结束本次充值；渠道允许时取消订单 | 原会话已就绪且仍在本站期限内，展示有效截止及来源 |
| 支付确认中 | 处理中 | 刷新结果、查看详情；无已收款事实时可按能力结束本站操作 | “支付结果正在确认，此笔请勿重复支付。”停用本单续付；本地到期不等于判定渠道未付 |
| 取消处理中 | 处理中 | 刷新结果、查看详情；按能力结束本站操作 | “正在确认取消结果，请勿继续支付此订单。”不能承诺已经关单；不因取消查询未知永久锁住钱包 |
| 支付结果待核实 | 待核实 | 按能力核实支付结果、结束本站操作、查看详情、联系客服 | 尚不能确认是否收款；到达本站截止转超时结果，已收款事实优先 |
| 已收到付款，到账核实中 | 待核实 | 刷新结果、查看详情、联系客服 | 收款已经可信验证；明确“此笔请勿重复支付” |
| 已到账 | 已完成 | 查看明细；当前结果提供“返回充值” | 展示入账时间、额度及可展示的可信付款信息，明确返回后才恢复表单 |
| 已取消 | 已关闭 | 查看详情；当前结果提供“返回充值” | 渠道确认关闭，或有可靠证据证明未形成可支付会话，明确返回后才恢复表单 |
| 本次充值已结束（ended） | 已关闭 | 当前结果主按钮“返回充值”；历史仅查看详情／帮助 | 仅表示本站操作结束；无续付、再取消、人工核实或补单，不声称渠道已关闭 |
| 本次充值已超时（timed_out） | 已关闭 | 当前结果主按钮“返回充值”；历史仅查看详情／帮助 | 创建后 30 分钟或更早渠道截止即生效；不依赖后台回填或渠道关单，晚到款继续处理 |
| 渠道已过期（expired） | 已关闭 | 当前结果“返回充值”、查看原记录 | 渠道可靠确认未付款且会话已关闭／到期；与本站 timed_out 区分，保留渠道证据 |
| 支付失败 | 已关闭 | 查看原因；当前结果提供“返回充值” | 已确认终态失败且没有仍可付款的会话，明确返回后才恢复表单 |
| 状态暂不可用 | 全部 | 只读详情、刷新本站记录、联系客服 | 未知状态或缺失可靠创建时间时使用；无续付、结束、人工核实／补单动作，不伪造 pending 或超时时刻 |

上述矩阵同时约束钱包当前区、记录、管理员视图及旧入口。钱包“重新打开支付页面”和记录“继续支付”都只能在期限内恢复同一原会话。支付确认、取消及待核实不保留活跃重开按钮；无已收款事实时可按后端能力结束，本站到期即保留 timed_out 结果。ended／timed_out 不再提供恢复、取消、再次结束、人工核实或补单，后台可信收款处理独立继续。success／credit_review 及可信已收款事实优先于本地结束标记和账龄；当前可返回结果仍须精确确认，主动 end 成功可在原操作内串行完成，历史查看或“重新充值”不能绕过当前门禁。

“全部”包含当前范围内所有可查询订单。筛选计数与列表使用同一范围、同一状态归属和相同查询条件；不能把前端当前页条数当作总数。普通用户未处理订单入口和按本人订单号精确查询不受现有 30 天历史窗口限制，仍须限流和分页。

本人记录六类筛选统一显示最近 30 天记录及全部账龄需保留的原始未完成／未定性记录，包含按本站期限投影为 closed 的旧 pending，并明确提示范围。不能切换筛选时漏掉旧记录，也不能将其继续计作待付款或其他未完成；全龄精确查询仍可定位更早的已完成或可靠关闭订单。

操作导致订单离开当前筛选时，列表和计数同步更新，并告知去向，例如“订单已取消，可在‘已关闭’中查看”，提供查看该订单入口。保持键盘焦点和可读反馈，不留下已终止但仍可点击的旧按钮。

未知状态不是确定的待核实业务结果；只有后端完成归类并建立核实责任后，才进入“待核实”队列。不能仅换文案掩盖后台缺少处理机制。

## 6. 关键流程与交互文案

### 6.1 创建订单与进入支付

1. 用户在充值表单和支付明细中核对充值额度、报价金额、币种和付款方式。
2. 报价有效时，点击“核对并支付”即创建订单并打开支付页，不再增加“确认充值订单／创建订单并支付”步骤。Creem 先选择产品并查看报价，再单击同一支付按钮提交；选择产品本身不下单。报价失效时先刷新明细，不使用旧报价或刷新后自动下单。
3. 提交后充值区切换为“正在创建订单…”，隐藏在线充值表单和购买入口，防止同一次动作重复提交；超时后查询本次创建结果，不提示用户立即再建一笔。
4. 服务端已保存原单和支付会话后，钱包主区仅显示当前订单详情，再将支付入口打开到外部新标签页；不并列展示在线充值表单，也不在订单上方堆叠独立余额卡。
5. 若新标签页未出现、被浏览器拦截或跳转结果不确定，在钱包当前卡提示：“订单已创建。如支付页面未打开，请点击‘重新打开支付页面’。”始终提供手动重开入口，不要求先进入订单记录，也不误报页面已成功打开。
6. 创建结果不确定时显示：“正在确认订单创建结果，请稍后刷新，此笔请勿重复提交。”不把网络失败当作确定未创建；原请求已结束后可选择结束本站操作，或在本站到期后进入超时结果，均不重建同单支付会话。

支付链接或表单不随订单列表公开，不在普通日志、客服文案或浏览器偏好存储中暴露 token。

### 6.2 继续支付

钱包主入口“重新打开支付页面”和记录内“继续支付”仅在后端允许时出现；恢复原订单的原会话，不能重算金额、套用当前汇率或刷新出一个新的有效期。钱包当前卡已展示付款信息，用户可直接点击主入口，无需再进入记录或通过第二层弹窗。

行内确认展示：

> 继续支付此订单
>
> 订单号：{trade_no}
>
> 应付：{currency} {amount}　充值额度：{credited_amount}
>
> 请于 {deadline} 前完成付款。

记录内确认按钮为“前往支付”和“返回订单”；钱包当前卡直接使用“重新打开支付页面”。两者均打开外部新标签页，并保留钱包当前卡。截止为本站创建后 30 分钟或已知更早渠道截止，来源明确显示；无渠道期限也可显示本站政策期限，不能称为渠道期限。创建时间缺失时不伪造倒计时或开放续付。

支付会话与浏览器标签页是不同概念：重新打开原会话不创建第二个可付款会话；用户重复点击时抑制并发恢复请求。产品不承诺可靠读取或检测跨域支付标签页是否关闭，不以“已关闭支付页”自动改变订单状态。

获取恢复结果期间再次变化的处理：已到账或已确认收款先显示资金结果；本站已结束／到期则显示 ended／timed_out 结果与主按钮“返回充值”，不再返回支付凭据；渠道可靠取消／过期或失败保留其独立结果。尚在期限内且未结束的未知或处理中保留进度。任何路径都不能凭旧恢复响应重开废单或绕过精确返回确认。

### 6.3 用户结束与渠道取消

未结束、未超时且无已收款事实的操作提供“结束本次充值”，不以渠道支持关单为前提。用户确认后持久保存本地原因／时间；当前原单实际 ended 且允许 acknowledge 时，前端在同次操作内串行精确确认，成功直接回表单，无需再点返回。确认失败保留 ended、错误和“返回充值”重试；资金事实或当前流程已变化时不自动清理。不删除原单或停止可信回调处理。本人有效历史单可结束，但返回的 wallet 仍代表实际当前流程。

支持可靠取消的渠道显示“取消订单”。行内确认文案：

> 取消这笔充值订单？
>
> 系统将核实支付结果并尝试关闭付款入口。若已完成付款，将以实际付款结果处理。取消充值不等于退款。

确认按钮为“确认取消”。提交后立即停止平台继续支付入口，展示“取消处理中”；重复点击只返回当前处理进度。

- 确认关闭：显示“订单已取消”，保留关闭原因与时间。
- 已支付：显示“付款已确认，正在更新到账结果”，按后端结果进入已到账或到账核实中，不把资金事实改成取消。
- 查询或关单超时：显示“暂未确认取消结果，正在继续核实”；仍可按后端能力结束本站操作，达到本站截止后进入本地超时结果，不等待渠道关闭才能返回。

本地结束确认统一给出内联说明，无在线取消能力的渠道也适用：

> 确认结束后将返回充值。此操作不会关闭渠道原支付页面，请关闭旧页面；如果已付款，请先核实结果，避免重复充值。

不显示能够成功取消的假按钮，不把本地结束称为渠道关单。无法核实时保留原资金处理责任与客服入口，允许本站结束／超时结果按规则明确返回；本地已结束／超时后的用户和管理员均无人工核实或补单入口。后来获得可信收款事实时，按已到账／到账核实重新呈现资金责任。

### 6.4 超时与有效期

- 本站操作期限统一为创建后 30 分钟，已确认渠道截止更早时取更早值；后端返回服务端时间、有效截止及 local_policy／provider 来源。客户端只能展示及重新查询，不能延长或自行解除门禁。
- 达到服务端截止即停止续付并返回 timed_out／closed 结果，钱包显示“本次充值已超时”、主按钮“返回充值”和“查看订单记录”。无需等后台扫描、渠道关单或历史写回；关闭浏览器、页面隐藏和客户端时钟回拨不改变本站到期判断。
- 本地原因／时间与渠道关闭证据分别保存。真实渠道确认未付款且已关闭／到期时保留 expired；用户渠道取消保留 cancelled，均不由本站超时伪造。不得将 timed_out 文案写成“渠道已自动取消”或“原链接已失效”。
- 原支付页可能仍可付款，结果说明提示关闭旧页面、避免重复支付；结束／超时后无恢复、再取消、再次结束、人工核实或补单入口，后台有限核实和可信回调仍保留。
- 用户点击“返回充值”后，由服务端校验结果并结束对应当前流程，恢复表单与新报价；原记录继续可查，不自动创建新单。支付成功、用户主动取消和可靠失败保留原有结果确认流程。重新进入钱包或换设备时恢复尚未确认的结果阶段，不依赖倒计时事件是否曾在本设备触发。
- 已确认收款的 success／credit_review 优先于本地截止及结束标记，不能按账龄变成未付款废单。仅渠道 processing 不证明已收款或未付款；本站操作可到期，但不能据此生成渠道未付／关闭事实。
- 已知创建时间的旧 pending 按同一有效期限显示超时废单并移出其他未完成数；创建时间缺失且无可信终态时显示 unavailable、只读／帮助，不伪造超时时刻。Pancake 等服务商自己的期限仍保留原事实。

### 6.5 支付返回与查询结果

第三方回跳、用户返回钱包、钱包页面重新获得焦点或从隐藏变为可见时向后端查询当前订单，合并短时间内重复触发的核实请求。关闭外部支付标签页并不一定触发可可靠识别的事件；不得依赖检测第三方标签页关闭来恢复卡片。当前卡在支付打开期间一直保留，用户回到钱包即可看到。

回跳参数、标签页关闭和重新获得焦点都不是付款或取消凭证。查询按钮使用“刷新结果”，不使用会造成确认错觉的“我已支付成功”。未获得新证据时保留当前已知事实及更新时间，不因焦点切换虚构终态。

仅对可见页面里当前正在处理的订单做短时结果轮询，建议每 5 秒一次、单次等待最多 2 分钟；进入结果、页面隐藏或轮询窗口结束后停止。期限内仍未知时按后端能力提供“刷新结果”“结束本次充值”和帮助；结束／超时后仅查询本站记录，不触发人工渠道核实或补单。后台自动核实有界，可信回调与已存收据恢复不因前台停止而中断。

到账后同步刷新余额和当前订单，二级记录的状态与数量同步更新；结果按 4.1 节保留到用户明确返回充值，期间仍不显示在线充值表单。主文案分别为：

- 处理中：“支付结果正在确认，此笔请勿重复支付。”
- 未确认是否收款：“支付结果待核实，可稍后刷新或联系客服。”
- 已验证收款但尚未完成入账：“已收到付款，到账正在核实，此笔请勿重复支付。”
- 成功：“充值已到账。”

文案不得暴露 session ID、数据库错误、任务租约、迁移版本、内部异常码或支付 token。用户需要的是当前事实、下一步和订单号；技术诊断信息仅对具备权限的管理员显示脱敏摘要。

## 7. 旧订单收敛与管理员核实

### 7.1 用户侧

已知创建时间的旧 pending 按本站相同期限显示 timed_out／closed，保留记录并移出其他未完成数，不等待渠道证明未付；这不是渠道 expired，也不修改原付款事实或删除历史。可信已收款的显示 success／credit_review；缺失创建时间且无可靠资金／关闭事实的显示 unavailable、无手动支付或补单动作。

待核实订单不冒充可继续支付订单。未确认收款的当前操作可按后端能力结束，或在本站到期后进入超时结果，再由用户明确返回；已确认收款未到账的保留核实责任，不能按账龄隐藏。历史只读定位不创建或替换当前流程；废单不计入其他未完成数，资金责任单继续保留。页面显示最近检查时间，不承诺未经确认的到账时间。

没有本次当前流程时，历史记录不永久封锁账户，用户仍可从空闲阶段充值；存在当前流程时须先进入可确认结果（含 ended／timed_out），再明确点击“返回充值”，不等待渠道关单、不自动回表单。A 结束并返回后创建 B，A 晚收款只更新并入账 A，不替换或清除 B；A 重复通知只入账一次，第二笔不同交易保留异常，历史结束和渠道事件继续可查。

### 7.2 管理员侧

全平台视图的“待核实”筛选列出待处理订单。管理员展开订单后依次看到：原订单快照、已掌握的付款证据、最近核实结果、异常原因与操作记录。

废单在全平台列表、详情及旧 `/api/user/topup/complete` 均无人工补单／核实入口，直接请求同样拒绝；未知创建时间订单也不开放手工恢复。仅仍有效、允许核实的对象或已由可信事实进入到账核实的对象提供“核实支付”：

1. 先查询渠道支付结果或使用受认可的可信付款证据核对，不能凭订单仍为 Pending 就直接认定用户已付款。
2. 确认渠道、原商户身份、订单关联、金额与币种；若证据不全，保留待核实，并说明需要补充什么证据。
3. 可信付款符合原订单账务规则时，通过既有幂等入账流程处理；重复操作不会再次发放额度。
4. 可靠确认渠道未付款且已关闭／到期时保留渠道结果；本站 ended／timed_out 独立存在，不能靠人工核实重新开放其支付或补单。
5. 需要人工处理的差异、第二笔实际付款或账务限制，保留收款事实、原因和处理责任，不自动退款。

管理员说明应面向业务，例如“已查到付款，金额与订单不一致，需进一步核实”，不直接抛出 SQL、堆栈或密钥配置。必要内部标识可在权限保护的诊断区域查看。

无付款凭据的人工额度调整不属于“支付成功补单”，必须走独立权限、原因与审计路径。

### 7.3 存量处理任务

先运行只读统计，按渠道、账龄和可核实性形成处理报告。人工历史批次筛除本地已结束／已超时废单，在每笔执行前再次判断，报告后才到期也不得穿透。其余经独立明确授权的对象分批核实，任务可暂停和续跑；正常有界自动核实、可信回调和已存收据恢复使用独立路径，不受人工批次暂停或废单门禁阻断。

管理员界面展示已处理、已到账、已关闭、待核实和失败重试数量，统计口径必须可解释。归档仅改变管理视图，不删除订单、收据或资金记录，也不停止迟到付款处理。

## 8. 渠道能力尚未确认时的约束

| 能力事实 | 产品处理 |
| --- | --- |
| 支持恢复原会话，且仍在本站期限内允许付款 | 提供继续支付和结束本站操作，展示可靠金额、币种及本站有效截止 |
| 无法确认原会话是否创建成功 | 保留创建结果未知，原提交结束后可按能力结束本站操作；结束／到期后不重放创建 |
| 支持认证查询和可靠关单 | 开放取消与自动关闭，按实际响应更新结果 |
| 支持查询但不支持关单 | 期限内按能力核实；仍可本地结束／超时并明确返回，不显示渠道已取消 |
| 无可验证查询或关单能力 | 如实限制渠道动作，仍提供本站结束／超时结果及返回；废单仅只读／帮助，无管理员补单入口 |
| 只知道本站操作截止时间 | 到期显示 timed_out 和返回，不声称外部付款页失效；原单保留晚到款处理责任 |
| 已有渠道到期回执或可靠到期查询 | 可靠确认未付款且不能继续支付后保留渠道 expired；不作为本站返回前提，晚到款仍按原资金规则处理 |

易支付实际服务商的查单、关单、到期和重复商户订单语义是一期实施前必须确认的输入。SDK 缺少方法不等于服务商没有能力；源码中存在方法也不等于线上已经接入。

产品可以按已验证能力逐渠道开放，但每个已开放渠道都须符合本稿状态和操作规则。不能为了让所有支付方式都有相同按钮而虚假承诺取消或恢复。

## 9. 可测验收标准

| 编号 | 操作或条件 | 预期结果 |
| --- | --- | --- |
| A01 | 下单打开外部新标签支付页，再关闭该标签页 | 本站期限内钱包保留原单，可重开原会话、结束本次充值或按能力取消；不生成第二个可付款会话，到期后不再重开 |
| A02 | 换设备登录并搜索本人订单号 | 本人可定位原单，不依赖浏览器存储；他人或其他租户不能读取、恢复、结束、取消、核实或确认返回 |
| A03 | 同次提交重复点击、网络超时后重试 | 同幂等操作返回原单或创建结果未知，不重复创建；同键变内容拒绝；本地结束／到期后不重放该单创建 |
| A04 | 支付跳转失败或弹窗被拦 | 已创建订单保留，期限内有原会话手动恢复入口，不误报已打开；已结束／到期则显示相应结果，不开放旧支付 |

| A07 | 关单查询超时、暂时查不到或渠道无取消能力 | 不显示渠道已取消；可按能力结束本站操作，本站到期进入 timed_out，结果明确返回，不等渠道关闭永久锁定；后台资金责任保留 |

| A14 | 本站已结束／已超时、渠道可靠取消／过期、可靠失败或已到账 | 超时及其他可靠结果保留查看记录和返回，用户确认后恢复表单；主动 end 成功串行精确确认后直接回表单，失败保留结果与重试；列表与数量同步，本地与渠道终态分别表达 |

| A18 | 临时断网或切换后台 | 当前订单及处理状态可恢复；后台停止短时轮询，重新可见时查询后端 |

## 11. 本次设计确认点

本稿推荐整体确认以下一套设计，不提供多条产品方向：

1. 钱包主区按空闲／创建中／当前订单／处理／结果互斥显示；订单阶段隐藏购买入口。本站 30 分钟或更早渠道截止进入 timed_out，用户主动 end 成功进入 ended 后同次串行精确确认并直接回表单，失败保留返回重试；超时保留“返回充值”，点击精确确认后恢复表单，不等待渠道关单。记录仍为二级入口。
2. 六个筛选与本稿状态动作矩阵；待核实有真实处理责任，不能冒充已付款或已关闭。
3. 支付在外部新标签页打开，钱包始终保留当前订单；回到钱包可重新打开原会话，不必进入记录。已关闭后重新充值使用新订单号。
4. 渠道 cancelled／expired 基于可靠证据；本地 ended／timed_out 独立表达，不能声称原链接失效。真实晚到款仍按原单入账或保留异常处理责任。
5. 用户、管理员、旧补单和人工历史批次均不提供废单恢复／核实／补单；老 pending 按本站期限投影废弃，不删除原单，不将已确认收款按账龄作废。

渠道实际能力和生产数据事实仍需在后续获授权的实施环节确认；本稿不替代这些证据，也不对真实截图订单作状态修改。

# KKAI 发票中心产品需求文档（推荐方案）

- **版本**：v1.1 开发基线
- **日期**：2026-10-22
- **状态**：需求基线已实现于本地，尚未在生产启用；示例数据均为虚构，不能作为正式发票。实施范围与验证边界见[实施记录](./invoice-center-implementation.md)。
- **目标**：让用户从真实付款订单发起开票申请，管理员完成审核和票据交付，用户完成收票确认或提出异议，整个过程可追溯且不重复开票。
- **配套交付**：[开发技术文档](./invoice-center-development.md)、[UI 实现与验收规格](./invoice-center-ui-spec.md)、[设计参考源码](./invoice-center-design-preview.html)。业务规则以本文和开发文档为准，布局/控件细节以 UI 规格为准；原型的演示限制不得直接成为生产逻辑。

## 1. 推荐结论

新增独立的「发票中心」，与钱包、会员订单关联，但不把发票状态塞进充值订单或会员订单。

首期支持两类来源：

1. **充值订单**：已支付成功，并且平台留有经验证的实际支付金额和币种。
2. **新会员订单**：直接付款成功，实收金额、币种、支付回执已核验的 `MembershipOrder`。会员过期、额度用完或会员降级，不影响该笔真实付款的开票资格。

以下情况不直接计入可开票金额：

- 旧订阅订单缺少可靠的实收金额/币种凭证；
- 余额支付的会员订单；
- 兑换码、赠送额度、管理员赠送；
- 支付异常、退款、拒付、冲正或重复回执。

旧订阅镜像到 `TopUp` 的记录必须与原支付来源去重，不能让同一笔钱出现在“充值”和“订阅”两条可选记录中。余额支付不会产生新的可开票现金；用户应查看对应的原始充值付款，避免重复开票。

## 2. 业务边界与默认规则

### 2.1 订单合并

- 同一用户、同一租户/站点、同一卖方主体、同一币种的订单可以合并申请。
- 只有财务确认税目、税率和服务明细兼容时才合并；不兼容的订单自动分组或要求分开申请。
- 不跨币种、不跨卖方主体、不支持部分金额或拆单开票。
- 每张新申请的实付合计至少为人民币 200 元，可合并多笔未开票订单达到门槛；金额恰好 200 元可申请。门槛可提高，不可低于 200 元，不追溯阻断既有申请的交付或更正。
- 一笔真实付款在待审核、待开票、待确认、异议处理中、待重新确认、财务待核查或已确认时持续占用；只有从未交付过正式票据、经财务确认未实际开具的申请被拒绝后才释放。
- 已开票订单不能再次申请；收票确认、异议、财务暂停或补发均不释放付款占用，补发只增加原申请的交付版本。
- 一期每张申请最多选择 50 笔订单；不提供提交后撤回、删除或部分金额开票。

### 2.2 金额口径

发票金额使用支付渠道核验的实际支付金额，按最小货币单位精确汇总，不使用充值额度、赠送额度或历史浮点展示金额推算。支付手续费是否影响发票金额由财务确认；推荐默认按客户实际支付金额开具。

### 2.3 支付数据完整性与上线门槛

产品范围包含直接付款的会员订单，但订单只能在支付回执核验结果和实际实收金额已可靠持久化后，才可进入用户的可开票列表。当前项目各支付渠道的数据落库并不统一：`TopUp` 有 `PaidMinor` 和 `Currency` 字段，但现有实现并未为所有渠道一致保存最终实收快照。因此，不能仅凭产品范围或页面展示就开放所有支付来源。

- 每个可申请来源必须能提供经验证的实收最小货币单位、币种、付款完成时间和渠道交易凭证标识；订阅订单也必须满足同样条件。
- 支付回调应幂等地写入不可歧义的付款快照。旧订阅镜像成充值记录时，必须通过原始付款来源去重。
- 缺少实收凭证或金额快照的订单显示为「待人工核验」，不展示推算金额、不计入可开票金额。
- 不得使用 `TopUp.Money`、套餐标价、充值额度、赠送额度或历史浮点金额代替实收金额。
- 充值历史列表的默认时间筛选不能限制可申请订单的查询范围；申请订单查询应覆盖全部有凭证的历史订单，并单独处理资料缺失的旧订单。

建议按来源逐步开放：先为支付快照完整且财务规则已确认的来源上线，再逐渠道补齐实收快照和异常处理，最后开放相应来源。此门槛不改变会员订单的产品资格，只防止未经核实的金额被开票。

### 2.4 票据与管理员审批

管理员“审核通过”只代表资料和订单符合要求，不代表税务发票已经开具。

管理员完成合法开票后上传正式原件（一期优先 PDF，也可上传 PNG/JPEG 预览图），填写发票号码、开票日期、金额等信息，系统校验成功后才向用户交付。

### 2.5 用户确认与异议

用户确认表示“已收到并完成当前页面可见的信息核对”，不表示放弃法定更正、售后或税务异议权利。

用户提出异议时：

- 不自动退款；
- 不自动释放已占用的订单金额；
- 不自动撤销或删除已交付的发票；
- 管理员需要回复、补发新版本或进入财务更正流程。

会员订单即使已经到期，也不因此失去其真实付款的开票资格。

## 3. 状态流转

```
待审核 → 待开票 → 待确认 → 已确认
  └─ 已拒绝          └─ 异议处理中 ← 已确认后反馈
                           ├─ 回复说明 → 待重新确认 → 已确认 / 继续反馈
                           └─ 补发新版本 → 待确认
```

退款、拒付或支付证据异常进入“财务待核查”，暂停流程并保存原阶段。已交付过的文件继续可查看；禁止通过拒绝释放已经开过票的付款。恢复时重新核验付款事实，回到合法阶段。正式状态与允许动作详见开发文档第 5 节。

## 4. 用户端信息架构

### 4.1 入口

- 钱包充值历史：增加「申请开票」。
- 会员订单历史：增加「申请开票」。
- 独立页面：`/invoices`，侧栏归入“财务”。
- 一期仅主站用户可申请、主站平台管理员可处理；租户站点在卖方主体与税务规则具备前关闭该能力，服务端必须同时校验 host、用户和角色。
- 旧的充值跳转路径继续进入钱包，不破坏现有入口。

### 4.2 发票中心

页面顶部：

- 标题「发票中心」
- 主按钮「申请开票」和「开票说明」入口
- 摘要卡：可申请金额、处理中申请数、待确认发票数

主页签：申请开票、申请记录、常用抬头。申请记录采用列表与详情联动，显示：

- 申请编号
- 抬头
- 订单来源与数量（充值 / 会员）
- 金额和币种
- 状态
- 提交时间
- 查看详情

记录筛选：全部、处理中、待确认、已完成；另提供明确状态、申请号/订单号搜索、日期和分页。待确认包含“待确认”和“待重新确认”；处理中包含待审核、待开票、异议和财务待核查；已完成包含已确认、已拒绝。

### 4.3 推荐申请页：双栏、三步

桌面端采用双栏布局：

- **左栏**：当前步骤表单与订单列表，占剩余空间。
- **右栏**：236–320px 的选择/金额/资料摘要和下一步操作，具体宽度/断点遵循 UI 规格。
- 移动端改为单栏，摘要转为底部固定栏。

#### 第一步：选择订单

订单筛选：

- 来源：全部 / 充值 / 会员
- 日期范围
- 订单号搜索
- 币种

每行显示：

- 复选框
- 来源标签
- 订单号
- 支付时间
- 支付方式
- 实付金额
- 可开票状态

「暂不可开票订单」独立区域包含「需人工核验」分类，不进入可申请金额汇总。跨币种、已占用、余额支付、重复来源和异常订单必须显示明确原因。表头只“选择本页”；筛选或翻页保留已选项，混合不可合并分组时禁止继续并给出拆分提示。

右栏显示：

- 已选订单数
- 按币种分组的小计
- 当前可合并性提示
- 「下一步：填写发票信息」

#### 第二步：填写发票信息

字段：

- 个人 / 企业
- 发票抬头
- 企业税号（企业必填）
- 发票类型（由后台财务配置）
- 接收邮箱
- 仅在票种需要时展示地址、电话、开户行、账号

不必要的银行信息不默认采集。常用抬头属于一期：个人/企业资料可新增、编辑、选择、软删除及保存；税号/邮箱等敏感信息加密保存、列表脱敏。修改或删除常用抬头不会改变历史申请快照。

#### 第三步：核对并提交

页面完整展示：

- 订单清单与总金额
- 卖方主体
- 发票类型
- 抬头、税号、邮箱
- 已经财务确认的处理时限（未配置时不承诺具体天数）
- 资料准确性确认框

提交成功后跳转申请详情，并显示申请编号。

## 5. 用户申请详情

详情页按时间线展示：

- 已提交
- 审核通过/拒绝
- 已交付
- 用户确认或异议
- 管理员回复和补发版本

待确认时提供：

- 预览
- 下载
- 「确认无误」
- 「发票有问题」

发票附件卡显示：

- 文件类型、文件名、上传时间
- 发票号码和开票日期
- 当前版本标识
- 下载和预览按钮

每次补发都创建新版本，用户必须重新核对当前版本。

已确认后仍保留「反馈问题」次操作，不将收票确认解释为放弃更正权益。回复说明只对同版本重新核对；更正补发必须创建新交付版本，旧文件可查且明确标记历史。

## 6. 管理端工作台

路径：`/invoice-admin`；详情为 `/invoice-admin/:public_id`。

### 6.1 待办首页

默认显示待处理队列：

- 待审核
- 待开票
- 异议处理中
- 全部申请（含“财务待核查”状态筛选）

筛选：

- 申请编号
- 用户名/邮箱
- 订单号
- 状态
- 日期
- 币种
- 订单来源

列表列：

- 申请号和用户
- 抬头
- 来源和订单数
- 金额
- 当前状态
- 提交时间
- 操作

### 6.2 详情工作区

沿用设计预览的「左侧申请队列、右侧详情工作区」，窄屏进入独立详情页：

右侧详情区：

- 用户与租户信息
- 发票抬头资料
- 订单付款凭证摘要
- 金额、币种、税目分组
- 历史申请和事件时间线

详情区底部根据当前状态显示：

- 审核通过
- 拒绝申请
- 上传发票
- 交付给用户
- 回复异议
- 补发新版本
- 财务暂停/恢复（主站平台管理员权限）

操作按钮只显示当前状态允许的动作，不能提供任意状态下拉框。

拒绝时必须填写用户可见原因。本期界面中的拒绝、暂停和回复说明均对用户可见，不提供内部备注输入；后续若增加内部备注，必须使用独立存储和管理员受众，不与用户反馈混淆。

上传发票分为两步：

1. 上传并校验文件和票据元数据。
2. 点击「确认并交付」，之后用户才可查看附件并收到通知。

## 7. 异议处理

用户可以选择：

- 抬头或税号错误
- 金额不符
- 附件无法打开
- 发票信息不全
- 其他

说明必填，支持补充附件。管理员可以：

- 回复说明，要求用户重新确认；
- 补发更正附件，创建新的正式交付版本；
- 标记需要财务线下更正；
- 通过异议消息请用户补充说明或佐证，不另建“待补资料”状态。

异议关闭前不释放订单占用。新版本交付后回到“待用户确认”，旧版本保留为历史记录。

## 8. 通知与服务承诺

用户中心及管理工作台提供“进度通知”入口、未读提醒、查看单项与全部已读；通知未读与待办数量分开。站内通知覆盖：

- 提交成功
- 审核通过
- 审核拒绝
- 发票已交付
- 异议回复
- 新版本补发
- 用户确认、异议/补充说明、财务暂停/恢复（按接收方权限显示）

推荐默认文案：

- 「申请已提交，可在此查看审核进度。」（具体时限仅在财务配置后显示）
- 「申请已通过，财务正在开具发票。」
- 「发票已送达，请核对抬头、税号和金额。」
- 「已收到你的反馈，我们会在此更新处理进展。」
- 「此订单由余额支付，请查看对应充值付款，避免重复开票。」

邮件通知可作为补充，不能成为状态成功的必要条件。

## 9. 视觉设计稿方向

不建议使用大幅营销插画。发票是高信任、低娱乐性的财务页面，推荐：

- 现有产品风格延伸：轻背景、清晰文字、使用产品主题主色。预览为蓝色示意，生产复用主题变量并支持深色模式。
- 状态使用颜色、图标和文字三重表达，不能只靠颜色。
- 卡片圆角适中，减少过度装饰。
- 订单来源使用小型标签：充值、会员。
- 申请页右栏使用清晰的金额摘要和步骤进度。
- 发票预览使用虚构抬头、虚构税号，并加「设计示例 · 非正式发票」水印。
- 不生成真实税票、真实税号、真实公司信息或可能被误用的官方票据图样。

推荐设计稿包含 6 张核心界面：

1. 用户发票中心；
2. 订单选择页；
3. 发票信息填写页；
4. 提交核对与申请详情；
5. 管理员待办工作台；
6. 管理员上传交付与异议处理页。

## 10. 关键验收

- 充值和已核验直接付款会员订单可以同单申请，金额精确且来源清晰。
- 会员过期、额度用尽不影响真实付款订单的开票资格。
- 旧订阅镜像 TopUp 不与原支付重复出现。
- 余额支付不产生新的可开票现金。
- 待核验订单不计入金额汇总。
- 同一订单不能被两张有效申请重复占用。
- 从未交付且确认未实际开具的申请被拒绝后可重新申请；已交付、确认、异议或财务暂停中的付款不能释放。
- 管理员通过后不会立即显示“已开票”。
- 上传失败、金额不符或重复点击不会造成假交付。
- 用户只能访问自己的申请和附件，不能跨用户或跨 tenant。
- 异议不会自动退款、自动释放金额或删除历史票据。
- 新发票版本必须重新确认。
- 桌面和移动端均能完成核心流程，关键状态不依赖颜色，表单错误可被读屏识别。
- 所有业务状态和文案支持现有多语言体系。
- 常用抬头的增删改选、异议佐证、同版本重新确认和历史版本访问均有明确接口与验收条目。

## 11. 发布前必须由财务确认

1. 卖方法律主体和租户开票主体关系。
2. 支持的发票类型、税目、税率和币种。
3. 客户实付金额与支付手续费的开票口径。
4. 充值、会员、余额支付之间的合法归属与去重规则。
5. 退款、拒付、冲正后的红字/更正处理。
6. 发票原件格式、附件留存期限和访问权限。
7. 审核与开票的服务时限。
8. 是否允许个人抬头、企业抬头、专票以及地址/银行信息。

在上述事项确认前，不应把产品文案写成“系统自动开具税务发票”；系统应表述为申请、审核、票据交付和异议处理。

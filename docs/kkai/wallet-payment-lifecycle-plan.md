# 钱包充值订单生命周期修复方案

**2026-10-24 交互修订：** 主动确认结束成功后，在同一次用户操作内串行精确 acknowledge，成功直接回充值页，无需再点返回；失败保留 ended 与返回重试。自动超时仍保留超时提示和“返回充值”按钮。自动确认只作用于原身份、flow/revision 与原订单均仍一致的 ended 结果，实际收款、身份变化、另一当前流程和迟到旧响应不能自动清理。以下条款按此区分主动结束与自动超时。

**2026-10-23 生效修订：** [本站超时与废单规范](./wallet-payment-local-timeout-spec.md)已获用户确认，统一规定本站 30 分钟期限、本地结束／超时结果及“返回充值”、废单禁止继续支付／人工补单、晚到款继续处理。本文下方与修订冲突的“仅本地超时不能结束、未知永久锁定、30 分钟仅期望、废单仍可人工核实”条款停止适用；其余资金、权限和互斥布局要求保留。

## 评审结论

由三个独立评审代理分别承担支付架构、资金安全与并发、钱包体验与质量角色，并交叉讨论。
推荐在现有 `TopUp`、`FinalizeTopUp` 和钱包订单记录上补齐生命周期。

核心决策：

1. 一笔充值订单只对应一个可付款会话；继续支付恢复原会话，重新充值产生新订单号。
2. 本地支付截止、渠道关单结果、实际收款和额度入账分别保留依据，由后端统一决定展示状态与操作。
3. 可信的真实付款优先幂等入账；本地取消、过期不能成为吞掉资金的理由。
4. 本站操作期限固定为创建后 30 分钟，取已知更早渠道截止；未确认收款的旧 pending 按同一期限成为只读废单，不留人工补单／核实入口。可信晚款独立按原订单处理。
5. 复用现有系统任务、账务事务、租户资金批次和返佣 outbox；本期范围限定为钱包余额充值。

本稿依据当前本地源码。未查询生产配置或实际支付服务商文档，不能据此声称线上渠道已支持查询、关单或某个有效期。

## 用户状态与操作

后端统一返回 `display_status`、`allowed_actions`、服务端时间、实际可用的截止时间和简要原因。
前端只据此呈现按钮；所有变更接口仍重新鉴权、重新检查状态和渠道能力。
倒计时归零只停止前端发起续付并触发结果查询，不能把订单自行改成资金终态。

| 页面状态 | 判断依据 | 用户操作 |
| --- | --- | --- |
| 待付款 | 原会话已就绪，未超过本地截止且未结束 | 继续支付、结束本次充值；渠道能力允许时取消订单 |
| 支付确认中 | 渠道已受理或正在处理，尚未形成可靠终态 | 刷新结果，提示此笔请勿重复支付 |
| 取消处理中 | 已持久化渠道关闭请求，仍在本站期限且未本地结束 | 刷新结果、按能力结束本站操作，停止本单续付 |
| 本次充值已超时／已结束 | 无已确认收款，本站期限到达或用户主动结束 | 超时保留结果和返回按钮；主动 end 成功串行精确确认后直接回表单，失败保留 ended 与重试。均不等待渠道关闭，历史只读／客服 |
| 已取消 | 渠道确认关闭，或能证明从未形成可付款会话 | 保留结果与详情，当前流程明确返回充值后才恢复表单 |
| 渠道已过期 | 确认未付款且支付会话可靠到期／关闭 | 保留真实渠道关闭说明与返回充值，不与本站超时混同；精确确认后恢复表单 |
| 支付失败 | 渠道确认终态失败，或确认创建未发生且无可付款会话 | 保留原因，当前流程明确返回充值后才恢复表单 |
| 已到账 | 可信收款已完成额度入账 | 保留明细，当前流程明确返回充值后才恢复表单 |
| 支付结果待核实 | 尚未结束且未到期、已建立责任的未知结果 | 按能力核实／结束、联系客服；到期无已确认收款则转本站超时 |
| 已收到付款，到账核实中 | 收款已验证，但归属、额度或其他账务问题阻止入账 | 查看订单号、联系客服，提示此笔请勿重复支付 |

渠道“已过期／已取消”须有可靠关闭证据；本站 ended/timed_out 独立记录 local_ended_at/local_end_reason，不填写渠道 closed_at／证据。本站期限到达即显示超时结果，不承诺外部旧页已失效；已确认收款／credit_review 优先。创建时间未知且无其他已确认事实为 unavailable，不伪造期限。
待核实订单退出普通待付款队列，但保留在本人历史、精确查询和管理员待处理入口中。
它不能因换了文案就失去后续处理责任。独立历史核实记录不能永久阻止新充值；有效期内未结束的当前未知订单保留处理阶段；可经服务端本地结束／到期及精确确认返回，不能由前端擅自归档解锁。

## 数据与实现边界

本期保持一订单一会话，增加最少的持久化信息；不引入多次支付尝试平台。
具体字段及迁移版本在实施时依照当前 schema 契约确定，下列为必须保存的业务信息。

- **冻结的订单快照**：充值额度、应付金额最小货币单位、币种、渠道、原商户账号／环境引用、产品及合法优惠规则。沿用已有可靠快照字段，避免两份可修改的金额来源；实际实收另存收据。不得用当前价格、汇率或商户配置重算旧订单。
- **结账会话**：渠道 session/order ID、原支付链接或签名表单、渠道返回的有效期，以及创建 claim、创建时间和结果是否确定。checkout 数据仅服务端保存，经本人授权的恢复接口按需返回；不能随历史列表公开，也不能写进普通日志。
- **本地截止与结束、渠道关闭意图**：本站截止及来源，独立 local_ended_at/local_end_reason（user_ended/timeout）；渠道关闭申请、原因、closed_at 及可靠证据另存。本地结束及关闭意图都不等于渠道已关单。
- **对账进度**：最近检查、下次检查、重试次数和脱敏结果。创建不确定与付款结果未知分别记录用途，避免再建一套与订单状态重复的 open/expired/cancelled 状态机。
- **资金回执明细**：保存规范化的可信付款凭据、原订单／session 关联、商户／环境、实收金额币种、付款／接收时间、处理结果和异常原因。唯一收款键为渠道＋商户账号／环境＋渠道交易 ID；一单可以保留多笔付款事实，但只发放一次订单额度。

资金回执是钱包的收款依据。现有 `invoice_payment_receipt.go` 仅覆盖部分平台易支付、依赖可选发票 schema，
不能当作所有渠道、所有租户的通用收款账本。新链路仍须保持现有发票证据、租户资金批次、返佣和信用纪元规则一致。
发票收据由已验证的钱包收据幂等关联或派生，在相关入账事务中同步必要证据，保留原有唯一性保护与异常 hold；
不能因引入钱包收据绕过既有发票异常，也不能让可选发票 schema 成为所有渠道保存收款证据的前置条件。

业务订单状态可沿用当前状态并补足取消、待核实等缺失语义；支付确认中、关闭处理中由明确的渠道结果和请求字段派生。
状态转换集中在服务层，页面和各个回调不得自行拼装另一套规则。
schema 使用跨 SQLite、MySQL、PostgreSQL 的类型和唯一约束；JSON 内容通过项目 `common` 包处理。

## 关键流程

### 创建与继续支付

1. 同一次下单动作使用稳定的请求幂等键，在用户／租户范围内绑定订单和请求内容；重试返回原订单，相同键但金额等内容变化则拒绝。先持久化原订单、冻结快照和创建 claim，再以固定幂等键创建渠道会话；网络调用在数据库事务外执行。
2. 以数据库约束／行锁保证重复点击、跨设备请求不会创建第二个可支付会话。渠道不支持可靠幂等创建时，超时先查询确认，不能直接再发一次创建请求。
3. 将原会话信息保存成功后才向页面交付支付入口。远端已创建但本地保存失败时，用原幂等键／商户订单号恢复；保留可追踪的不确定状态。
4. 恢复接口校验用户、租户、截止时间、关闭请求和当前 session，返回原会话。对外不承诺可以恢复缺少关键凭据的历史订单。
5. 无已确认收款时，本站到期保留结果与“返回充值”，点击精确确认后恢复表单；主动 end 成功同次串行精确确认后直接回表单，失败保留 ended 与重试，重新提交使用新订单号；结束／到期的未知创建不重放，即使随后进入 credit_review。原订单保留，不能在原单下悄悄重新创建一个可付款 session。
6. 创建结果与渠道关闭／本地结束并发时，保存结果前核验最新版本、关闭意图及本站期限；不得在用户已结束或到期后再交付活跃支付入口。

### 用户取消与自动到期

1. 校验本人／租户和可用操作，持久化关闭意图，立即停止平台续付；重复取消幂等返回当前结果。
2. 在事务外查询渠道：已支付进入可信入账；处理中继续确认；未支付且支持关单则请求关闭。
3. 收到可靠关单／到期结果后，重新锁定原订单，并核验目标 session 和并发版本，写入 cancelled/expired。
4. 有效且未结束的查询或关单超时保留核实并有限退避；本站结束／到期后转本地结果，不保留人工核实入口，自动收款处理有界继续。只有经过协议验证的“确认未创建”才可当作无会话；暂时查不到订单不自动等同未支付。
5. 任何过期、取消、失败结果都不能覆盖已经成功的订单。渠道已收款与本地取消竞争时，以真实资金事实处理。
6. 本站期限为创建后 30 分钟，取已知更早渠道截止，不依赖浏览器或后台先写回；无已确认收款时到期派生 timed_out，主动结束为 ended。超时或未确认 ended 保留准确结果、显眼返回充值及查看记录；主动 end 成功同次串行精确确认后直接回表单，失败保留重试；提示原支付页可能仍可付款，已付款继续核实，请关闭旧页并避免重复付款。超时仍由用户点击并经服务端精确确认后恢复表单，不自动跳转。渠道取消／过期仍须可靠证据，但渠道无关单能力不阻止本地结束。真实收款／credit_review 优先，普通 processing 不延长本站期限。

后台复用 `service/system_task.go` 的持久任务、租约、进度和后台写入角色门禁。
新订单及时对账与历史批量处理使用独立任务类型／处理预算，历史积压不能饿死正常支付。
任务可暂停、续跑和重复执行；采用带索引的到期查询、游标分页、有限批量、速率限制和退避。
订单列表读取保持只读，不在每次打开钱包时无界扫描或写入整批历史数据。

### 真实收款、迟到回调与人工操作

1. 渠道通知先验签，查询结果先认证；核验渠道、原商户账号／环境、原订单与 session、币种和冻结的合法计价规则。
2. Stripe 已支持优惠码，合法实收须按原订单允许的优惠规则验证，不能简单要求实收等于标价，也不能使用当前配置放宽旧规则。
3. 可信收据必须持久化，并建立明确的待处理责任。额度入账、订单成功和收据处理结果在数据库事务内协调，复用现有账务链路；同单和同渠道交易重复通知只能入账一次。
4. 本地已过期／已取消但付款证据完整且满足账务规则的充值，自动幂等入账，并保留此前关闭记录。
5. 无法验证归属、金额异常、旧信用纪元限制、额度超限或同单第二笔真实付款，保留收据及原因进入异常处理。同单第二笔款不能再次发放原订单额度，也不自动退款。
6. 业务异常不能把可信收据一起回滚掉。只有已入账，或收据与后续处理责任已可靠保存，才确认通知；数据库无法保存时让渠道重试。已保存未处理的收据由后台重试兜底。
7. 本地结束／超时废单禁止续付、恢复、再取消、人工补单／核实，覆盖用户／管理员界面、旧 complete API 及人工批次；只有非废单的合法操作按能力改为“查询支付结果并核实入账”。无付款凭据的人工额度调整使用独立授权、原因和操作审计，不伪装为支付成功。

必须先修 Creem 的非 pending 提前确认、Waffo 的非成功统一失败、Stripe 的读取后整行保存。
也不能直接放开 `FinalizeTopUp` 的所有 expired/failed：管理员补单同样调用此入口，
`invoice_payment_receipt.go:31` 的金额校验目前只覆盖 pending，需在可信收款入口中补足与状态无关的验证。

## 渠道能力与期限

| 渠道 | 本期方案与已知限制 |
| --- | --- |
| 易支付／微信／支付宝入口 | 当前 SDK 仅签名生成表单与验签。实施前核实实际服务商的查单、关单、有效期与重复商户订单语义；按真实协议用现有 HTTP 能力接入。SDK 没有接口不证明渠道没有接口。未验证前不宣称可自动关单。 |
| Stripe | 保存 session ID 和实际 expires_at，复用查询／Expire 能力。异步付款处理中不能按未支付直接过期；成功与失败结果统一走安全状态转换。 |
| Waffo | 接入 Inquiry／Cancel 和实际有效期；所有渠道状态按明确协议映射，处理中不记 failed。 |
| Waffo Pancake | 持久化 session/order ID 和实际有效期，保留现有请求 45 分钟的行为直至验证调整。SDK 的 BuyerSession 取消需要特定 buyer token 和 order ID，不能假定 checkout token 就是商户关单凭据。 |
| Creem | 持久化 checkout／产品快照并先修迟到成功处理；查询、关闭与期限按实际 API 能力确认后开放。 |

本站操作期限统一为创建后 30 分钟，已知渠道截止更早则取更早值；已知创建时间的旧 pending 同样生效，无需历史批量写回。渠道创建参数仍满足真实支持范围并单独保存有效期，例如 Pancake 原 45 分钟不改写为本站期限；未知创建时间不伪造截止。
服务商无法查单／关单时仍可结束本站操作，不能承诺外部旧页失效；废单仅保留只读详情／客服及可信收款处理，不保留人工核实入口。

## 页面和 API 范围

钱包充值区采用互斥阶段：无当前订单时展示充值表单；创建订单后切换为完整订单详情，直接显示金额币种、额度、付款方式、订单号、截止时间与状态，提供重新打开原支付页面、按能力取消和刷新结果。订单阶段不展示充值表单、购买入口或独立余额卡；超时保留结果与“返回充值”；主动 end 成功同次串行精确确认后直接回表单，失败保留 ended 与重试；均不等待渠道关闭，原订单留在记录且无人工补单／核实入口。确认到账或主动取消完成后同样保留结果，用户选择“返回充值”再恢复表单。复用“订单记录”作为二级入口，增加状态筛选、按订单号定位和必要详情，不要求新订单中心。
服务端增加当前流程恢复、本人订单详情、恢复支付、本地结束、请求渠道取消、结果精确确认后返回充值，以及触发有速率限制的结果核对接口；历史接口增加展示状态、操作能力等可选字段。API／DTO 与文件级计划以 [开发总纲](./wallet-payment-development.md) 及其分册为准。
所有接口强制校验本人和租户，订单号不是访问凭证；订单列表与旧前端的兼容需明确过渡。

- 按本轮产品要求，在外部新标签页打开支付，钱包保留当前订单。处理异步创建后的弹窗拦截，未能打开时显示手动“打开支付页面”入口；再次打开必须恢复同一订单、同一会话，不能顺带生成新单或延长期限。
- 关闭外部支付标签页不会移除钱包订单卡片，也不取消订单。支付返回、浏览器返回和钱包重新获得焦点／可见性时查询后端；不能依赖可靠检测第三方标签页关闭，回跳 URL 或“支付页已关闭”都不是付款凭据。
- 当前充值阶段及可用动作由服务端恢复并校验创建权限，钱包刷新、重新登录、旧标签页或换设备不能绕过当前订单阶段。取消中、超时处理中与当前结果未知时保持订单详情；无已确认收款时，到期保留结果与“返回充值”，点击精确确认后恢复表单；主动 end 成功同次串行精确确认后直接回表单，失败保留 ended 与重试；无需等待渠道关闭。其他可靠终态同样按结果确认流程返回充值。订单记录始终保留。已由后端归入历史核实范围的旧单单独保留核实责任，不把所有历史 Pending 自动作为当前订单，也不能由前端擅自归档当前未知订单来解锁充值。
- 仅对可见页面中当前正在处理的订单短时轮询；完成后刷新余额和订单，切后台、终态或超时则停止。
- 恢复前展示冻结的应付金额及币种，区分充值额度；优惠确认后的应付金额按渠道结果展示，实际实收仅来自可信收据。修正当前“支付”只显示裸数字的问题。
- 下单前的取消按钮改成“返回修改”等准确文案；创建后才显示真正的订单取消操作。
- failed、未知、待核实等状态明确展示，全部状态文案使用现有 i18n 体系。
- 浏览器可保存最后订单号作为定位便利，恢复依据始终在服务端，不把支付 token 当普通本地偏好存储。

## 存量订单处理

先提供只读 dry-run，按渠道、原商户身份、账龄、会话数据和可用查询依据统计，不改业务数据。
人工批次报告、选单及执行前重读均跳过本地结束／超时废单；非废单在独立授权范围内受控核实并保存进度。可信晚款及收据补偿独立继续。

| 核实结果 | 处理 |
| --- | --- |
| 已付款、未入账，证据完整 | 按既有账务／信用纪元规则幂等入账；不能入账则保存收据进入待处理异常 |
| 渠道确认未付款且已关闭／已到期 | 写入已取消／已过期，保留历史 |
| 本站已结束／超时的旧 pending | 保留 ended/timed_out 只读历史，不计入其他未完成，无人工续付／关单／补单／核实／恢复；自动可信收款处理独立继续 |
| 有效范围内渠道仍可付款 | 仅按真实能力和授权请求关单，取得可靠证据后记录渠道结果 |
| 仍有效且未结束的缺身份／缺会话／查询失败 | 保留真实核实责任；不得以 review 延长本站期限。创建时间未知且无收款事实保持 unavailable，无人工补单入口 |

无渠道证据的历史单不能只因账龄大就声明未付款。
管理员可对已处理事项做界面归档，但归档不修改收款事实，也不关闭迟到回执的处理能力。
批处理有暂停、限流、幂等和报告；订单、收据、资金记录不作批量删除。
历史业务数据处理与应用发布分开执行，实施时分别明确授权与范围。

## 实施顺序与发布门禁

1. **确认渠道契约与兼容路径**：优先确认截图所涉易支付网关的查询／关单接口、账户归属和有效期；确定 schema 增量以及当前／回退运行契约。此项没有完成前，不承诺易支付自动关闭。
2. **建立资金安全底座**：持久回执、可信支付结果、迟到款、状态并发和人工补单边界；渠道过期／取消功能保持未启用。同步让前端能正确识别未来状态，旧字段继续可用。
3. **完善新单闭环**：冻结快照、原会话恢复、渠道查询／关单、后台对账及页面按钮；按能力逐渠道启用，不能将未验证渠道标为已支持。
4. **启用自动收敛**：先核对新订单路径和任务指标，再开启自动过期与取消。当前版本和回滚版本都须能安全处理新状态及迟到付款；仅关闭功能开关不能使已经产生的新状态被旧代码正确处理。
5. **处理存量**：先只读报告并排除本站废单，再在独立授权范围内分批运行；抽查入账、可靠渠道关闭及待核实样本，留下可续跑记录；不把废单重新放进人工核实。

新增字段／表属于 schema 变更，需按项目专用迁移流程获得独立授权，并验证三种数据库及精确运行契约。
不要用 `AutoMigrate` 在生产启动时顺带安装，也不要假设旧／回退镜像接受新 schema 或新状态。
若回滚基线尚不具备迟到付款保护，先交付兼容底座，待正式回滚基线具备该能力后再开启自动关闭；
具体运行版本与能力在实施发布时通过官方流程确认，本稿不推断当前安装情况。

观测至少覆盖：超时未收敛订单数量与最大账龄、查询／关单失败、创建结果不确定、已收款未入账、
重复凭据／重复付款、后台重试积压及任务最近成功时间。告警使用脱敏统计，支付链接、token、密钥不进入日志。

## 最小验收清单

| 场景 | 必须满足的结果 |
| --- | --- |
| 下单后关闭支付页、刷新或换设备 | 本人可找到原订单并恢复同一有效会话 |
| 重复点击、网络超时后重试创建／续付 | 不产生多个可付款会话；不确定结果能查询恢复 |
| 支付回跳早于回调、异步付款 | 展示确认中，最终到账一次并刷新余额 |
| 取消与成功、过期扫描与成功跨实例并发 | 成功不被关闭／失败覆盖，额度只发一次 |
| 关单超时、暂时查不到 | 不谎称渠道已关闭；无已确认收款时仍可本地结束／到期并精确返回，废单无人工入口 |
| A 本地结束并返回后创建 B，A 晚付款 | 只按 A 幂等入账，不替换／清除 B；未知创建不重放，旧 complete 及人工批次不能操作废单 |
| 过期／取消后的可信迟到成功 | 正常幂等入账，或有持久收据与明确异常处理 |
| 同交易重复通知／跨订单复用 | 不重复入账；非法归属不能套用为新收款 |
| 同一订单第二笔真实付款 | 保存额外付款异常，原订单额度不再次发放 |
| 金额／币种／商户不符、合法优惠码 | 严格验证异常，同时允许符合冻结规则的合法付款 |
| 额度超限、历史信用纪元、数据库失败 | 收据不静默丢失；有处理入口或渠道重试路径 |
| 超过 30 天的本人旧单、跨用户／租户访问 | 本人可精确定位；其他用户／租户不可读取或操作 |
| failed／未知／新状态、手机／Safari／键盘 | 状态准确且翻译完整，跳转失败可恢复，操作可访问 |
| 任务重启／租约丢失／历史批量积压 | 可续跑，不重复入账，不阻塞正常新单对账 |
| SQLite／MySQL／PostgreSQL、当前／回退版本 | 迁移约束有效，状态和 API 过渡符合发布契约 |

验证按资金／并发／schema 风险选择相关包与直接依赖的定向测试，并覆盖关键渠道模拟集成与真实受影响流程。
全量或预计超过五分钟、耗时未知的命令按项目规则先说明并取得批准；本方案评审不运行测试。

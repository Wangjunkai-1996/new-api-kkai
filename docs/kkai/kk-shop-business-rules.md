# KK 商城：交易、交付与售后业务规则

更新日期：2026-10-28。状态：首版业务规则基线，应用实现及实际验收范围见[实施状态](./kk-shop-implementation-status.md)。
本文定义应实现的行为，不表示商城、支付能力或配置已经上线。
产品范围见 [产品需求文档](./kk-shop-prd.md)，技术边界与已有能力见 [实施方案](./kk-shop-implementation-plan.md)。
涉及交易状态、资金与库存冲突时以本文为准；范围调整应同步修改两份文档。

## 1. 首版范围与规则优先级

- 单商家、主站自营；每个可售商品只有一种规格，每单一件，支持自动交付与人工交付。
- 沿用现有登录体系，购买与领取必须登录；不向租户站点默认开放商城。
- 首发仅一个已开通、允许首批商品类目且能力已核实的支付渠道、一种币种。
- 不增加商城储值、API 额度抵扣、充值赠额、充值返佣、优惠券、购物车或批量购买。
- 普通商品款首版仅支持全额退款；多收款按收款逐笔全额差错退款。
- 首版由管理员在支付商后台人工原路退款，商城记录审批、处理过程与结果证据，不调用自动退款接口。
- 不提供物流、发货地址或收货确认；“交付”指订单获得约定的数字内容或人工服务交付结果。

| 优先级 | 含义 | 发布要求 |
| --- | --- | --- |
| P0 | 钱款、库存归属、秘密访问、事实持久化与权限边界 | 必须完成并通过对应验收，不能用页面提示替代 |
| P1 | 首版完整购买、人工交付、补发、售后与运营处理能力 | 首版上线前完成；内部开发里程碑可以分批交付 |
| P2 | 运营效率增强，如更丰富筛选、提醒或统计 | 不阻塞首版，不改变 P0/P1 规则 |

P0 优先于操作便利；可信付款事实优先于浏览器状态、本地倒计时或管理员手动标签。
运营设置不能允许重复发货、忽略实收、超额退款、越权领取或自动回收已揭示凭据。

## 2. 开通前必须确定的业务参数

| 参数 | 当前状态 | 未确定时的处理 |
| --- | --- | --- |
| 首发渠道、商户身份、允许商品、实收及退款核验方式 | 待核实实际能力 | 不启用真实支付 |
| 币种、最小货币单位、允许金额范围 | 待确定 | 商品不能按不明币种收款；不套用 API 额度换算 |
| 库存预留时长、每用户未付款单上限 | 待渠道与运营确认 | 设计稿使用明确标记的演示参数，不能写成生产默认 |
| 支付入口可支付期限、查单和关单能力 | 待渠道验证 | 本地到期不能显示“支付渠道已关闭” |
| 人工交付预计时限、营业时间口径、接单容量 | 按首批商品确定 | 缺项商品不能上架人工交付 |
| 质保范围、起算事件、期限、例外和处理方式 | 按首批商品确定 | 缺项商品不能上架；不得承诺统一“七天无理由” |
| 凭据可查看时长、首次起算事件、补发起算规则、到期处置 | 按首批商品确定 | 售前明确且保存到订单快照，不用演示期限兜底 |
| 付款核实、交付异常、退款核实的处理责任人与提醒阈值 | 待运营确定 | 每个待处理项目必须可在后台找到，不能无人负责 |

任何样例中的“15 分钟”“24 小时”“7 天”等均须标注演示或待确认；本文不设固定到账、交付或退款时效承诺。
对客文案只能使用实际已配置、能执行且保存在订单快照中的时限与规则。

## 3. 订单的独立业务事实

### 3.1 付款事实

每笔支付尝试单独记录；一个订单可以有失败或结果未知的历史尝试，但只接受一笔有效商品款用于履约。
“收到钱”和“钱已正确匹配该订单”分开：金额、币种、商户、环境或订单身份不符时保留可信实收并进入差错处理，不自动交付。

| 付款展示事实 | 判定 | 允许推进 |
| --- | --- | --- |
| 未付款 | 没有可信、匹配的实收，且当前没有必须核实的支付结果 | 在订单可支付且库存预留有效时使用已有支付入口 |
| 付款核实中 | 支付创建、付款结果或实收匹配存在未决事项 | 查原交易、接收回调、后台核实；禁止盲目新建支付尝试 |
| 已付款 | 有可信且匹配的有效商品款 | 根据交付与售后事实决定是否交付 |

退款不会删除“曾经收款”的事实；退款另记原收款、金额、币种、原因、处理进度和确认结果。
相同支付商交易的重复通知仍是一笔钱；不同交易身份的两笔实收必须各自保存。
浏览器跳转成功、用户截图、管理员口头确认或本地订单状态均不能单独证明实收。

### 3.2 交付事实

| 交付事实 | 含义 | 进入条件 |
| --- | --- | --- |
| 未就绪 | 尚未取得有效商品款；可能持有临时预留 | 下单完成 |
| 待交付 | 已付且需要执行自动分配或人工交付 | 有效商品款已确认，无交付暂停 |
| 处理中 | 已有明确的交付处理责任 | 后台任务接手或管理员接单 |
| 待补充信息 | 人工交付缺少商品约定的必要资料 | 已说明缺项及提交入口 |
| 已交付 | 约定内容已安全保存并归属该订单，可供合法领取 | 成功提交交付记录；不能仅凭通知发送成功 |
| 交付异常 | 已付但缺货、资料不可用、处理失败或有风险阻断 | 保存原因类别、处理责任与下一步 |

“已交付”与“查看记录”分开。系统只能证明内容已提供及领取接口曾返回，不能据此断言买家已成功登录、内容有效或放弃售后。
交付记录不可覆盖；补发创建关联的新记录，旧记录保留但可停止对客揭示。

### 3.3 售后事实

| 售后事实 | 含义 | 对付款与交付的影响 |
| --- | --- | --- |
| 无申请 | 没有正在处理的售后 | 不额外限制交付 |
| 待审核 | 买家已提交问题或管理员登记差错 | 普通申请不自动关闭已交付内容 |
| 处理中 | 已受理排查、资料修复或补发 | 是否暂停交付/揭示必须明确记录，不能靠备注隐含 |
| 退款已批准/待执行 | 有权限的管理员批准退还有效商品款 | 立即暂停该订单新的交付及秘密揭示 |
| 退款处理中/待核实 | 已在支付商操作或结果尚未确认 | 保持暂停；不得显示退款成功 |
| 已补发/已解决/未批准/已关闭 | 本次申请的明确结论 | 保存理由与证据；不抹掉原交易和历史申请 |

退款成功仍保留历史交付；退款后停止领取，不表示买家已看到的密码能被收回。
重复收款差错退款只针对额外收款，不因退还额外一笔钱而暂停合法商品款对应的交付。

### 3.4 风险暂停

P0：风险暂停是独立订单事实，可以发生在没有售后申请时，不修改付款、交付或退款历史。后台订单详情提供“暂停交付与查看”和“复核恢复”。
暂停与恢复均要求有权限的管理员明确操作，并保存订单、内部理由、买家可见说明、证据引用、操作者和时间；普通备注或库存隔离不能代替该控制。
暂停生效后阻止新的交付、补发和秘密查看/复制，买家仍能查看处理进度及申请售后。风险影响多个订单时逐单记录，不通过普通商品下架隐含改变既有订单。
复核恢复只解除当前风险暂停；必须重新校验有效付款、退款/拒付与争议状态、库存、版本归属及查看期限，不能恢复过期凭据、绕过已批准退款或未经核实的资金事实。未解决争议不得恢复相关履约与揭示。

## 4. 订单聚合状态与动作矩阵

聚合状态用于说明当前主要进度，页面同时保留付款、交付、售后时间线，不以单个标签代替事实。
按以下顺序计算主状态：有效商品款已全额退款 → 有效商品款退款处理中 → 活跃售后 → 已付款下的交付进度 → 付款核实中 → 未付款订单关闭或待付款。
多收款差错、库存不足、人工补资料等同时存在时显示独立提示；不得让提示覆盖真实实收或退款结果。

| 主状态/条件 | 买家可用动作与文案 | 管理员可用动作 | 禁止动作 |
| --- | --- | --- | --- |
| 待付款，预留有效且支付入口已知 | `去支付`、`查看订单`、`结束本次购买` | 查询原交易、查看预留 | 改价、按前端金额收款、展示凭据 |
| 付款核实中 | `刷新付款结果`、`查看订单`；提示“正在核实付款，请勿重复支付” | 查原交易、处理差错 | 换交易号盲目创建付款、手工点击“已付款”发货 |
| 已关闭且无实收/无待核实结果 | `重新购买`、`查看记录` | 查看历史、继续接受迟到回调 | 恢复旧价格入口、宣称不可能再收款 |
| 已付款，待交付 | `查看进度`、`申请售后` | 执行交付、登记异常、审核退款 | 再次付款、取消成未付款 |
| 交付处理中 | `查看进度`、`申请售后` | 提交交付、要求必要资料、登记异常 | 通过重复接单重复分配库存 |
| 待补充信息 | `补充信息`、`申请售后` | 审查资料、继续交付 | 要求在普通文本粘贴登录密码或恢复码 |
| 交付异常 | `查看处理进度`、`申请售后`；提示“已收到付款，交付待处理” | 补货后继续、人工处理、批准退款 | 让买家再付一次、隐藏异常、假装交付完成 |
| 已交付且未暂停揭示 | `查看交付内容`、`复制指定字段`、`申请售后` | 查看交付审计、处理问题 | 每次查看分配新库存、无权限批量导出 |
| 已交付但凭据查看期限已结束 | `查看订单`、`申请售后`；提示“查看期限已结束” | 查看审计、处理未结事项 | 返回到期秘密、自动关闭未结售后/退款 |
| 售后处理中，未暂停揭示 | `查看售后`、`补充说明`；原内容仍可合法查看 | 解决、补发、批准退款、说明未批准理由 | 仅因提交售后删除历史交付 |
| 售后处理中，已暂停揭示 | `查看售后`；提示“交付内容暂不可查看，正在处理” | 按权限复核、恢复或退款 | 返回秘密、用复制按钮绕过暂停 |
| 独立风险暂停，无论是否已有售后 | `查看处理进度`、`申请/继续售后`；展示公开说明 | 有理由地暂停、核实证据、复核恢复 | 通过解除暂停绕过退款、资金争议或查看期限 |
| 退款处理中/待核实 | `查看退款进度`；提示“退款结果待核实” | 录入或核实同一退款结果 | 新交付、秘密揭示、重复无关联退款 |
| 渠道已确认退款失败 | `查看退款进度`；提示“退款失败，正在跟进” | 核实旧尝试后在同一责任下重试 | 当作未知或已退款、未排除成功/在途/拒付冲突就重退 |
| 拒付/外部退款存在未决资金争议 | `查看处理进度`；显示可公开的核实说明 | 登记后续事实、查证金额和结果 | 新增退款、继续相关履约、删除原实收 |
| 有效商品款已全额退款 | `查看退款记录`、`重新购买` | 查看审计、处理未结额外收款 | 重新领取旧凭据、自动回库 |
| 存在额外重复收款 | 订单主状态不变；提示“发现重复付款，正在处理额外款项” | 逐笔核对与差错退款 | 二次发货、把整单标成已退款 |

`重新购买`创建新订单并重新检查商品、价格与库存，不复活旧支付尝试。
同一订单不得同时存在两个活跃售后申请；重复提交返回现有申请。已关闭申请允许按规则新建后续申请并保留关联。
后台动作必须带理由并校验最新状态；按钮禁用只改善体验，服务器仍须拒绝已失效动作并返回最新可操作状态。

## 5. 下单、预留与支付创建

### 5.1 下单前与订单快照

P0：服务器校验主站、用户、商品上架状态、价格币种、销售资格、购买数量一件及接单能力。
订单保存商品名称、规格、售价、币种、交付内容、时限口径、凭据可查看时长及首次/补发起算规则、质保和退款条款快照；后续商品编辑不改写已成交约定。
客户端只选择商品与渠道，不决定最终价格；金额为整数最小货币单位，拒绝越界、负数、溢出或币种不匹配。
同一用户的相同下单幂等键返回同一订单；同一键对应不同商品或请求内容时拒绝并提示重新确认。
订单未付款且仍有效时按原快照支付；到期后重新购买使用新价格。停卖或凭据风险另按存量处理规则执行。

### 5.2 有限库存与人工容量

P0：自动商品下单时原子预留一份具体库存；一份库存同时最多属于一个订单，售出后不能被到期释放。
可售数量从库存事实计算，不能由编辑商品详情覆盖；预留、售出、隔离库存不计入可售。
人工商品需要有限接单容量；未付款订单可临时占用容量，付款后转为待处理责任，完成或安全关闭后释放对应容量。
未付款订单上限与预留期限需实际配置，并在提交订单时重新核验；限流不能代替库存归属约束。
到期释放与付款确认必须基于同一订单最新状态顺序处理；迟来的释放任务不得解除已确认售出的库存。

### 5.3 支付创建与未知结果

P0：调用支付商前先保存本地支付尝试、交易号、预期金额币种及商户身份；外部请求不持有库存数据库事务。
成功创建后保存原支付入口；用户恢复支付使用该入口，不重复创建。支付页面失效需依据渠道事实处理。
创建超时、连接中断或结果无法确认时记为“付款核实中”，使用原交易号查询，不能直接换号再试。
只有渠道证据能确认原尝试未创建或已不可付款，且订单仍可支付，才允许建立新尝试；原记录必须保留。
若渠道无法提供足够查单/确认能力，转人工核实并禁止自动重建；首发能力评估必须覆盖此路径。
未知支付结果不无限占库存：可按预留政策释放，但必须保留交易核实责任与迟到付款处理能力。

### 5.4 到期、用户结束与迟到付款

`结束本次购买`结束本地购买流程；提示“若已完成付款，请查看付款核实进度”，不承诺撤回外部支付。
到期优先核实原交易，渠道支持时按能力申请关单；未得到可信关单证据不得记录“渠道已关闭”。
允许按已确定政策释放库存，但原支付尝试仍接收回调和查询结果；待核实责任不能随订单列表清理而消失。
迟到款先保留真实收款，再尝试原子分配一份可履约库存或人工容量；价格仍以原订单快照核对。
无可用库存/容量、商品暂停交付或原约定无法履行时，进入“已付款，交付异常”，由管理员补足原约定或处理全额退款。
不能把迟到款改成余额、赠额、其他商品或无条件重新扣款；替代商品交易需未来单独定义，首版不支持。

## 6. 付款确认、重复收款与恢复

P0：异步通知或主动查单先验证签名及渠道身份，再核对商户、环境、交易号、订单、金额、币种和支持的支付状态。
业务前缀只用于定位订单；浏览器返回页只查询服务器结果，不能触发可信付款标记。
可信实收须先可靠保存；后续订单或交付处理失败不能回滚或抹掉“已收到钱”。
匹配成功只绑定一笔有效商品款。相同交易重复通知不新增实收、不再次发货，乱序失败通知不能覆盖已经确认的付款。
第二笔真实付款保存为额外收款，进入差错队列并逐笔退款；用户只获得一件商品，退款额外款不改变合法交付。
金额、币种或归属异常的可信收款进入人工核实；不自动按较小金额交付、不自动补差，也不随意关联其他用户订单。
退款、拒付等后续事实不能删除原实收；发现资金风险时由有权限管理员登记并明确是否暂停交付与揭示。
已付款但处理失败的订单由持久任务恢复，通知独立重试；任务重复或进程重启不得产生第二份交付。
每一笔未匹配实收、未履约有效款、结果未知退款都必须能从后台队列定位到责任、最近进展和下一步。

付款差错以渠道、商户、环境及渠道交易号确定的收款身份独立检索，不以已有订单为前提。明细保存原支付引用、候选原订单、实际与预期身份/金额/币种/环境差异、可信证据、责任人、操作时间线和待办。
恢复归属仅限可信证据证明的原支付尝试与原订单映射；恢复后重新执行全部验签/身份/金额/币种/环境与付款状态校验，再按最新库存、退款和风险状态决定履约。不能修改实收事实、跨用户改绑或由管理员把短款、异币种、错误环境直接标成成功。
无法满足原映射恢复与全部校验条件时，按原收款建立差错退款责任，不发替代商品。归属或渠道退款依据仍不明时继续核实并保持责任人，不以“已处理”关闭异常；核实与退款结案均保存证据及对客可见结果。

首发单渠道必须同时保护原充值与商城两条业务：充值按既有规则仅一次额度入账及适用返佣，商城只核销独立订单与履约，不触发充值权益。双方回调只能处理其持久化业务归属对应的支付尝试；向另一业务入口投递或使用错误交易归属不能串单、互认或重复结算。实施验收包含同渠道两类正常交易、各自重复通知及交叉投递，范围限定该渠道与直接受影响的支付模块。

## 7. 自动与人工交付

### 7.1 自动交付

P0：只有有效商品款、唯一库存归属、可用凭据和无交付暂停同时成立，才能提交首次交付。
交付提交前再次检查退款/暂停状态，不能使用任务开始时的旧状态绕过后续退款批准。
库存变为售出与交付记录建立需要原子完成；成功后订单本人读取固定内容，任务重放不重新选库存。
若凭据解密失败、缺字段或库存被隔离，停止揭示并进入交付异常；不能返回半截秘密或改用未经验证的库存。
成功交付不依赖邮件或站内提示到达；通知只包含已可领取的提示和订单链接，不携带账号密码、卡密或恢复资料。

### 7.2 人工交付

P1：商品上架前定义所需资料、约定交付内容和实际可执行的预计时限；首版仅有限字段，不提供自由表单搭建器。
人工交付时限从可信付款完成且约定资料齐全两项均满足时开始，按订单快照中的自然/工作时间口径、服务时段和时区计算绝对截止时间。资料未齐只显示起算条件，不生成假的截止时间；开始后请求补充不得擅自重置承诺。
支付后进入待交付队列。管理员接单、请求补充信息、提交交付、登记异常均留下操作人和时间。
缺少资料时明确列出缺项及原因，保留原时间线；不能静默重置时限或假装已经交付。
若等待买家资料会暂停预计时限，该规则须事先展示并写入订单快照，未约定时不能单方追溯变更。
人工提交内容也须加密保存，并核对订单归属及最新退款状态；禁止直接把秘密发在普通备注或通知正文。
管理员重复提交同一次操作返回已有交付；不同管理员并发提交只能有一次首次交付成功，冲突者看到最新状态。
超过商品配置的处理阈值进入需关注队列；显示“处理超出预计时间”，不编造新的完成倒计时。

## 8. 领取、补发与质保

P0：领取接口逐次校验登录用户、主站/租户归属、订单有效付款、交付记录归属和是否允许揭示。
每个交付版本的凭据查看期限依订单快照规则计算；该版本到期后停止返回秘密并显示“查看期限已结束”，但保留订单、售后和资金进度。展示截止时间不等于数据库立即删除；实际删除策略须满足未结交易责任及已确定的资料保留规则。
订单列表及普通详情默认只返回交付状态和脱敏描述；完整内容仅经专门领取动作返回，响应禁止缓存。
凭据不进入 URL、日志、浏览器持久存储、分析工具或后台任务内容；通知、审计只保存必要标识与动作。
重复查看返回当前合法交付版本，不消耗库存；复制字段与整份查看遵守相同权限和暂停规则。
版本查看期限的边界由服务端判定；直接调用领取或复制所用接口也必须拒绝到期秘密。刷新页面、发起或关闭普通售后不能重置期限或解除到期限制；历史交付和未结处理继续可见，新补发版本仅按下述规则产生独立窗口。
管理员查看、导出或更换凭据需要明确权限和现有强认证保护，审计记录操作对象、操作者、原因与结果，不记录秘密正文。
首版管理仅平台管理员开放，不新建复杂角色系统；普通用户、租户管理员、API Key/PAT 不默认获得管理或领取权限。
已揭示、售出、退款或被替换的凭据默认隔离，不自动成为可售库存；库存导入错误报告也不回显整条秘密。

P1：质保以商品公开规则及订单快照为准；推荐以完成约定交付为起点，实际起算事件和期限必须在上架前确定。
用户未点击查看不会无限延后质保；点击查看也不意味着商品有效、验收通过或售后权利终止。
售后收集问题现象、脱敏截图或必要标识；不要求买家在普通申请文本粘贴密码、卡密或恢复码。
补发必须关联售后申请，先锁定订单最新状态，再分配新的库存或保存新的人工内容；不得与已批准退款并行。
旧内容保留历史但可撤销揭示，新内容成为可领取版本；“撤销揭示”不表示已泄露秘密已被回收。
本次建议首版规则：补发版本沿用原订单快照的凭据可查看时长，自该版本交付完成起算新的截止时间，并保存到该版本；真实时长仍由运营确定并售前明确。原版本已经到期不妨碍新版本按该窗口领取，但旧凭据不恢复，退款/风险暂停等条件仍须通过。重置领取窗口不延长商品使用权益或质保，不能据此改变原售后约定。
补发不收第二次商品款。质保是否延长或重新起算按原条款执行；没有约定时不得默默缩短原有保障。

## 9. 退款审批、执行与证据

### 9.1 普通商品款退款

P0：退款申请不等于退款批准；有权限管理员核对付款、交付、问题和条款后给出批准或未批准结论及理由。
批准全额退款时同一事务锁定有效收款与订单、记录退款责任并暂停新交付及秘密揭示；并发交付只能按先后事实得到一个结果。
若交付先完成，审批记录必须明确已交付；仍可按条款退款，但不能自动回库或声称账号已收回。
批准后管理员在支付商后台按原收款原路退款；不转入 API 额度、不用站内余额替代、不要求买家提供无关收款账户。
执行前登记唯一的本地退款记录和原收款引用。再次打开流程必须继续该记录，不能重新发起无关联退款。
首版不支持部分退款；退款金额必须等于所选收款尚未退款的全额，币种一致，累计确认退款不得超过该笔实收。
已批准但未执行的退款如需撤销，须由有权限管理员核实尚无外部退款且填写理由；结果未知时禁止撤销或恢复交付。

### 9.2 人工结果核实

| 记录阶段 | 必须具备的信息 | 对客展示 |
| --- | --- | --- |
| 已批准待执行 | 原收款、订单、全额金额币种、原因、审批人和时间 | “退款已批准，等待处理” |
| 已操作待核实 | 原退款记录、操作人和时间、渠道交易/退款引用或待补证原因 | “退款处理中，结果待核实” |
| 确认成功 | 能核实商户、原交易、退款身份、金额币种、成功结果的渠道证据及核实人/时间 | “支付渠道已确认退款”；不另承诺银行入账时间 |
| 确认失败 | 渠道失败证据、失败原因、后续处理责任 | “退款失败，正在跟进” |
| 结果未知 | 操作超时、证据不全或结果矛盾的原因与待办 | “退款结果待核实”；继续查同一退款，不盲目重退 |

买家截图或管理员勾选不能单独证明退款成功；渠道截图也需可核实原交易、金额与结果，普通订单页面仅展示脱敏摘要。
敏感凭证限制访问，保存证据引用与必要摘要；冲突证据追加记录，不覆盖已接受的资金事实。
渠道已确认失败必须与结果未知分开记录和展示；“失败”要求可信渠道结论，不以请求超时或页面错误推定。失败不终止退款责任，不自动解除原订单的履约/查看限制。
失败后继续同一退款责任，仅在核实旧尝试不存在成功或在途结果、没有拒付冲突且当前仍有可退金额时允许重试。每次尝试保存关联原退款责任的本地与渠道引用、核实证据、金额币种、操作者及时间；未知结果继续查原尝试，不盲目重退。

### 9.3 重复付款与其他差错

每笔额外实收建立独立差错退款记录；一笔退款不能同时抵扣两个收款，也不能跨订单或用户拼金额。
额外收款全部退完后关闭差错提示，合法商品款与交付保持原事实；额外款尚未退款时不得显示“该订单所有款项已结清”。
有效商品款已退款而额外收款未解决时，主状态为已退款，同时明确“仍有额外付款待处理”。
无法匹配、金额异常或币种异常的实收先由管理员核实归属，再按原交易处理；首版不自动收差价或发替代商品。

### 9.4 拒付、外部退款与重复退赔防护

P0：渠道后台退款、拒付及其争议进展是关联原收款的独立后续资金事实，记录渠道身份/引用、金额币种、结果、证据、核实人和时间；不得删除原实收或伪装成原付款从未发生。
每次执行或重试普通/差错退款前，人工核实该原收款的已退、在途和争议金额，并以渠道引用识别同一笔调整，避免把本地退款与相同外部退款重复计入。已确认返还或扣回的金额不得再次退款，在途金额不得重复发起。
争议未定、拒付冲突或证据矛盾时停止新增退款，按独立风险暂停规则停止受影响订单的新交付、补发与秘密查看，继续保留处理责任及买家可见进度。
证据明确后先更新真实资金记录，再核实剩余可退责任或履约资格；不得仅撤销页面暂停就恢复。有效商品款已确认全额外部退款时按原款退款完成限制领取；额外重复款的外部退款不自动影响合法商品交付。拒付单独展示核实结果，不冒充商家退款成功。部分外部调整不代表开通商品款部分退款功能，需人工核实剩余责任，禁止自动补退或重复退赔。
首版使用人工核实与记录即可，不增加自动拒付处理或新的资金系统；操作入口位于付款差错明细及关联退款记录。

## 10. 停售、功能关闭与存量责任

P0：`暂停新订单`只关闭新的下单和新支付创建；已创建支付的回调、查单、实收恢复、交付、领取、售后与退款核实继续运行。
一般商品下架不撤销已付款订单的约定；存量可正常交付。发现凭据或授权风险时使用明确的“暂停交付/揭示”措施，并进入异常处理。
关闭商城入口不能删除订单入口或让买家失去售后与退款进度；历史订单保持受权限保护的可访问方式。
若系统回退无法处理商城任务，不得继续接入新商城交易；必须先保证能够处理存量的服务与责任承接，不能仅关闭前端按钮。
技术实现复用现有持久任务、审计、加密设计与支付适配基础；商城核销独立，不调用充值额度或返佣核销器。
发布与 schema 变更遵守既有 NewAPI 手册；本业务文档不授权生产迁移、商户操作或真实交易。

### 10.1 账户禁用、删除与存量责任

P0：有付款未知、未完成交付、活动售后、未决资金争议或未结退款责任的账户，软删除与硬删除均须拒绝。删除校验及执行与新建订单通过同一用户状态和一致事务边界保护，避免先查无责任、随后并发建单却仍删除成功。
账户禁用不绕过认证授权领取；由有权限管理员承接已有交付、售后及资金处理，并保留用户关联、审计和必要联系依据。不得因禁用或删除失败而关闭回调、核实或退款责任。
仅在无未结责任时，依确定的保留政策去标识化个人资料；交易、收款、交付、售后和审计引用不得随账户级联删除，留存标识不再允许新登录或新交易。
实施接点：`model/tenant_consumption.go` 的 `checkTenantUserDeletionTx` 已为主站调用商城未结责任检查；`model/user.go` 的软删、硬删进入与建单一致的事务边界。旧 schema 未安装时保持原行为，部分商城表或回执异常时拒绝删除；覆盖和剩余数据库实测缺口见实施状态。

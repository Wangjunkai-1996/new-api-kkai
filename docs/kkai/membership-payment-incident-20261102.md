## 公网请求复现

从 sys1 和 Mac 使用固定虚构订单、虚构商户及无效签名探测，均不会形成有效收款。

| 请求 | 结果 |
| --- | --- |
| `Python-urllib/3.12`，GET 或 POST，空请求或完整表单 | Cloudflare HTTP 403，响应 `error code: 1010` |
| 同一无效表单，`Mozilla/5.0` | HTTP 200，应用返回 `fail` |
| 同一无效表单，`curl/8.10.1`、`Go-http-client/1.1`、`Zpay-Notify/1.0`、空 UA | HTTP 200，应用返回 `fail` |
| 保留 Host/SNI，通过 curl `--resolve` 分别指定当前两个 IP 与旧 SaaS IP | 普通 Go UA 均为 200 `fail`；Python UA 在当前与旧 SaaS IP 均为 403/1010 |

因此已证明入口存在按客户端特征拦截程序请求的行为，但不能声称所有程序回调都失败，
也不能把 Python 探测的 403 直接当作 Zpay 的实际失败结果。当前和旧 IP 的一致表现同样
不足以支持“把 CNAME 改回去就必然修复”。`api-origin.kkrich.ltd` 和备用
`api.kkai.win` 的 Python UA 探测也返回 1010，不能直接拿它们作为已验证的修复入口。

Cloudflare 官方将 1010 解释为基于浏览器签名的拒绝，常见关联 Browser Integrity Check：
https://developers.cloudflare.com/support/troubleshooting/http-status-codes/cloudflare-1xxx-errors/error-1010/

代表性复现 Ray ID：`a5411507abff52d6-IAD`（403），`a5411507df66d6a0-IAD`（200）。
这些是诊断探测的 Ray ID，不是真实付款通知的 Ray ID。

## 下一步修复与验收范围

后续用户已确认 Zpay 无法提供更多错误信息。以下按自主恢复推进，详细实施顺序见
[会员支付可靠性优化方案](membership-payment-reliability-plan-20261102.md)，不再等待上游日志。

1. 保留通知具体失败环节尚未证明的结论。当前商户查单协议不返回通知尝试详情，
   不能以缺少上游诊断信息阻塞本站查单补偿、付款证据保存和可观测性改进。
2. 对确认的失败环节修复；若建立支付专用入口，只调整支付通知所需路径，保留 HTTPS、
   签名和商户/金额校验，不全站关闭安全防护。必须用真实通知路径验收，浏览器可打开不算通过。
3. 为会员增加有界的认证查单补偿，复用现有支付事实和唯一回执逻辑，保留原订单价格及升级
   账户版本；处理重复通知、迟到款、已结束订单、并发消费和人工补发，不重复加额度。
   不能直接把钱包结算入口用于会员。
4. 增加脱敏的失败原因日志。用一笔明确授权的真实支付或服务商重发通知验证：商户已支付 →
   公网通知到达 → 回执落库 → 会员生效；重复通知额度不变；通知缺失时查单可恢复。

# 钱包充值订单验收与合并质量规范

**2026-10-24 交互修订：** 主动确认结束成功后，在同一次用户操作内串行精确 acknowledge，成功直接回充值页，无需再点返回；失败保留 ended 与返回重试。自动超时仍保留超时提示和“返回充值”按钮。自动确认只作用于原身份、flow/revision 与原订单均仍一致的 ended 结果，实际收款、身份变化、另一当前流程和迟到旧响应不能自动清理。以下条款按此区分主动结束与自动超时。

**2026-10-23 生效修订：** 本文正文及 A01—A32 已按获用户确认的 [本站超时与废单规范](./wallet-payment-local-timeout-spec.md)统一：本站 30 分钟期限、本地结束／超时结果及显式“返回充值”、废单无续付／人工补单入口，晚到款仍按原单处理。本地操作结束与渠道可靠关闭分别验收。

## 1. 验收基线与证据口径

产品行为以 [本站超时与废单规范](./wallet-payment-local-timeout-spec.md)及已对齐的 [生命周期 PRD](./wallet-payment-lifecycle-prd.md) 正文、A01—A32 为准，视觉与交互以 [UI 规格](./wallet-payment-ui-spec.md) 的最新正文为准；其余资金、并发与兼容约束继承 [技术方案](./wallet-payment-lifecycle-plan.md)。旧版验证记录只证明对应旧原型，不覆盖最新要求。开发分册确定字段与接口，本规范验收可观察行为，不要求额外状态平台或新的测试框架。

本站到期流程为：创建后 30 分钟（已知渠道截止更早则取更早值）→ 服务端返回 timed_out／closed → 原位保留“本次充值已超时”和直接可见的“返回充值” → 用户点击、服务端精确确认对应流程 → 恢复表单与新报价。主动 end 成功在同次用户操作内串行精确 acknowledge，成功立即回充值，无需第二次点击；确认失败保留 ended、错误与返回重试。超时不自动返回，两者均不等待渠道可靠关单。渠道 cancelled／expired 另凭可靠证据验收；本地结束不代表原链接失效或退款，已确认收款／credit_review 优先于账龄和本地标记。

矩阵中的验证层级：

| 标记 | 必需证据 | 不能代替什么 |
| --- | --- | --- |
| M | 模型／服务定向测试，显式准备数据库与账务状态 | 单进程互斥不能代替数据库并发证据 |
| H | 路由／控制器契约测试，覆盖鉴权、租户、状态与错误响应 | 绕过鉴权直接调用函数不能证明接口安全 |
| F | 前端组件／Hook 定向测试，使用可控异步响应、时钟与接口桩 | 本地状态模拟不能证明服务端门禁或真实渠道 |
| B | 实际应用浏览器旅程、截图、焦点和新标签页检查 | 本地外部支付示意面板不能证明跨域行为 |
| C | 受影响渠道的官方协议与沙箱或受控联调证据 | SDK 方法、注释、模拟 HTTP 成功不能证明商户已获能力 |

每项执行记录写明目标 commit、测试名称／命令、环境和数据库版本、结果及证据位置。结果使用通过、失败、未执行、因渠道能力不适用；跳过和未执行不能记为通过。渠道能力不适用时，同步验收能力受限提示和功能关闭，不能以此宣称完整取消能力已交付。

## 3. 不可省略的资金与隔离断言

### 3.1 并发、凭据和事务

| 场景 | 确定性准备方式 | 最终可观察断言 |
| --- | --- | --- |
| 跨实例重复成功、成功与取消／过期／失败竞争 | 两个独立数据库连接／执行方，用显式屏障控制读写次序；同时覆盖关闭先到、成功先到 | 只发一次原单额度；成功不会被后续关闭／failed 回写覆盖；重复请求返回稳定结果。不能只测试 controller 的进程锁 |
| 同一交易重放、跨单套用 | 固定渠道＋商户账号／环境＋交易 ID，同单重复以及另一单使用同凭据 | 唯一收款事实不被重复占用；跨单不发额度；可解释异常保留。不同商户同名交易 ID 不应互相误认 |
| 同单第二笔真实款 | 两个不同可信交易 ID 对应同一原单 | 两笔事实均可追踪，原订单额度只发一次；第二笔进入有责任异常，不自动退款 |
| 收据已保存但账务被拒绝 | 准备旧信用纪元、额度超限、归属／计价异常 | 收据及原因持久存在，未处理队列可恢复；不会无凭据记 success；额度没有负数、溢出或部分入账 |
| 数据库写入、outbox 或资金批次故障 | 注入一次明确失败，再按原凭据重试 | 入账、订单成功、处理结果及既有资金／返佣事务保持一致；不能部分成功。无法保存收据时通知不确认成功，渠道可重试 |
| 已存未处理收据重启 | 保存可信收据后模拟进程退出，再由后台接管 | 继续处理一次，不能因通知已确认而永久丢款；可处理异常不在重试中消失 |
| 本地结束后新单与旧单晚款 | A 本地结束／超时并精确返回，建立当前 B，再提交 A 的可信收据及重复通知 | 只给 A 原单入账一次，B 的流程／订单不变；A 第二笔不同交易保留异常，不自动退款；普通负查询不能覆盖已有收款／到账核实责任 |
| 发票证据联动 | 有发票 schema、无可选发票 schema、部分 schema、已有异常 hold 四种明确 fixture | 钱包证据不依赖可选发票安装；安装后仍遵守原证据唯一性、关联及 hold；不绕过已有异常，不用钱包成功掩盖发票异常 |

新增或重写后端测试使用 testify 的 require 做准备与致命断言，assert 做值断言；时间和任务调度使用明确输入或可控时钟。禁止随机循环、等待真实分钟数、用 sleep 猜测竞争结果、只检查日志或只判断“不报错”。新增并发路径必须断言订单、用户额度、收据、资金批次和受影响 outbox 的准确结果，不把现有测试名称当作覆盖证明。

### 3.2 金额、额度与身份

- 应付最小货币单位、币种、额度和合法优惠规则来自原订单冻结快照；实收来自可信收据。改当前汇率、产品价、商户配置后恢复旧单，显示和入账不得被重算。前端按 DTO 的整数字符串及币种 exponent 保持精度；大于 JS 安全整数的金额／额度和不同比例币种必须准确显示，不先转 number 再格式化。
- 报价和订单按后端 pricing_mode 同口径验证：fixed 时 expected_payment 与 payable_payment 相同，显示应付；channel_adjusted 在合法优惠／税费尚未确认时显示冻结基础“订单金额”及可翻译说明，payable_payment 为 null，不把基础金额冒充最终应付。认证确认后可展示最终应付但不改原基础快照；received_payment 仍只表示可信实收。unknown 仅缺证据旧单，不允许新建。合法变化与任意金额篡改分别验收，不能为简化测试取消现有优惠能力。
- 对应付与实收不符、币种不符、大小写规范化、零／负数、超范围值、小数精度、错误商户／测试生产环境、错误 session、跨用户／租户和合法优惠分别准备明确样本。异常不入账，可信资金事实保留；合法原优惠不被“必须等于标价”误杀。
- 钱包充值现有额度使用其正 int64 与余额上限契约，沿用既有配额换算与溢出检查；不能为本功能把充值余额误限到单次模型扣费的 int32 范围。测试最大合法边界和超一位的拒绝，不能出现负额度或负余额。
- 所有本人接口绑定服务端用户与租户；对详情、恢复、结束、取消、核实、当前流程确认逐一做 IDOR 测试。管理员本人钱包仍限本人，管理视图另验管理权限与全平台范围；调用体中的 tenant_id／user_id 不得改变所有权。
- 原链接／签名表单只经本人授权恢复按需返回；列表、普通日志、错误提示、客服文案、本地偏好及截图不能泄露支付 token、密钥或完整敏感载荷。原商户配置失效时保留核实事实，不悄悄切新商户重建原单。

### 3.3 当前流程、历史与恢复

服务端为“本人当前充值流程”保留权威依据。所有钱包在线充值创建入口共同执行相同门禁，包含 classic／旧客户端原接口；只隐藏按钮不算通过。本地 ended／timed_out 或可靠资金／渠道结果“可返回”与“已返回、可新建”分开：确认绑定当前身份、流程版本及订单；重复确认幂等，旧确认不能解除新流程。服务端计算本站有效截止，不能把渠道无关单能力当作拒绝本地结束或到期返回的理由。

接口与枚举只引用 [后端开发规格](./wallet-payment-backend-dev-spec.md) 第 4 节；浏览器消费规则引用 [前端开发规格](./wallet-payment-frontend-dev-spec.md)，交付顺序见 [开发总纲](./wallet-payment-development.md)。以下为契约测试要求，不另定义 API：

- 首次 POST current/restore 是显式、幂等的原子恢复，后续 GET current 只读；已有流程不能被历史 trade_no 替换。创建中 display_status=creating，归 processing，不是 pending；unavailable 不伪造 review 责任。
- 新 orders 及 end 返回 `{wallet:最新WalletState,order:操作对应OrderDTO}`，restore、current、acknowledge 返回 WalletState；detail／resume 和 cancel／reconcile／admin-reconcile 按后端各自包装消费。本人有效历史单 end 不改变当前另一单；旧单已确认返回后重试原创建 key，order 仍指原单、wallet 反映实际新当前流程，不能重绑或重开废单。断言 wrapper、checkout=null 和失败响应，不能把历史 order 当 current 或把管理员目标 wallet 塞入本人钱包。
- 新创建不含 checkout，只有授权 resume 按能力返回短暂凭据；创建返回 201／200／202 分别覆盖新单就绪、原操作重放和结果待确认。202 不是取消完成或付款成功。
- flow revision、order version、金额与额度保持字符串精度；确认、旧响应隔离和 query cache 身份范围均覆盖大于 JS 安全整数的版本值，不能以时间戳、Number 或字典序判断更新。
- 生命周期启用后，5 个旧渠道 pay 入口缺 Idempotency-Key 返回 CLIENT_UPGRADE_REQUIRED 且不请求渠道；有 key 时仍走同一门禁。新前端遇新 API 404／不可识别不能退回无门禁的旧支付路径。兑换码接口不冒充支付创建。
- 本人／管理员权限、access-token route scope、tenant 白名单、Origin／现有 CSRF 链及限流按各接口逐项验证；管理员核实目标订单不改变其本人当前流程，不能通过参数扩大管理范围。
- 服务端截止为创建后 30 分钟或更早渠道截止，`deadline_source` 区分 `local_policy`／`provider`。结束原因／时间独立于渠道关闭证据；到期无需先回填历史字段。废单 resume／cancel／end／人工 reconcile、管理员核实及旧 complete 均拒绝，旧客户端列表也不得凭原始 pending 显示可补单；缺创建时间且无资金／渠道终态时 unavailable，只读／帮助，不伪造超时。
- 合法 idle 可以 can_create=false，例如充值关闭、渠道限制或额度容量不足；应显示安全、可翻译的 create_block_reason_code 及适当重试，保持空闲原模块各自配置权限，不能误判恢复失败、伪造当前单或连带封锁兑换／订阅。quote 和 create 均重新检查购买规则，伪造调用不能绕过。配置重新允许后根据最新服务端状态恢复购买，不使用本地布尔解锁。

订单阶段隐藏现有钱包其余充值、订阅／Creem 购买、兑换等入口，空闲阶段恢复现有功能与排序，不删除模块。这里是已确认的互斥布局要求：订阅／会员生命周期、兑换码账务不纳入本期重构，不对兑换接口额外增加无关的全钱包资金锁。共享支付回调必须继续正确分流订阅／会员与钱包订单，不得因引入钱包状态提前确认其他业务或重复入账。

历史兼容至少包含：期限内原会话、缺快照／商户身份、已知时间且超过本站期限（含 30 天以前）、缺创建时间、信用纪元限制、独立资金待核实及与当前单并存。老 pending 依据本站期限只读投影 timed_out，不批量伪造渠道关闭，不按账龄废弃已收款事实；禁止当前价格补造原报价、历史重绑当前或仅前端归档解锁。旧单批处理先只读报告、写入另获授权；人工批次筛选及逐笔执行均跳过废单，不删除收据，不停止可信晚款处理。

本人六筛选显式使用后端 `scope=wallet`：最近 30 天全部记录与全部账龄需保留的原始未完成／未定性记录取并集，含按本站期限投影为 closed 的旧 pending，不要求先知道订单号才能发现。老 pending 不再混入 pending／processing 或其他未完成数；已收款待核实仍归 review，精确 trade_no 全龄可查。列表、total 和 counts 使用同一集合及归类，界面说明真实范围，不凭当前页条数计总数。旧 self 默认 recent、旧 admin 全龄 `legacy_admin` 的范围兼容保留；旧响应对本地废单投影不可操作状态，不能继续显示补单。所有入口都不把旧未知单解释成可付款。

关键失败恢复清单：远端创建成功本地保存失败、保存成功响应丢失、恢复时并发取消、发起关单后渠道超时、确认关闭前收到成功、返回确认成功响应丢失、旧返回请求晚于新单、商户凭据轮换、任务租约过期。每条分别断言没有新会话、没有错误解锁、没有重复额度，并能继续查询可信事实。

### 4.1 历史批次专用回归

下列覆盖 PRD 第 7.3 节和 A12／A16／A24／A30 的处理责任，不扩展产品编号或通用任务框架。API 路径、RunDTO 和状态只引用后端规格第 8 节。

| 操作／故障 | 最小确定输入与验收断言 |
| --- | --- |
| report | 明确 provider、原账号／环境、tenant 和创建区间，包含可核实／缺证据／信用纪元旧单。业务订单、额度、收据和远端支付不被修改或主动查单；可保存报告元数据。报告冻结 scope_digest 与 max_order_id，空 scope、越界批量／速率拒绝；counts／capability_gaps 与实际 fixture 一致 |
| start 与权限 | RootAuth 交互 session 持真实授权引用和原因，以同幂等键重试只启动同一 run；过期报告、digest 不符、范围外授权拒绝。普通用户、租户主、普通管理员、scoped token、缺 origin 不能调用批次接口；单笔核实权限不能扩大为批处理权限 |
| 冻结与 status | run 保存报告、scope、max_order_id、cursor、control_version、owner 和结果；报告后新单超边界不扫入，变更范围重新报告及授权。废单在选取和每笔远端查询前再次排除，报告后才到期不穿透。列表／状态不泄露凭据，分段任务成功不等于整批完成 |
| pause 与在途请求 | 显式屏障停在一次远端请求中再 pause。desired_state 和 control_version 已持久化，旧 worker 回来可保存可信付款事实，但不能启动下一查询或推进旧 run 游标；在途释放后显示 paused。旧控制版本返回 RUN_CHANGED，重复同意图幂等，不能重写新控制决策 |
| resume 与重启 | 使用原 digest／授权和当前 control version，从已持久游标继续。进程在批次提交前／后退出，未确认段可重查但入账／收据／结果不重复；checkpoint 通过控制版本 CAS，过时执行者不能推进。暂停／恢复不删除订单、收据或此前结果 |
| 独立任务与计数 | 暂停历史 run 时另准备一笔新单到期和一笔 pending receipt，二者仍可正常核实／处理；暂停不是停止 webhook、正常新单任务或收据入账。reviewed 总量及 credited／closed／review_required／retry_failed 等互斥结果按 RunDTO 口径可解释，重复分段不重复计数 |

authorization_ref 是可追踪引用，不是字符串自身证明批准；若授权系统未接入，验收记录须保留已获授权操作者按运行册核对范围的证据，不由接口测试或 UI 自动生成“已授权”。未执行真实历史写入时只确认上述隔离测试，不能声称历史订单已经收敛。

### 5.3 实际浏览器与渠道证据

浏览器至少在实际应用里覆盖：真实外部新标签打开与手动关闭、拦截恢复、noopener、不回跳、focus／visibility 合并、刷新／换设备恢复、手动返回按钮、旧查询迟到、320px 与手机／桌面、浅深色、Safari、键盘和关键读屏路径。按受影响路径检查，不能用本地示意面板截图代替。

每个拟启用渠道须附下列脱敏证据：

1. 实际服务商、商户账号／环境引用、官方接口版本和权限；查询、关单、到期、幂等、通知重试及异步付款的语义。
2. 一单一会话创建与恢复、真实 session／订单关联、渠道有效期、创建不确定后的查回方式；原配置失效时的限制。
3. 已支付、未付可关闭、可靠关闭、付款处理中、临时查无此单／超时的真实响应映射；可靠关单后原会话不可继续付款的证据。
4. 取消／到期与支付竞争、可信迟到款、重复通知、合法优惠及金额币种异常；沙箱无法制造的场景由协议和确定性模拟补充，并明确真实联调缺口。
5. 回调验签／查询认证、通知确认与收据持久性、密钥及 token 脱敏；保存证据位置，不在文档粘贴可用支付链接或商户密钥。

易支付现有 SDK 缺少方法不证明服务商无能力；现有发票补证服务中的认证查单也不证明 pending 订单可查、可关闭或已具备钱包自动过期。Stripe 异步付款不能按 checkout 完成或本地截止认定未付款；Waffo 中间态不能统一 failed；Pancake BuyerSession 取消凭据不能用 checkout token 代替；Creem 非 pending 不能提前确认并丢掉迟到款。

# KK 商城产品需求文档（PRD）

- 文档版本：v1.1；更新日期：2026-10-28；状态：首版产品基线已有本地实现；正式验收及上线未完成，见[实施状态](./kk-shop-implementation-status.md)。
- 适用范围：现有 KKAI 网站内的单商家自营虚拟商品商城首版。
- 方案依据：[需求评审与推荐实现方案](./kk-shop-implementation-plan.md)。
- 交易规则依据：[业务规则与交易状态](./kk-shop-business-rules.md)；本文规定用户可观察行为，交易状态、并发及资金处理细节以该文为准。
- 本文不代表支付渠道已经启用、商品已经获得销售授权或任何生产能力已经安装。

## 1. 产品定位与目标

KK 商城向现有 KKAI 用户销售账号、卡密等可数字化交付的商品，复用主站登录与已核实可用的支付渠道，在站内完成购买、领取、重复查看及售后。

首版成功的定义是：用户看得懂买什么、付多少钱、何时拿到、出现问题如何处理；运营人员能追踪每笔真实收款和每份交付，异常不会因页面关闭而丢失。

优先级依次为交易正确、交付可用、售后可追踪、操作清晰。成交转化率和营销效率是后续优化目标，当前不设置缺乏基线的增长指标。

## 2. 已确认、推荐与尚未确定

| 类型 | 事项 | 当前结论 |
| --- | --- | --- |
| 已确认 | 经营模式 | 单商家自营，平台管理员运营 |
| 已确认 | 商品类型 | 账号、卡密等虚拟商品；不涉及实物和物流 |
| 已确认 | 交付方式 | 自动交付与人工交付均属于首版 |
| 已确认 | 入口与账号 | 在现有 KKAI 增加商城入口，复用现有登录 |
| 已确认 | 支付方向 | 使用本项目已有支付体系的可复用渠道能力 |
| 推荐首版范围 | 交易单元 | 一个商品对应一种规格，每单一件，直接购买 |
| 推荐首版范围 | 购买资格 | 商品公开浏览，登录后购买；只向主站开放 |
| 推荐首版范围 | 支付与币种 | 先接入一个已核实渠道、一种币种；不使用 API 额度支付 |
| 推荐首版范围 | 退款 | 原商品款仅全额退款；多收款独立处理；人工原路退款登记与核实 |
| 尚未确定 | 上线业务参数 | 真实商品、价格、币种、渠道、交付 SLA、质保及退款规则 |

本 PRD 的“推荐”是可实施的首版基线，不等同于用户已确认的经营条款。推荐范围变更需要更新需求及验收，不要求为继续文档和设计工作反复确认。

**演示数据规则：**所有设计稿中的商品、价格、数量、付款记录、交付时限和质保文案都必须明确标注“演示”。使用通用虚构商品，不借用未经授权的第三方账号品牌，不展示虚假销量、评分或保证秒发。演示商品不得自动导入生产，不得生成真实支付入口，不得作为后台预置经营条款。

## 3. 角色与权限

| 角色 | 可执行动作 | 边界 |
| --- | --- | --- |
| 访客 | 浏览、搜索、查看商品详情 | 购买时登录；无法查看任何订单或交付内容 |
| 已登录买家 | 创建自己的订单、付款、查看交付、申请售后、补充所需信息 | 仅本人且属于当前主站的订单；不因知道订单号获得访问权 |
| 平台管理员 | 商品、库存、订单、人工交付、售后、退款登记和异常处理 | 使用现有后台管理员权限；敏感动作单独确认并记录操作者 |
| 非管理员、租户及分销站角色 | 无商城管理权限 | 首版不因现有角色名称自动获得运营、凭据查看或退款权限 |

管理员普通订单浏览不自动展示完整账号密码。查看秘密、补发、隔离库存、登记退款等动作应留下可追溯记录；不新增独立商城角色配置系统。

API Key/PAT 不作为首版商城购买或领取的身份凭据。运营不能把某个买家的已售库存直接改给另一个买家。

## 6. 买家端页面规格

### PAGE-01 商城首页与商品列表

- 展示名称、封面、简短规格、价格与币种、交付方式、是否有货；缺少封面使用统一占位图。
- 支持名称关键词、单层分类筛选及分页；默认按运营配置的展示顺序，不伪造销量和评价。
- 主动作是“查看商品”；售罄商品可显示“暂时缺货”，不提供付款按钮。
- 首版允许售罄商品保留在列表供用户查看，管理员可下架隐藏；分类管理采用简单名称和排序。
- 商品卡价格与详情一致；未上架商品不进入公开搜索、推荐或直接链接访问。

### PAGE-02 商品详情

- 必填展示：名称、规格、成交币种与单价、交付方式、交付内容说明、适用地区/平台、必要使用条件、交付时限、凭据可查看期限、质保与退款规则。
- 账号类补充：交付哪些资料、是否交付恢复资料、是否支持改绑、有效期及起算方式；卡密类补充：兑换方式、适用范围及有效期。
- 不展示真实库存凭据；详情说明可举示例，但示例凭据必须为明显无效的演示值。
- 自动商品显示“付款确认后自动交付”等已核实描述；不能承诺支付后固定秒数到账。
- 人工商品显示运营确认的交付时限和必要资料字段；超过接单容量时显示暂不可购买。
- 主动作为“立即购买”；访客先登录，返回原商品后重新校验价格和库存，不自动生成付款。
- 每个商品就是一种规格，详情不出现无实际能力的数量选择器或规格矩阵。

### PAGE-03 确认订单与支付

- 展示商品快照、数量 1、应付金额、币种、交付方式、必要买家资料及售后条款摘要和完整入口。
- 明确告知购买内容是虚拟商品及其交付规则；如需要条款确认，使用明确、未默认勾选的确认项。
- 商品价格或关键规则在下单前改变时，展示变化并要求重新确认；不得静默使用旧展示价收取新价格。
- 下单后使用订单快照；同一次提交重试返回同一订单，按钮防连点只作为体验辅助。
- 展示真实可用渠道；没有可用渠道时禁止开始付款并提供返回商品的操作。
- 支付入口可按渠道能力使用二维码、跳转或按钮；倒计时表述为“订单保留时间”，不冒充支付商关单保证。
- 返回页立即查询服务端状态；“已付款”按钮仅主动查询，不允许前端直接把订单置为付款成功。
- 付款核实中显示查询进度与返回订单入口；重复打开恢复原有效付款入口，结果未知时不盲目创建新交易。
- 未付款订单允许用户取消；取消与迟到收款的处理遵循业务规则，不保证已经打开的外部付款页一定失效。

### PAGE-04 我的订单

- 按时间倒序分页，支持订单号搜索及“全部、待付款、待交付、已交付、售后/退款”快捷筛选。
- 每条展示订单号、商品快照名称、数量、金额/币种、创建时间、当前进度和一个主要操作。
- 待付款显示“继续付款”，待交付显示“查看进度”，已交付显示“查看交付”，售后/退款显示“查看处理”。
- 不在列表展示账号、密码、卡密或完整买家补充资料；异常状态不与普通待付款混为一类。

### PAGE-05 订单详情与交付

- 固定展示订单号、商品快照、金额/币种、下单时间、付款确认时间、交付时间、售后规则与当前主要操作。
- 用时间线表达已发生事件；状态和事件名称沿用业务规则文档，不展示内部回执、队列、租约等术语。
- 自动交付完成后显示“查看交付内容”；用户主动查看后显示必要凭据字段、复制按钮和使用说明。
- 重复查看同一交付版本；补发在原订单下显示新的有效交付及该版本查看截止时间，保留可识别的历史处理记录。补发期限计算见 PAGE-11，不恢复旧凭据。
- 人工交付时限从可信付款完成且约定的必要资料齐全两项均满足时起算；采用自然小时还是工作时间、服务时段和时区须在商品及订单快照中明确。
- 资料不完整时显示缺少哪一项以及“补充信息”，说明资料齐全后的承诺时限；开始计时后显示最晚交付时间，尚未交付不能伪装为已发货。
- 管理员后续请求补充信息不能擅自重置已开始的承诺时限；任何暂停必须有商品约定依据，并记录原因与时间。
- 付款/交付异常展示事实、正在处理的方向及售后入口，不要求用户重新购买来解决已经收款的订单。
- 有效商品款退款已批准或因明确风险暂停领取时关闭新的秘密展示，说明原因；普通售后申请及额外重复款退款不自动剥夺查看权。
- 按订单快照规则显示当前交付版本的凭据可查看截止时间；该版本到期后提示“查看期限已结束”，停止秘密展示，保留订单事实、售后及资金处理入口，不自动关闭未结事项。
- 风险暂停显示面向买家的原因摘要和处理进度，不暴露内部证据；退款已确认失败与结果未知分开展示，失败仍需处理，不能据此恢复领取或声称退款成功。
- 退款完成不声称已撤回用户之前看过的信息；不把多付款差错退款误显示成原商品订单已全额退款。

### PAGE-06 售后申请与处理记录

- 申请字段：问题类型、问题描述、期望处理方式；以文字为首版必需输入，附件能力按现有安全上传能力选择。
- 问题类型使用固定选项：无法使用、内容不符、未收到交付、其他；期望处理可选排查、补发或退款，最终由规则和审核决定。
- 明确提示无需填写完整账号密码；提供使用错误现象、发生时间等必要信息。
- 每单同一时间仅有一个活动售后申请；重复提交定位到已有申请，关闭后可依规则再次申请。
- 显示申请时间、买家补充、公开处理说明、结果及关联补发/退款；管理员内部备注不对买家公开。
- 质保期外仍可提交问题，由后台依据订单快照判断，不自动承诺补发或退款。
- 首版不建设实时聊天；售后沟通采用订单内受限文字追加记录，不允许改写已经提交的历史内容。

## 7. 管理端功能规格

### PAGE-07 运营概览

- 默认显示待人工交付、交付异常、待处理售后、退款待核实、付款差错和低库存数量，点击进入对应列表。
- 展示订单量、已确认实收及退款概况时，明确时间范围和币种；订单应付金额不作为实际收款。
- 不提供混币种合计、虚构收入趋势或无法从事实记录复核的“净收益”。

### PAGE-08 商品管理与编辑

- 字段：名称、分类、封面、简述、规格说明、价格、币种、交付类型、商品类型、交付资料说明、适用限制、交付 SLA、凭据可查看时长及起算方式、质保及退款规则、排序、上架状态。
- 交付类型固定为自动或人工；商品类型首版固定为账号、卡密、其他虚拟交付，不能借类型新增物流功能。
- 自动商品选择相应交付字段模板；人工商品配置接单容量及最多三个必要的固定补充字段，不建设表单生成器。
- 固定补充字段仅允许接收账号/标识、联系邮箱、订单备注等必要项；不得收集支付密码、短信验证码或无关身份资料。
- 保存草稿允许缺少经营参数；上架必须完成真实价格、币种、交付说明、售后条款及可用付款能力校验。
- 人工商品还须配置有效交付时限和接单容量；自动商品无库存时可展示售罄，但不能创建新付款订单。
- 有有效订单或关联库存后，不允许直接切换交付类型；需要新建商品并下架旧商品。
- 编辑影响后续新订单，已下单规则保持快照；下架只停止新增购买，不中断既有交付、售后和退款。
- 有历史交易的商品保留历史记录，不提供物理删除；支持下架及后台归档筛选。

### PAGE-09 库存管理与导入

- 列表展示所属商品、脱敏标识、可售/预留/售出/隔离状态、关联订单和时间；不默认展示秘密。
- 导入先选商品和模板，再上传或粘贴；首版提供固定账号与卡密模板，不接受任意脚本或自由字段解析。
- 账号模板至少区分账号标识与密码，恢复资料按商品模板确定；卡密模板每条记录对应一份可售卡密。
- 确认导入前展示有效、重复、错误的行数及脱敏错误原因；存在错误时默认整批不入库，修正后重试。
- 导入确认执行时重新校验重复，避免预览后库存变化造成重复入库；必须给出最终成功或失败结果。
- 允许隔离可疑或失效库存并记录原因；不得直接编辑已售库存，补发必须进入售后交付流程。
- 售出/已展示库存不能由退款自动变回可售；重置后的账号如需再售，执行独立复核并保留原关系。
- 首版不提供批量明文导出；必要的管理员单条秘密查看有显式动作、权限检查和审计。

### PAGE-10 订单管理与人工交付

- 支持按订单号、买家 ID、商品、时间和状态查询；列表展示金额、付款/交付摘要、期限与异常标记。
- 详情包含不可变订单快照、收款摘要、交付记录、买家必要资料、售后、退款、公开说明和内部备注。
- 人工队列按超时优先、付款确认时间排序；管理员可标记处理中，但标记不改变付款或交付事实。
- 提交交付前核对订单、商品及加密保存的交付内容，展示确认摘要；成功后才显示“已交付”。
- 两位管理员同时操作时，后一位看到已处理提示及最新状态，不重复交付。
- 需要买家补充信息时明确列出缺少项，并向买家发送无秘密的状态提示；暂停计时必须符合订单约定，不可临时更改。
- 超过交付期限仍保留订单并突出逾期；运营给出预计处理时间或进入退款审核，不自动关闭已收款订单。
- 异常付款和交付必须有当前处理记录；管理员可以处理异常，不能手工伪造渠道付款成功。
- 订单详情提供“暂停交付与查看”和“复核恢复”：暂停是独立订单事实，必须有权限、内部理由、买家可见说明及操作审计；不以普通备注替代。恢复仅解除该暂停，仍校验有效付款、退款、争议、库存与当前版本查看期限，不恢复已过期或已退款内容。
- 付款差错可独立于订单，按渠道、商户、环境及渠道交易号检索；详情展示原支付引用、候选原订单、实际与预期身份/金额/币种/环境差异、可信证据、责任人、处理时间线和下一步。无法匹配订单也必须保留可处理入口。
- 差错恢复履约仅允许凭可信证据恢复原支付尝试与订单映射，再重跑全部付款及履约校验；不能跨用户改绑、修改实收事实或把短款、异币种、错误环境人工确认成功。不满足条件时沿原收款建立差错退款责任，证据或归属未定则继续核实，不虚假结案。

### PAGE-11 售后、补发与退款

- 售后队列可按待审核、待买家补充、处理中、已完成等状态筛选，查看商品快照中的原始约定。
- 动作包括请求必要补充、记录排查、批准补发、批准退款、拒绝申请并说明原因；不提供无理由关闭。
- 补发先确认有效库存或人工交付内容，再关联售后形成新交付；历史交付保持可追溯，是否重置质保期限依订单中的商品规则，不作统一隐含承诺。
- 本次建议首版规则：补发版本沿用原订单快照中的凭据可查看时长，从该版本交付完成起算新的查看截止时间；真实时长由运营确认并售前明确。只更新新版本的领取窗口，不延长商品使用权益或质保，不恢复旧凭据；退款或风险暂停等限制仍生效。
- 退款批准需要确认关联实收、退款类型、金额和理由；批准不等于支付商已经退款。
- 首版先批准退款并建立唯一退款记录，再由有权限的管理员在渠道后台执行原路退款，最后回到同一记录登记渠道退款单号/凭证及核实结果。
- 退款结果未知时保持处理中；不能仅点击“完成”就将真实资金标记为已退款。
- 有可信渠道证据确认退款失败时，显示“退款失败，待处理”，与“结果待核实”分开。保留同一退款责任；仅在确认旧尝试没有成功或在途退款、没有拒付冲突后允许重试，每次尝试记录关联渠道引用、证据及操作者，不重复建立退款案件。
- 拒付与渠道后台发生的外部退款单独登记为后续资金事实，关联原收款并保留原实收。每次执行或重试退款前核实已退、在途和争议金额；争议未定或证据冲突时停止新增退款，并按风险规则暂停受影响订单的新履约与秘密查看，不能重复退赔。首版采用人工核实与记录，不建设新的自动争议处理系统。
- 正常商品款首版全额退款；多收款按对应收款记录单独退款，不影响应保留的正常商品交付。
- 驳回售后提供面向买家的理由；内部风险判断、私密凭据和其他用户信息不得进入公开说明。

## 8. 通知与沟通

| 事件 | 买家侧 | 管理员侧 |
| --- | --- | --- |
| 付款已确认 | 订单进度更新；人工商品资料齐全时展示截止时间，否则提示补充 | 人工队列新增或自动交付状态更新 |
| 交付完成/补发完成 | 站内可见的可领取提示及订单链接 | 更新交付结果，保留记录 |
| 需要补充信息 | 明确所需项和订单链接 | 标记待补充，不隐藏逾期事实 |
| 售后/退款进度变化 | 可见处理说明和当前进度 | 更新队列与待核实项 |
| 晚到收款、多付款、交付异常 | 说明相关订单正在处理 | 独立异常队列和待处理计数 |
| 低库存、交付逾期 | 不发送无关通知 | 后台显著提示及筛选入口 |

首版必需的是订单内状态、站内可见提示及后台待处理计数；若现有全局通知能力不适用，可直接通过商城入口标记和订单页面实现。邮件仅在已有能力且收件地址有效时启用，不要求新建短信或即时通信服务。

通知只带商品/订单摘要和受登录保护的链接，不发送账号、密码、卡密、完整买家资料。通知失败可重试，不能导致再次发货或重复退款；用户始终可主动到订单页查阅。

## 9. 隐私、安全与信息呈现

- REQ-16：商品列表、普通订单查询、运营概况和日志不含完整交付秘密；单独领取动作逐次检查身份及订单权限。
- 秘密不进入 URL、分析事件、错误上报、邮件、普通缓存和浏览器持久存储；退出登录、切换用户后清除页面中的秘密。
- 凭据默认遮罩，用户显式查看或复制；复制成功提示清晰，复制失败允许手动选择，不误报成功。
- 买家补充资料仅用于对应订单履约；管理员列表脱敏，详情按必要操作显示，不擅自扩展为营销联系人库。
- 富文本、买家文字和导入内容按内容展示，不执行脚本；错误报告不整行回显账号密码。
- 订单、收款、交付与售后记录保留可追溯关系；凭据和个人资料保存期限由运营政策确定，上线前确认，不默认无限期保留。售前须明确交付内容的可重复查看期限、到期处理和售后时限，设计稿不得承诺永久查看或无限质保。
- 账户存在付款未知、未完成交付、活动售后/资金争议或任何未结退款责任时，拒绝软删除与硬删除；删除判断和新建订单须通过同一用户状态及一致事务保护，避免“检查后又新增订单”。禁用账户不绕过认证开放领取，由管理员承接存量交付、售后和资金责任并留痕。
- 无未结责任后才可按保留政策去标识化账户资料，订单、收款、交付、售后及审计引用不得级联删除；商品归档和入口关闭也不能清除这些责任。实施需覆盖现有主站用户删除路径，不能只增加商城页面提示。

| 场景 | 必须呈现的内容和动作 |
| --- | --- |
| 暂无商品/筛选无结果 | 区分店铺未上架和无匹配结果；提供清除筛选 |
| 缺货/人工容量已满 | 明确暂不可购买；不创建可支付订单，不承诺补货日期 |

| 登录过期 | 引导重新登录并返回原订单；不丢失已创建订单，不自动重新下单 |
| 价格/规则变化 | 展示新信息并重新确认；已建立的订单使用其快照 |

| 售后超期/退款未知 | 显示仍在处理及最新记录，不自动宣告失败或已退款 |
| 渠道已确认退款失败 | 显示失败与后续处理；同一退款责任下核实安全条件后重试，不混同未知 |
| 拒付/外部退款或资金争议 | 保留原实收及后续事实；管理员核实已退/在途/争议金额，买家看到可公开的处理进度 |
| 越权/订单不存在 | 不泄露订单是否属于他人；提供返回本人订单入口 |

## 11. 关键业务规则摘要

1. 售价、币种、数量和可售状态由服务端确定；首版数量恒为 1，任何界面都不能改写最终价格。
2. 一份库存只属于一个有效订单，一次真实收款可以重试处理但不能重复交付；细节见业务规则文档。
3. 浏览器返回、用户点击“已付款”及管理员普通状态编辑都不是可信收款依据。
4. 商城收款不增加 API 额度，不触发充值赠额、充值返佣或商城储值。
5. 付款、交付、查看、售后和退款是不同事实；查看过不等于商品有效或买家放弃售后。
6. 普通售后申请及额外重复款退款保留正常领取能力；明确暂停或有效商品款退款获批后，停止新的交付和秘密揭示。
7. 退款不能收回已被查看的信息，原库存不自动回库；退款事实不得通过删除原订单代替。
8. 商品规则在下单时形成快照；质保建议从完成交付起算，真实商品如需不同规则须明确展示并保存。
9. 关闭购买入口仅禁止新交易；现有付款核实、交付、售后、退款继续处理。
10. 时间存储与显示保持一致，面向买家的日期和截止时间带明确时区；绝对截止时间不因刷新页面重新计时。
11. 复用首发单渠道必须对商城与原充值执行交叉验收：充值仍按原规则仅一次额度入账/返佣，商城仅处理订单履约，不增加充值权益；两者交易和回调不可串单或互认。

以上是实施后的验收要求，本次文档编写并未执行这些交易测试。详细故障与交易矩阵见业务规则文档。

## 14. 首版禁用项

购物车、多商品合单、多规格组合、批量购买、拆单/部分履约/商品款部分退款、多商户、租户商城、分销返佣、优惠券、积分、秒杀、用户转卖、账号租赁和共享席位、供应商自动采购、多币种、商城储值钱包、API 额度抵扣、物流地址与运单、实时客服、任意表单生成器、明文库存批量导出。

这些能力不以隐藏按钮、预留伪配置或无后端实现的设计入口交付；新增必须重新确认资金、库存与售后边界。

## 16. 实施与设计交付边界

- 产品文档冻结交易范围后，UI 设计覆盖 PAGE-01 至 PAGE-11，并标注 REQ/AC 对应关系；关键异常状态与正常页面同时评审。
- 本轮 UI 是供用户审核的设计稿，不代表用户已经批准生产商品、商户收款或发布部署。
- 开发先实现一个渠道和人工闭环，再完成自动库存、安全交付及售后；两种交付和完整异常处理均通过后才满足首版。
- 实施任务不得以设计效果替代支付、库存、权限与退款验收，也不得因缺少真实经营参数而把演示值写成正式默认。

# 大请求体压缩优化方案

评审日期：2026-10-17，北京时间。用户已授权启动实施；实施范围、验证结果及未完成的上线门槛见 [实施记录](large-request-compression-results.md)。

## 最终推荐实施方案（2026-10-17）

### 决策

采用“三层方案”，按下面顺序实施：

1. **客户端 gzip 作为主优化**：由可控客户端在发送 JSON 前压缩请求体，直接减少客户端到实际 CDN 入口的上传字节。
2. **NewAPI 后端修复作为上线底座**：发布已完成的 gzip/br 长度、读取错误、超限状态码修复，保证压缩请求失败时在选渠道和计费前终止。
3. **Cloudflare Worker 暂不接正式流量**：当前 `api.kkrich.ltd` 经 SingG SaaS CNAME 接入，在自有 Cloudflare zone 建 route 不能证明公网请求会经过该 Worker。只有确认真实入口归属后，才重新做 Worker B 臂实验。

这不是把压缩能力绑定到某个固定客户端。不能控制客户端时，下一优先级是在 **SingG 实际入口** 或其明确支持的 SaaS/Edge 层启用同等压缩；不再把自有 zone 的隐藏 route 当作生产入口。

### 证据和目标

追加的 3 组、12 条正常 API 对照全部进入 channel 31 并成功完成：

| 原始体量 | 原文 GIN 总耗时中位数 | 客户端 gzip 中位数 | 体积比例 |
| --- | ---: | ---: | ---: |
| 8 MiB | 26.556 s | 13.699 s | 48.45% |
| 24 MiB | 64.084 s | 35.606 s | 48.45% |

因此第一阶段目标设为：压缩请求保持 100% 协议成功，8/24 MiB 的首内容中位数至少下降 15% 且至少 1 秒；没有新增 4xx/5xx、499、重复回源、重复计费或内存/CPU告警。实测结果明显超过这个初筛线，但仍需真实客户端和多窗口样本确认。

### 客户端实现合同

- 只对 JSON 的 `/v1/chat/completions`、`/v1/responses`、`/v1/messages` 请求启用；已有 `Content-Encoding`、multipart、文件上传和流式上传旁路。
- 原始 JSON 大于 128 KiB 才进入候选；客户端先在内存或受控临时文件中 gzip，再按压缩后大小发送真实 `Content-Length` 和 `Content-Encoding: gzip`。
- 压缩后仍超过 32 MiB 的请求按原有 API 限制处理，不借压缩放大解压后上限。服务端继续按解压后的字节数限流，不能信任压缩 `Content-Length` 绕过限制。
- 若压缩后节省不足 5%，发送原文，避免为不可压缩数据付出 CPU；阈值做成客户端开关，默认先开启 gzip。
- gzip 失败、内存不足、超时或客户端不支持时只回退为一次原文发送；一次请求不能同时发送 gzip 和原文，也不能自动重试 POST。
- 记录请求大小、压缩后大小、准备耗时和结果状态，不记录正文、Authorization 或 API key。客户端开关可按用户/SDK版本关闭，作为第一回退手段。

### NewAPI 后端发布内容

先发布现有本地改动，再接入更多客户端：

- gzip/br 解压后删除旧 `Content-Length`，将 `Request.ContentLength` 设为未知，由完整缓存大小作为真实解压后长度。
- 第一次 body 读取失败时缓存终态错误，插件识别、分发和模型解析再次读取时保留同一错误，不重复消费或关闭上传。
- 解压后超限统一返回 413，并在分发、计费和选渠道前终止；普通插件识别失败仍保留原 fallback。
- 保留当前解压后总大小上限，不将 Worker 的 32 MiB 压缩资格误当作 API 解压上限。
- 发布前保持已通过的 middleware 定向回归、Worker runner 回归和 `make policy` 证据；应用正式交付仍按 NewAPI 本地手册的 `production/kkrich`、bridge schema 和蓝绿门禁执行。

### Worker 后续路径

Worker 只在以下条件全部满足后重新启动：SingG 明确提供真实入口接入方式、Host/TLS/SNI 和回源身份经过验证、外层 Edge 有可关联日志、正式入口旁路等价通过。届时：

1. 先以 allowlist 和专用低额度 key 做隔离三臂：原文、Worker gzip、客户端 gzip。
2. 固定 2/8/24 MiB 规格，交错顺序，每规格至少 3 对；记录首内容、总耗时、实际回源字节、CPU、单次回源和 SSE 完整性。
3. Worker 只处理三个 JSON API 路径，32 MiB 是压缩资格上限；已有编码、超限和不可压缩请求旁路。
4. 保持单次回源、取消传播、无 POST 自动重试；生产诊断变量 `ACCOUNT_UPSTREAM_BODY=0`、`FORWARD_BENCH_ID_TO_ORIGIN=0`。
5. 只有隔离结果满足门槛，才按 allowlist → 10% → 50% → 100% 放量。任一协议错误、额外回源、CPU/内存超限或错误率上升立即关闭压缩并移除精确 route。

### 观测和验收

每个请求只保留阶段和关联字段：编码、原始/解压后字节、body 开始/完成、首内容、总耗时、HTTP 状态、channel/token、origin request ID。禁止记录正文、请求头、密钥和完整上游错误内容。

验收分四层：

- **协议**：100% 解压字节一致；SSE 恰有一个成功终止事件；损坏/截断/取消在选渠道前失败；超限为 413。
- **业务**：成功率、重复计费、重复回源、channel 选择和正常小请求不回退；上游 `server_error` 单独统计，不与上传失败混淆。
- **资源**：客户端准备耗时、Worker CPU、NewAPI RSS/GC/临时盘均在现有预算内；不以合成 padding 代替真实业务容量。
- **效果**：按等长窗口比较首内容和完整成功率；不要用单条成功请求或单条上游过载错误宣称修复历史 125 秒断开。

### 回退顺序

先关闭客户端 gzip 开关；若仍有问题，再将 Worker 压缩设为 off 或移除归属明确的 route；后端异常按正式蓝绿 rollback 回退。回退过程中不改 DNS、不切换 SaaS Custom Hostname、不自动重试失败 POST、不删除旧 rollback 资产。

## 结论

实施后的优先路线是：客户端支持时前移 gzip，配套 NewAPI 已确认的解压/错误处理小修；保持当前 CDN 入口。追加 12 条对照已证明 8/24 MiB 客户端 gzip 均可成功通过并显著降低耗时，但尚不能承诺历史超时消失。

复用现有 Cloudflare Worker 的原生流式 gzip，把候选范围从 8 MiB 扩到 32 MiB 的准备已完成；当前 SingG SaaS 入口不执行本次挂载的自有 zone route，因此先不接正式流量。独立接入方案及三臂验证通过后，再决定是否启用 Worker；它不能替代客户端到 CDN 这段的上传优化。

32 MiB 覆盖本次观测的 21,903,139 字节（约 20.89 MiB、21.90 MB）请求。它是 Worker 的压缩资格上限，不是新的 API 接收上限；超过该值仍按现有生产策略原样转发。

### 实施后调整（2026-10-17）

当前权威 DNS 将 API 指向 SingG SaaS CNAME；自有 zone 的隐藏 Worker route 实测没有改写前缀，请求在外层 Edge 返回 405，随后已撤销。不得直接把“自有 zone 挂回正式 route”当作可行上线步骤，也不在本次实验中修改 DNS 或 SaaS 入口。

在这个实际约束下，优先验证客户端直接 gzip：它能减少上传前半段及后续链路字节，无需改变当前 CDN。正常 API 已取得有限成功样本，精确数据与局限见实施记录。Worker 32 MiB 准备版本已发布但没有业务路由；B 臂仍待独立入口方案。下述三臂和放量门槛继续保留，不能因 A/C 功能成功而省略。

## 已知事实和证据边界

| 事实 | 含义与边界 |

| 本次会话核实 gzip Worker 脚本存在，但没有正式 `/v1/*` route，也没有对应 Worker Custom Domain | 核实当时普通请求未通过这个压缩入口；不能据此反推事故发生时路由状态，也不知道旧路由停用原因 |
| 方案开始前已部署代码压缩范围为大于 128 KiB、至多 8 MiB；遗留配置为 production / sample / 100% | 当时 21.90 MB 不在覆盖范围；实施后已调整至 32 MiB/allowlist，但没有业务路由，不代表已启用 |

| 同条请求在计费入口到 `doRequest` 入口间约 3.51 秒 | 压缩不会消除后续所有处理；函数入口不等于网络发送完成 |
| 历史五条请求在 Edge/Router 约 125.01 秒无响应头断开 | 高置信符合 Cloudflare 首包等待超时；历史日志不能直接证明这五条都卡在 body 接收 |
| NewAPI 已有 gzip/br 解压，并在完整读取 JSON 后分发 | 可复用；不需要为本次优化重写渠道、DTO 或计费链 |

## 四个评审视角及收敛结果

| 视角 | 核心意见 | 最终采纳 |
| --- | --- | --- |
| 链路与架构 | Worker 只能减少后半段传输；前半段慢需客户端压缩或减少上下文 | 三组对照后选择有效措施，不按压缩率直接推算节省时间 |
| Cloudflare Worker | 复用 CompressionStream；挂正式 route 会使全部 `/v1/` 流量经过 Worker | 隔离验证原样转发和压缩两条路径；入口切换与压缩比例分开验收 |
| Go / NewAPI 后端 | 未知长度先整包读取；压缩错误、超限和取消需要真实路由验证 | 小范围可先测试；正确性不通过则先修，资源不足才加入存储优化 |
| 发布与验证 | 遗留 100% 配置、8 MiB 测试工具边界及停用原因不能忽略 | 明确配置、同步工具、审查旧停用原因；保留精确路由回退 |

讨论后的取舍：不先全面重构 BodyStorage，也不带着未验证的压缩入口扩大普通用户流量。先用有上界的隔离实验判断收益，再用明确门槛决定必要修复。

## 实施顺序

### 1. 本地准备与小范围验证

- Worker 压缩上限候选改为 32 MiB，保留 128 KiB 下限及原有三个 JSON POST 路径。
- 同步 payload generator、canary runner、边界测试和说明；runner 不再保留独立的 8 MiB 限制。
- 保留流式压缩、单次回源、取消信号和禁止跟随重定向。压缩开始后若失败，不能退回原文自动重发 POST。
- 未知 Content-Length、已存在 Content-Encoding、正文签名/摘要、multipart 等继续按原策略旁路。
- 覆盖 8 MiB、观测体量 21,903,139 字节、24 MiB、32 MiB、32 MiB+1 的资格和字节保真边界。大于压缩资格上限应旁路，不应因此拒绝原来合法的 API 请求。
- 测试不使用客户原文。准备普通代码/工具日志/中文 JSON，以及伪随机字节转 base64 两类语料；不使用全重复字符夸大收益。

现有 `_kkai_canary_padding` 可控制模型输入成本，但它会被 DTO 丢弃，只能代表入站读取、扫描和压缩负载。另用本地真实 Responses 结构验证 DTO 解码、重编码和内存，不能用 padding 实验代替完整业务容量验证。

### 2. 隔离路径做三组对照

使用现有 `__gzip-production-canary`，专用低额度测试 key，先并发 1；新配置先明确设为 allowlist，不触及正式路由。

| 对照组 | 客户端 → Cloudflare | Cloudflare → NewAPI | 用途 |
| --- | --- | --- | --- |
| A：原样 | 原始 JSON | 原始 JSON | 基线 |
| B：Worker gzip | 原始 JSON | gzip | 判断后半段压缩收益 |
| C：客户端 gzip | gzip | gzip 原样透传 | 判断把压缩前移是否更有效 |

C 利用已有 `already_encoded` 旁路，不在 Worker 新增第三种工作模式。客户端压缩只在客户端支持或可控测试发送端上验证，不承诺现有客户端已有相应开关。

同一网络、尽量同一 POP、相同语料/体量/模型/输出限制，交错测试，先每规格 1 组、再 3 组；只有通过且有收益的候选进入 20 组决策样本。CPU/内存的本地容量检查逐步增加有限并发，不对生产运行无界压测。

短诊断批次可启用 `ACCOUNT_UPSTREAM_BODY=1`，完整消费后计算真实回源压缩比；性能批和生产恢复为 0。记录客户端首内容/总时长、完整回源字节、源站 body 读取阶段。Worker 读取 EOF 受回源背压影响，不能单独当作客户端上传完成时间。

结果决定路线：

- B 显著改善：进入 Worker 正式接入验收。
- B 收益很小、C 明显改善：主要措施前移到客户端压缩或由用户缩减上下文，不能为追求覆盖率强行启用 Worker。
- 两者均无稳定收益：重新定位剩余耗时，不宣称压缩修复了超时。
- 高熵语料压缩收益有限是合法结果，不要求所有语料都达到同一压缩比例。

### 3. 正式用户流量前的后端门槛

用真实路由验证正常 gzip/br、损坏/截断压缩流、解压后超限和客户端断开。校验失败必须终止，不得继续选渠、提交上游请求或发生费用扣除；解压后超限应符合 413 契约。

运行回归已确认两项问题，已完成本地修复，尚未发布到生产：

1. 解压后保留旧 ContentLength。Worker 自身会删除旧长度，主要风险在客户端自带 gzip/br；修正为解压后长度未知并移除旧头，完整缓存的真实大小仍由 BodyStorage 提供。现有代码未见按旧长度截断数据的证据。
2. 首次 body 读取失败在插件识别/分发时丢失错误身份或进入后续读取；解压后超限被返回为 400。修复保留错误身份和首次读取的终态错误，超限返回 413，同时保留普通插件识别失败的既有 fallback。

未知长度当前先 `io.ReadAll`，读完才决定落盘；磁盘 `Bytes()` 又可能整包分配。先测 32 MiB 下的 RSS/heap、GC、临时盘和有限并发，再决定是否加按实际字节跨阈值溢写。若资源余量不足，容量修复成为放量前置；即使渐进落盘，也不能宣称现有扫描全程常量内存。

维持当前解压后总大小限制，不把 Worker 的压缩资格直接放大到 500 MiB。

### 4. 正式入口接入与压缩放量

正式接入前重新核对线上 route、Worker 版本/变量、回源身份、现有相关日志能力，并查明旧路由停用原因。源码里的日志模板不证明线上已经安装。

先通过隐藏 production-canary 验证 control 原样转发等价：正确 Host/TLS/SNI、鉴权、非压缩路径、错误状态、SSE、单次回源和无递归。使用关联 ID 时，先满足现有外层/Router 日志与剥离门槛，再允许转发测试 ID。

正式 route 接入是独立入口切换：即便压缩关闭或仅 10%，100% `/v1/` 请求仍会经过 Worker 和现有 resolveOverride。接入后先验收旁路等价和立即回退能力，再 allowlist → 10% → 50% → 100% 扩大压缩范围；每阶段依据等长窗口及足够的大请求样本作决定，不只按等待时间自动推进。

完整回退使用现有 `route:formal-remove`，只删除归属明确的精确路由。把压缩设为 off 只能停止 gzip，不能回退 Worker 转发路径。回退不改变 DNS、Custom Hostname 或其他 Worker 路由。

## 验收与停止条件

- 正确性：解压字节一致；三类 API 的 SSE 完整且恰有一个终止事件；错误码、鉴权和取消行为保持契约；每请求一次回源，无自动重发、重复结果或重复计费。
- 覆盖：21.90 MB、24/32 MiB 样本确实命中 gzip；32 MiB+1 保持生产旁路。
- 收益：保留现有小请求首内容不回退门槛；建议把 24/32 MiB 普通文本候选的决策线设为首内容中位数至少下降 15% 且节省至少 1 秒，并核对 body 读取耗时和 P95 趋势。这个数值是本方案建议，尚不是实测结果。普通文本回源比率不高于 70% 可作为初筛，不能替代延迟证据，也不强加给高熵语料。
- 资源：没有 Worker CPU 超限/1102/内存故障；Worker CPU 分位用 Dashboard/GraphQL 取证；NewAPI 有足够的并发内存余量，无持续 GC、临时盘或清理异常。
- 超时：对比同体量请求的首内容分布、完整成功率与约 125 秒断开；20 组实验只判断初步效果，不能证明稀有故障已消失。正式放量仍需足够业务样本。
- 停止：任何协议/解压/正确性错误、额外回源或资源超限立即停止并回退；仅省带宽而延迟不改善，不继续以“修复超时”为由扩大范围。

现有 canary runner 的 `pass=true` 只代表其功能及状态类别检查，不自动证明压缩率、CPU、性能和上述全部门槛通过。

## 最小改动范围与后续事项

一期优先改 Worker policy、既有 payload/runner、对应行为测试、明确的首轮部署配置和 README；保留现有 Worker 流式处理主体。后端只加入经路由测试确认的必要正确性修复，不先重写完整读取/解析链。

实施验证按改动范围执行 Worker 的相关行为/配置测试和语法检查；基础设施仓库要求的 `make policy` 是可执行策略变更的发布门槛，不因只修改 Worker 而省略。若需后端小修，执行相关 Go 包的定向测试；不以全仓测试替代上述路由、字节保真和容量验收。任何实际后端上线仍走现有本地构建与蓝绿发布门禁。

建议补少量持久诊断字段：入口到 body 开始、body 读取完成、解压后字节数、转发开始。保留现有 use_time 口径，避免改写历史含义；若需证明网络发送完成，用 `httptrace.WroteRequest`，不能用 `doRequest` 函数入口。只记阶段/大小/编码及关联元数据，不记正文或密钥。

本期不采用：上传未完先发 HTTP 200/SSE 心跳、自动重试 POST、全包缓存后计算压缩长度、静默截断用户上下文、直接放开 64/500 MiB、全渠道 NewAPI→Sub2 压缩或盲目增大超时。NewAPI→Sub2 的压缩能力和成本另行验证。

## 方案形成时的审议状态

三位独立子代理分别审议架构、Worker、NewAPI 后端，主代理负责发布与验收收敛，已进行交叉质疑。方案形成时没有修改业务代码、Worker 配置或生产路由，也没有发起模型业务请求。之后按用户授权开展实施；验收门槛不因本地测试通过而自动视为全部满足。

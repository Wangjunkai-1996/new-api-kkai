## 2. 已核实的计费语义与价格影响

设旧模型基础费用为 `B`，旧有效分组倍率为 `G`，旧充值档位折扣为 `D`：

```text
旧人民币成本 = B × G × 0.075 × D
新人民币成本 = B_new × (G / 2) × 1
旧余额单位 → 新美元额度：× 3/40
QuotaPerUnit 保持 500000，不改变内部存储精度。
```

本次所有实际生效货币单价都按 `B_new = B / 7`：

```text
新单次内部扣费 / 旧单次内部扣费 = 1/14
新充值价格 / 旧无折扣充值价格 = 20/21，约降低 4.7619%
老余额换算后的可用量 / 原可用量 = (3/40) ÷ (1/14) = 1.05
```

例如旧 `1000` 额度变为 `$75`；原基础费用 `7`、分组 `0.4` 的用量原扣 `2.8` 旧额度、实付成本 ¥0.21，新扣 `$0.20`，实付成本 ¥0.20。

若取消后续充值档位折扣，新购同样用量与旧档位的比较为：

| 原充值折扣 | 新价格相对原实际价格 |
| --- | ---: |
| 无折扣 | -4.7619% |
| 97 折 | -1.8164% |
| 95 折 | +0.2506% |
| 92 折 | +3.5197% |

这些比例适用于本次货币单价 `/7` 且有效消费分组减半的非免费计费项，是未计整数 quota 舍入与最低扣费的理论比例。小请求用实际计费引擎核验，不能强行要求整数结果精确等于 1/14。订阅和外部现金价仍按各自单位核对，不套用站内消费公式。

`USDExchangeRate=7` 是显示换算，不是支付结算时额外乘 7。`Price=1` 表示 ¥1 购买一个内部美元额度。余额选择 USD 后显示 `$1`；如果切为 CNY 才会显示参考值 `¥7`，它不是用户实际支付过的人民币金额。

- 核实旧键 `GroupRatio/GroupGroupRatio` 与注册配置 `group_ratio_setting.*` 的有效加载顺序；若双份配置冲突，先明确单一有效值，保证重启后不会恢复旧值。
- 奖励/阈值 `QuotaForNewUser/Inviter/Invitee`、`QuotaRemindThreshold`、`checkin_setting.min_quota/max_quota` 等原始额度配置按 ×3/40 核定。
- **`PreConsumedQuota` 不按余额比例转换**：当前调用点将它用于最低预估输入 Token 数；名称不能代替单位分析。
- 充值单价独立的 Stripe/Waffo/Waffo Pancake/Creem 逐项核对。人民币 1:1 不能被当成国际支付渠道的 USD 现金 1:1；未部署或未启用的渠道保持其启用状态。

## 7. 旧订单、旧事件和历史统计的兼容原则

### 7.1 新旧纪元

定义本次唯一 `migration_id`，并持久化币制版本、精确比例、提交时间、执行计划 hash、旧记录边界及结果摘要。优先复用现有配置存储放置一个经过审查的迁移收据，避免仅为一次转换新建通用平台；具体键名/结构由准备阶段实现并验收。

迁移收据与主库金额修改在同一事务提交。旧记录边界使用表主键高水位及必要的源订单/事件映射，不能只依靠时间戳。晚到 webhook、异步事件和退款按**原业务来源的纪元**判断，不按“今天才收到”判断为新币制。

新代码在旧纪元也能工作，先通过正常发布安装，并让两个可回退应用版本都理解两种纪元。迁移后不能回退到完全不认识新单位的旧应用。若兼容设计需要 schema 变化，单独准备和授权对应 schema 方案，不把它偷塞进本次数据更新。

### 7.2 支付

`top_ups` 同列在不同渠道下单位不同：

- Epay/Waffo/Waffo Pancake 常按 `amount × QuotaPerUnit` 入账。
- Creem 的 `amount` 是原始整数 quota。
- Stripe 存在使用 `money × QuotaPerUnit` 入账的路径，不能把该列一概称为人民币现金。

用户已明确：现有未完成旧充值单是问题订单，没有需要补到账的款项。本次只记录旧订单主键边界与原状态用于拦截，不生成补款清单，不改变订单金额或状态，不在聊天打印个人交易信息。

币制收据固定记录 `legacy_topup_policy=hold`。切换前未成功订单的迟到回调和人工完成请求均返回明确的hold错误，钱包、订单及返利outbox保持原状。禁止自动补单、重试入账、按新单位补款或批量标记成功/过期；以后若需处理某个订单，应另行获得针对该订单的明确指令。

已成功的旧订单重复回调仅返回原有处理结果，不再次入账或触发返利。新纪元订单按新充值规则正常结算；旧问题订单hold不构成需要排空的支付积压，也不阻塞其他已满足条件的迁移步骤。

### 7.3 任务与预扣

默认要求窗口内没有活跃计费请求或未解决的任务结算。长视频等应提前暂停创建，等待真实任务、退款、账务 outbox 全部收敛；排空时间可能超过正式窗口，不能最后一分钟才等。

如果业务决定允许任务跨窗，必须提前实现：保留旧费率快照，以旧单位完成费用计算，记录已预扣在迁移时对应的新单位金额，再将最终目标额转换后计算差额。若换算函数为 `R`，应使用 `delta_new = R(final_old) - mapped_pre_new`，不能单独用 `R(final_old - pre_old)`。例如旧预扣7、最终14，两者换算后都是1，正确差额为0；对旧差额7单独换算会额外扣1。退款也必须按原交易已映射的实际金额及幂等记录处理。不得让旧快照按新组倍率再算一次。

部分退款、多次调整与事件重放都以持久化的已应用新金额计算差额，不能每次独立转换旧差额。订阅还要绑定原消费周期：当前预扣退款路径可能直接减少当前 `amount_used`，原记录未提供足够周期信息时，不能把旧周期退款冲减新周期消费。默认结清跨窗订阅请求；需要支持迟到退款时必须先实现周期识别，来源无法确定则停止自动处理并进入对账。

不能通过将未完成任务强制改成功、清空 outbox、立即退款后仍允许供应商完成来制造“排空”。账单、供应商订单与任务状态不明时停止推进。

### 7.4 Invitations、Redeem Issuer 和 outbox

- `topup.completed` 含 `credited_quota`，当前事件协议未明确币制。发方与收方一起升级，保留旧 payload/hash；旧事件重放按旧纪元处理，新事件显式携带或可靠关联新纪元。
- 返利原账本不重写。旧返利撤销先按原记录验证请求、签名和幂等，再按转换规则操作新钱包；禁止直接把旧 delta 从新钱包扣除。必须持久化“原操作ID/原币制金额→实际新钱包增减额”的对应及幂等状态，保证新账务 `balance_after - balance_before = applied_delta`，原payload/hash不变；不能仅在内存换算，导致重试或再次撤销无法重建。
- Redeem Issuer 自有 SQLite 的请求金额、quota、扣回快照和幂等响应必须有对应迁移/旧纪元解释。只改 NewAPI 的 `redemptions` 不够。
- `image.accounting.v1`、task accounting/audit/cache reconcile 等事件会校验或重读金额，必须纳入 drain 与重放测试。
- 辅助服务是否实际启用以窗口前发现为准。已退役服务不重建、不启动；历史 AI Image Jobs 不当成当前 worker。

### 7.5 历史显示与统计

保留原始历史日志、订单、审计 payload。展示旧金额时可同时呈现“旧额度原值”和“按3/40折算的新美元值”；不标成当时按新费率实际收取的金额。

所有跨窗口的看板、累计额、排名、导出、兼容 API 都先统一单位再汇总。主表累计 used 字段迁移后继续累计新单位，历史明细视图按纪元归一化。差额仅允许来自记录清单中已知舍入或既有统计口径，不接受“看起来差不多”。

## 8. 迁移工具的数据安全合同

### 8.1 精确计算

原始整数 quota 采用有符号四舍五入、半值远离零：

```text
new_q = sign(old_q) × floor((abs(old_q) × 3 + 20) / 40)
```

计算使用任意精度整数/decimal，或已证明不会溢出的分解算法；不能先在固定宽度整数里算 `old_q*3`。按实际字段类型验证上下界，溢出即终止，不能饱和截断。通用计费 helper 的 int32 饱和上限不适用于 int64 钱包迁移。

负数不擅自归零；普通余额极小值正常舍入到0时计入差额报告。字段语义优先于通用舍入：`subscription_plans.total_amount`、`user_subscriptions.amount_total` 中原正数不得因舍入变0而获得无限额度；原正数1至6个quota会出现此风险。当前工具对这类有限上限及正值未用兑换码若换算成 0 则拒绝自动迁移并报告具体行，避免误变无限或失效；此次样本未发现需要额外政策的微小额度。原来的 0 仍保持原有无限语义。其他要求严格正值的字段先列出处理政策，不能依赖隐式默认值。独立 unlimited 布尔保持不变。

订阅 total/used、令牌累计/剩余等关联字段采用统一且满足字段语义的规则，逐项证明余额关系；组合差异必须来自清单内可计算的舍入或最小有限值保护，不能用泛化容差跳过错误。

保留每行旧值、新值、精确理论值及舍入差。汇总验收必须等于逐行目标之和，不能只比较 `round(sum(old)×0.075)`，两者可能不同。

### 8.2 输入、幂等与漂移

迁移计划包括：维护 ID、应用/infra/工具版本、数据库身份和 schema 摘要、配置白名单 hash、逐表字段清单、逐模型目标、行数/主键边界、旧新汇总、变更前镜像和辅助库步骤。

记录迁移ID、当前阶段、各存储完成状态与停止的服务；跨库未完成时保持业务停止。连接中断后先查持久化收据，再决定继续或恢复，禁止盲目重复换算。用户已取消额外断电、宿主机重启和故障注入演练，不为这些场景追加通用维护框架；正常操作使用现有工具和逐项清单。

apply 必须：

1. 校验维护锁、身份、停写证明、备份可读和计划 hash。
2. 比较每个配置旧值与预期；数据与最终停写快照一致，否则重新生成计划并解释差异。
3. 拒绝未知字段、未知计费项、缺失价格、未分类来源和不可表示的目标金额。
4. 相同迁移 ID 已提交时只验证并报告已完成；不同计划 hash 或半完成状态必须进入恢复流程，不能再乘一次0.075。
5. 捕获中断，按持久化收据查询事务是否提交；SSH 断开不能当成未执行。

窗口前价格清单应已冻结；业务余额仍会自然变化，最终行级余额计划在停写后由确定算法重新生成，并与预演范围对账。不得将“余额与几天前不同”当作错误，也不得借此允许未经审查的价格/字段变化。

### 8.3 事务边界

主库可变金额与配置、迁移收据在单一事务里更新。设置有限的锁等待和 statement timeout，依照本次受影响表规模和定向验证设置数值；不能盲用5秒超时或无限等待。大表历史不在此事务中批量改写。

主库、独立日志库、Invitations 数据库与发码 SQLite 不存在天然共同事务。采用“持续停写 + 按存储记录步骤与前后镜像 + 所有存储验证完成才开放”的协议；任一步失败保持维护，按保存旧值精确恢复。主库 commit 不是整体迁移完成。

## 9. 备份与恢复准备

现有核心 DR 说明排除了 `public.logs`，也不能证明包含辅助数据库、SQLite、Redis队列和完整宿主配置。历史文档中的 restic/PITR 状态、备份定时器存在、或 schema snapshot 命令存在，都不等于本次数据可恢复。

`kkai-newapi-schema-snapshot create` 的已知条件绑定特定 schema 升级，不作为任意业务数据备份/还原入口。不得对整个 PostgreSQL 数据卷做默认回退，误删同机其他业务的新数据。

联合窗口采用两阶段备份：缩容前B0在现有其他文件系统或已验证远端保存完整appdata和元数据；缩容、挂回验收后，从释放的VG空间创建独立备份卷，在其上完成B1主库/辅助库备份与隔离恢复。B0/B1绑定持续停写边界，期间不恢复业务消费者，B0原副本继续保留。不能等缩容后才做首份磁盘安全备份。

备份/恢复工作目录必须使用本次独立备份卷，不落在缩容后的 16 GiB appdata。基础设施已按该目标准备外部存储参数与设备/挂载/容量校验，实际安装和冻结容量以 [联合计划](rc41-usd-joint-maintenance-plan.md) 为准；不使用临时软链接或降低容量门禁。

本次至少准备：

- NewAPI 主库完整、一致、可恢复的备份，包含日志表（同库时）、序列及必要权限。
- 独立 `LOG_DB`（若存在）、Invitations 库、Redeem Issuer SQLite 的一致副本。
- 白名单配置前后版本、不可变账本摘要、旧订单与事件清单、原拓扑与服务状态。
- 待恢复的有关队列/事件事实；只读确认 Redis 里哪些是可重建缓存、哪些是不可丢的业务数据。
- 全部拟修改行的精确 before-image，采用受限权限并加密保存，不进入 Git 或聊天。
- SHA-256 manifest、备份完成时间、数据库身份、行数与校验摘要。

准备期使用最小定向测试验证转换/收据/恢复逻辑；窗口按现有备份工具校验真实 B0/B1。用户已取消额外大规模演练，不追加克隆全平台、断电或实际缩容演练。任何本地测试均不得连接真实支付、回调、模型转发或生产队列。

最终备份在停止全部相关写入并完成 flush 之后取得。若采用前置全量备份加增量方式，必须先证明该组合能够精确恢复至本次停写点；未经验证的 WAL/PITR 不作承诺。

## 10. 维护窗口操作顺序

**本次联合窗口执行 [联合计划第4节](rc41-usd-joint-maintenance-plan.md#4-一次窗口的执行顺序)。** 下表保留为币制迁移本身的阶段说明；不能执行完本表后再单独做一次架构切换。顺序为B0卷外备份→磁盘缩容并验收→新备份卷与B1验证→schema升级→金额/配置迁移。目标应用启动和公开开放服从三项任务的联合门禁，其他受影响业务默认持续冻结到统一开放。

维护时间按用户安排执行，不以已取消的断电、实际磁盘演练追加数小时准备或自行宣布延期。实际步骤包含停流、备份、数据更新、验证和恢复服务；若某项必要代码或产物尚未完成，必须具体列出，不能谎称已准备好或到点强行更新。

| 阶段 | 操作与输出 | 推进条件 / 失败处理 |
| --- | --- | --- |
| W0 窗口前 | 完成第4节准备、精确版本产物与签名；冻结价格/字段清单 | 必要产物、辅助库验证或签名缺失时报告具体缺口 |
| W1 身份与互斥 | 重新 status；核对版本、schema、前端、安装 pin；取得维护锁与平台操作锁 | 无 candidate/rollout/switch/schema 操作；不与发布并行 |
| W2 禁止新业务 | 维护入口覆盖公网、origin、私网、管理员、内部接口；阻止新支付、兑换、签到、调额、订阅、relay、图片视频任务 | 私网和后台旁路同样受控；正常健康探针与运维通道按清单保留 |
| W3 旧业务收敛 | 在旧币制下完成流式/实时请求、任务结算、退款、支付对账和相关 outbox | HTTP连接归零不等于账务收敛；旧 settled UNKNOWN 和旧终态 task 保留原始金额并在运行时按高水位禁止再次资金变动；dead 保留且禁止通用重放；pending 仍须收敛 |
| W4 停写与 flush | 通过受管维护工具停止实际写入者，阻止自动拉起，完成进程本地统计flush；隔离数据库写权限及存量连接 | 所有目标表写入静止、无业务事务、flush无错误；失败保持旧配置并排查 |
| W5 最终快照 | 完整备份、before-image、边界和金额汇总；生成最终行级计划 | 校验备份完整可读，计划与冻结规则一致 |
| W6 主库迁移 | 一个受控事务更新当前金额、配置及收据；校验目标后提交 | 错误自动回滚事务；断线先查收据，不重复 apply |
| W7 其他存储 | 按清单完成辅助账本/SQLite/必要元数据处理，保持所有入口关闭 | 逐存储状态可核对；失败精确恢复，不能半开服 |
| W8 缓存与私网恢复 | 失效有关余额、令牌、订阅、价格/配置缓存；只启动受审维护模式下所需serving/测试组件 | leader、真实回调、Invitations/reconcile、outbox仍暂停；旧进程已退出且无旧值回写 |
| W9 私网验收 | 完成第11节受控局部验收及跨存储复核；完整真实副作用测试已在隔离环境完成 | 是否能精确恢复按第12节B/C判定，不能仅凭公网未开放判断 |
| W10 开放与观察 | 记录首笔真实业务写入及开放时间，逐步恢复入口、回调和辅助worker；确认唯一leader和幂等重放 | 首次真实支付、自动重置、迟到结算或其他新业务写入即进入12C边界 |
| W11 收尾 | 立即及至少5分钟后status、错误聚合与账务对账；次日复核重置/延迟事件 | 保存最终收据、前后汇总、异常清单和恢复资产 |

维护工具需要证明所有实际写入者均已隔离，包括 serving 节点、独立 leader、任务/风险worker、Invitations、Redeem Issuer 及其私网路径。数据库 `NOLOGIN` 不能阻止已经建立的连接；仅看连接数或只修改公网路由也不够。

本地已审计版本禁止 `BATCH_UPDATE_ENABLED=true`，但仍有 `quota_data` 等进程缓存在退出时 flush。执行时按实际安装版本核验，不把“等待一个TTL”当成写入静止证明。

缓存清理复用实际失效机制。用户缓存示例为 `user:<id>`，令牌缓存含 HMAC 及 fence；只清金额有关数据，保留认证fence、幂等、锁、队列、会话等需要的状态，禁止 `FLUSHALL`。订阅/选项/计费快照的内存缓存通过受管重载或重启一起处理。

私网验收产生的写入也算写入。只允许专用测试账号、明确额度与可追踪交易；若 W9 后需要直接还原，必须同时还原这些局部测试写入并证明没有外部业务事实。任何真实支付、晚到结算、自动订阅重置或返利发生，都立即进入第12节C边界，不等到W10。不能启动会 `RunOnStart` 执行真实业务的leader后仍声称可无条件还原。

## 11. 验收清单

### 11.1 数据与配置：全量验证

- 每个更新字段的行数、逐行目标值、分组汇总、总和、负数、0、极大值、软删除记录均符合清单。
- 所有未转换列、账户权限、密钥、原始支付数据及不可变账本 hash 保持一致。
- 用户钱包、邀请可用余额、令牌限额、订阅总额/已用额、已发未用码均为统一单位。
- 旧历史记录视图与转换后的累计值没有未解释的混单位相加；跨窗口滚动桶不能重写同一旧桶。
- `Price=1`、汇率7、USD显示、新充值档位/折扣、普通/专属分组及所有目标价格实测生效。
- 两次执行同一迁移不会再次缩放；重复/旧版本apply被拒绝；重启后仍保持目标配置。

### 11.2 业务验证：确定输入，核对真实账务

| 场景 | 预期 |
| --- | --- |
| 普通余额 | 旧1000额度→$75；真实页面/API一致，无额外×7显示 |
| 有限/无限令牌 | 有限剩余额度正确；无限权限不变；使用统计单位一致 |
| 普通文本扣费 | 输入、输出、缓存命中、缓存创建分别比对新模型基础价与有效组倍率 |
| 专属组/自动组 | 覆盖倍率生效；自动切换按实际组计费，未追加隐藏倍率 |
| 表达式模型 | 阈值前后、长上下文、fast、时间规则、图像音频分类均符合目标；不重复扣缓存 |
| 失败与退款 | 钱包、令牌、累计使用统计同时正确；重复通知不重复退款 |
| 图片部分成功/视频 | 预扣、实际生成数量、失败退款、迟到回调按同一纪元结算 |
| 订阅 | 有限额度、无限套餐、有限极小值不变无限、溢出钱包、余额购买、周期重置、旧退款全部正确；维护跨重置时刻和旧周期退款迟到不误减新周期消费 |
| 兑换码与发码 | 老码兑现转换后的权益，新码面额为美元；重复发码、撤销与SQLite账本一致 |
| 充值 | 新订单¥1→$1；网关币种为CNY；历史现金不变；旧问题订单晚到回调/人工完成均hold且零资金变化；已成功订单重复回调不二次入账 |
| 邀请返利 | 新事件、旧事件重放、旧返利撤销、重复dispatch不会多发或多扣 |
| 历史与导出 | 旧日志原始费率可追溯，新美元归一化有标识，累计与明细关系可解释 |
| 兼容接口/客户端 | Codex balance shim 等USD命名字段实际返回新美元；旧页面提交被币制版本检查拒绝 |

模型/支付的完整回归先在隔离环境用确定性响应完成。生产验收调用限定模型、测试账号与费用预算；实际支付使用经确认的支付方式完成，不模拟伪造生产到账。若暂不能做真实网关验收，保持该支付入口关闭并如实记录缺口，不能宣称该功能已验收。

观察错误使用批准的 `make newapi-error-window`：取迁移前正常业务窗口与恢复后等长窗口，使用UTC秒级RFC3339，候选窗口结束至少60秒后查询。维护期主动返回的503单列解释，不混入正常业务窗口。复核者为执行者，不增加一次用户审批。

模型错误聚合不是充值/账务正确的替代证据。另需脱敏支付失败、重复事件、退款差额、账本对账结果；不打印原始请求、密钥或个人支付信息。

## 12. 回滚边界

联合窗口采用更严格的控制器边界：`open`在启动任何writer/辅助进程前落盘`irreversible=true`。该标记一旦成立，即便尚未观察到新交易，也禁止使用本节B直接覆盖旧库；按 [联合计划第5节](rc41-usd-joint-maintenance-plan.md#5-恢复必须覆盖整套组合) 保全增量并评估前向修复。若更早已有真实外部业务事实，同样提前进入C边界。

外层还记录全体受影响应用的最早业务恢复边界。任何Sub2API、CPA或辅助服务已经恢复新写入，即使NewAPI尚未`open`，也禁止用B0覆盖整个appdata；只能按明确的数据归属恢复并保全其他业务增量。健康16 GiB卷上的币制/架构恢复不要求扩回144 GiB；从空闲池分配备份卷后，也不再默认具备完整扩回容量。不得删除备份卷或恢复旧LVM映射腾空间。

### A. 主库事务未提交

回滚事务，确认无其他存储已更新；保持或恢复原配置、缓存和服务状态，验证后退出维护。不得仅依据客户端报错判断事务状态。

### B. 已提交，但没有外部新业务写入

用同一 migration ID 的 before-image/备份**精确恢复旧值**，连同配置、收据、辅助存储状态一并恢复；重新失效缓存、私网验收并核对旧总额后开放。不能乘 `40/3` 逆算，因为舍入不可逆。

### C. 已恢复真实业务或接收了新付款/结算

禁止直接覆盖旧备份，也禁止只回滚镜像。再次进入维护，保全当前数据与迁移后的增量业务，按订单/请求/事件对账后前向修复或补偿。若必须退回旧币制，制定新的反向迁移清单并处理全部新业务；它不是本次自动恢复分支。

普通蓝绿应用 rollback 只处理应用运行和路由，不恢复余额、支付、辅助账本。迁移后应保留理解新纪元的应用回退版本。退款、支付和返利不能用数据库恢复抹去已经发生的外部事实。

恢复资产至少保留到两个完整日结/对账周期，以及最长旧订单/任务/返利重放时限被明确覆盖。暂以加密备份至少7天作为方案建议；删除以实际重放窗口与验收结果为准。基础设施默认24小时产物retention不自动等于数据迁移恢复保留期，必要时提前实现保留措施。

## 13. 验证范围与实施交付物

本次已包含 L3 账务和 schema 准备，已执行相关定向验证；具体命令、产物和未完成项见联合计划。不得把单模块通过当作生产联合迁移完成。

账务实现属于 L3。优先运行迁移工具的精确比例、舍入、幂等、漂移、失败恢复与旧事件测试；按影响运行 `model`、充值controller、计费表达式、relay helper、相关service和前端钱包/价格/历史视图的定向测试。测试必须覆盖真实账务合同，不用随机大循环或实现镜像测试填充数量。

实现前冻结确切命令及预期时间：应用目标测试通常应在5分钟内；全套、耗时未知或预计超过5分钟的命令按项目规则取得明确批准。基础设施维护行为修改仍须满足 `make policy` 等强制门禁；Ansible变化按规定执行 `make check`。保留金额舍入、有限上限不能变无限、收据写失败事务回滚等必要定向用例；不追加已取消的宿主重启/故障注入演练。不把本文件中的测试矩阵伪称为已经通过。

至少交付以下可审查产物：

1. 本方案的最终版本和用户商业选择记录。
2. 脱敏 inventory、逐字段数据字典、逐模型价格前后表、旧订单/任务/返利清单摘要。
3. 明确标注已存在/新实现的迁移工具与维护工具、源提交、可复现构建信息、精确操作命令。
4. 定向验证记录：精确换算、重复执行、漂移拒绝、事务回滚、价格与必要业务兼容。
5. 加密备份 manifest、before-image 索引、逐存储进度记录和回滚命令。
6. 维护后收据：唯一 ID、UTC与本地时间、版本、计划hash、前后汇总、舍入差、业务验证与遗留项。

本次新架构要求v9/API2，按全局入口的维护准备路径及infra runbook 22构建和交付；不能用普通bridge或canary直接部署到v7。现有架构流程与币制 CLI 分别保存 schema 与金额收据，操作者在全程停流下按清单协调提交与恢复。稳定到新schema/API/币制后的兼容迭代再用正常发布路径；不用生产candidate数据库演练迁移。发布产物按已授权准备流程在本机构建，生产执行仍等待用户维护窗口。

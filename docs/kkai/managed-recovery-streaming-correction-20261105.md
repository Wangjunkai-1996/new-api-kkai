# Managed recovery: 流式性能与恢复边界修正

日期：2026-11-05；验证状态更新于 2026-11-06。状态：两端本地代码、定向验证和本地首增量/分配小样本对照已完成，进入配套发布准备；CPU、磁盘大请求、真实客户端和线上验收仍待完成。

## 目标与取舍

- 正常请求不为可能发生的失败等待整次生成，也不被恢复专用计时器主动截断；流式内容产生后及时转发。
- 普通文本在可恢复的 429、暂时性 5xx、断流或超时后，继续按有界预算同号重试或切号。已输出的文本无法撤回，允许显示“正在重新生成”并发送新结果。
- 显式 JSON/schema 和工具调用不做**输出后的**特殊恢复。它们成功时正常流式交付；输出后失败就按原协议结束，不拼接另一轮结果。响应尚未提交前，保留原有安全重试；非流式请求同样只在提交前重试。
- 不新增客户端 reset 协议。上游重复计费可以接受；NewAPI 仍负责终端用户的计量与收费，Sub2 负责内部账号调度。

“正常请求完全零开销”不能按字面保证：要识别文本流中的错误并在输出后恢复，仍需逐帧解析和保存少量状态。验收目标是没有恢复造成的整段缓存、额外等待或健康请求截断，并实测剩余开销。

## 现状与原因

NewAPI 渠道开关 `setting.managed_recovery_v1` 同时启用了恢复协议和部分输出的完整性缓存。Sub2 `backend/internal/service/openai_recovery_stream_writer.go` 的普通文本逐帧发送，但 `writePublic` 将显式 JSON 内容暂存到 `structuredOutput`；Chat 工具帧、Responses 非消息项目也暂存到 `CommitAttempt` 后才释放。因此正常成功的 JSON 和工具请求也会延迟内容首字。

该 writer 还会逐帧解析/改写 SSE；首轮尝试被 `openAIManagedAttemptContext` 限为最多 600 秒，NewAPI 对受管请求设置 930 秒截止。Sub2 在 Responses 成功终态前发布续聊别名，别名写入失败可能把已经正常生成的内容转成失败。这些都是正常路径需要审视的影响，不能只删除缓存。

现有 `synthetic_begin/end` 仅用于文本重生成提示。NewAPI 消费内部控制帧，不向标准客户端公开 attempt 重置；客户端无法撤回已收到的半截 JSON 或工具参数。因此本方案明确放弃这两类输出后的自动重生成。

## 请求行为

| 场景 | 交付与失败处理 |
| --- | --- |
| 普通文本流 | 逐帧转发；输出前和输出后遇到可恢复错误，Sub2 按现有预算重试/切号。输出后重试显示重生成提示，失败尝试的用量不重复结算。 |
| 请求声明了 `tools`，实际仍只输出文本 | 在真正出现工具事件前，仍按普通文本处理；不能仅凭 `tools` 或 `tool_choice: auto` 禁用文本恢复。 |
| Chat `tool_calls`/`function_call` 或 Responses 工具项目开始输出 | 在转发首个工具事件前标记该次尝试不可重试；工具增量立即转发。此后错误发出失败终态，不再尝试第二轮，也不插入文本重生成提示。客户端可能收到不完整的工具数据，不能把它报告为成功工具调用。 |
| 显式 `json_object`/`json_schema` | 在请求开始时识别并走原有代理路径，不启用输出后受管恢复；流式内容实时发送。输出后错误正常结束，不向 JSON 插入提示。 |
| 非流式请求 | 保持响应提交前的安全重试；受管请求保留从请求开始起算的 930 秒总截止，不存在流式首字问题。 |

仅靠提示词要求 JSON、但未声明结构化格式的请求，协议层无法可靠识别，仍按普通文本处理。对未知的可执行工具输出，保守地采用工具事件边界。已发布的工具事件不能撤回；本方案保证服务端不会在其后再启动一次可能产生重复工具调用的尝试，不保证第三方客户端如何处置失败流中的部分参数。

## 实现边界

1. NewAPI 在发送 `X-KKAI-Recovery-Protocol`、选择受管超时/transport 和决定重试归属之前，识别显式 JSON 及现有不支持的请求形态；这些请求走原有路径，不因关闭受管能力而收到 422。Sub2 对直接到达的请求做相同的入口保护。带自动工具声明的文本请求仍可进入受管路径。
2. Sub2 保留现有文本 attempt 状态机与有界同号重试/切号。普通文本不增加整段缓存。工具事件一出现就停止该逻辑请求的后续恢复，并实时交付工具帧；Chat 与 Responses 的事件顺序、item ID、output index 和终态保持协议一致。不要把两次尝试的工具参数或 JSON 拼在一起。
3. NewAPI 保留受管握手后的 Sub2 独占重试、内部控制帧过滤和最终有效尝试的计量；不在已输出的流外再开启一层渠道重试。工具事件后失败仍须有明确失败终态和正确计量，不得被误记为成功。两端的受管选择必须一致。
4. 正常进行中的首轮流式请求沿用原有流式超时和客户端取消规则，不再受恢复专用的 600 秒首轮截断或预先启动的 930 秒硬截止影响。非流式受管请求仍保留从 `StartTime` 起算的 930 秒总截止，避免响应头之后无限等待正文。实际失败后才开始有界恢复，仍防止无限重试。Responses 续聊别名失败不得悄悄把已成功的本轮生成改成另一轮；不能将续聊导向错误账号。
5. 保留现有渠道级开关，不增加用户参数或客户端协议。两端代码都准备好并完成定向验收后，才重新启用试点渠道；本文件不授权修改线上开关或部署。

## 定向验收

- 用可控上游证明：正常文本、显式 JSON 和工具增量均在上游终态前到达客户端；健康长流不会在原有规则之外被 600 秒首轮计时器截断。
- 文本在输出前及输出中分别遇到可恢复 429/5xx：确实同号重试或切号；输出中只有可见的重生成提示和一个最终逻辑终态，NewAPI 不重复结算失败尝试。
- 带 `tools`/`tool_choice: auto` 但仅输出文本的请求仍可恢复；一旦输出工具事件，随后失败就结束，既不重新派发，也不拼接第二份工具数据。Chat 和 Responses 各覆盖一个实际用例。
- 显式 JSON 成功时实时输出；半截 JSON 后失败不注入提示、不拼接新尝试。非流式的响应提交前重试保持可用。
- 两端对受管协议选择一致；普通路径无新 422。检查 Responses 续聊别名与计量所需的基本成功/失败路径。
- 用相同请求、相同上游做开关对照，记录首个真实内容增量、完成延迟及 CPU/分配的代表性结果。没有实测数据前不承诺具体毫秒数或“零性能影响”。

不为罕见格式组合或极端故障矩阵扩大本轮范围；发现实际阻断正常请求或计费正确性的问题仍须修复。

## 当前验证结果

NewAPI 协议选择、取消/截止、transport/scanner、外层重试以及 Sub2 真实 SSE 样本的原生/转换回放定向测试通过；精确命令见[开发规格的验证记录](managed-recovery-development-20261105.md#本次验证记录2026-11-06)，未运行全套。非流式的 930 秒总截止已保留，流式不再使用它作为固定整段期限。

Sub2 本地可控上游小样本的开关对照已完成：关闭时首增量 2.316 ms、完成 29.922 ms、624 allocs；开启时首增量 0.524 ms、完成 27.737 ms、1008 allocs。样本采用 25 ms 终态屏障和 `AllocsPerRun(3)`，只证明本地首增量可及时交付并记录分配，不能推断生产快慢或零开销。CPU 对照、真实客户端、磁盘大请求额外读取与内存峰值仍待测；两端配套上线及线上验收另按发布手册执行，本文件不代表这些步骤已完成。

# 受管恢复优化产品需求

版本：1.0 · 2026-11-07

状态：本地代码、定向测试与有界性能对照完成；代表性负载、真实客户端及生产验收待完成

适用范围：KKAI NewAPI 与 Sub2API 的 OpenAI Chat/Responses 受管恢复链路

本文件是本次 `encrypted_content` 恢复优化的产品行为基线。实现细节与本地验证记录以配套开发文档为准；当前状态不代表性能验收完成、功能已开启或已上线。

## 1. 目标

本次优化解决两个问题：

1. 含 `encrypted_content` 的正常请求不应因为恢复保护被整体排除，正常内容应继续及时流式返回。
2. 上游出现可恢复的 429、暂时性 5xx、断流或超时后，系统应在安全边界内重试，并让管理员能够判断重试是否生效、是否救回。

恢复必须服从请求协议和上下文绑定。不能为了提高“救回”数量删除密文、删除 `previous_response_id`，或把不可迁移的上下文改写成普通文本。

## 2. 用户可见结果

| 请求情况 | 用户看到的行为 |
| --- | --- |
| 普通文本请求成功 | 首个真实文本增量按原有流式路径及时到达，响应格式不变。 |
| 普通文本在安全边界内失败 | 沿用现有有界同账号重试，仍失败时按现有策略切换账号；已输出文本无法撤回，客户端可能看到一次重新生成提示，最终只保留一个逻辑终态。 |
| 含 `encrypted_content` 的请求成功 | 密文字段原样保留并继续透传；不解密、不记录密文、不删除密文、不把密文转换为普通文本。首个真实文本增量不等待完整响应。 |
| 含 `encrypted_content` 的请求失败 | 只在原账号、原出口和原协议路线仍可用时进行有界重试。无法证明路线一致时停止并返回原始错误，不使用其他账号制造一个看似成功的响应。 |
| 请求含 `previous_response_id` | ID 保留并继续绑定原账号、出口和端点。没有完整可迁移历史时停止恢复，不删除 ID，也不做纯文本重建。 |
| 请求声明工具但尚未输出工具事件 | 仍按普通文本处理，不能仅因声明 `tools` 或 `tool_choice:auto` 就延迟首字或关闭文本恢复。 |
| 已向客户端输出工具事件后失败 | 立即结束当前逻辑请求并返回失败终态，不重新派发第二次工具调用、不拼接两次工具参数。 |
| 显式 `json_object`/`json_schema` | 保持原有 JSON 路径和流式行为。输出后的失败不拼接第二份 JSON；响应尚未提交前的既有安全重试继续有效。 |

客户端不需要新增请求字段、响应字段或 reset 协议。内部恢复控制信息不得出现在标准客户端响应中。

## 3. `encrypted_content` 的恢复边界

### 3.1 入口资格

含 `encrypted_content` 的请求可以进入受管恢复的诊断和失败处理流程。它进入内部 `opaque` 模式：系统只把请求体当作不可解释的原始上下文保存和重放，不尝试读取或修改密文内容。

显式结构化 JSON、不可重放的请求体以及其他已有不支持形态继续走原有路径。仅仅带有工具声明不能作为排除理由。

### 3.2 路由约束

受管恢复阶段的密文请求必须满足以下条件才能再次 Forward：

- account ID 与首轮一致；
- egress/binding 与首轮一致；
- endpoint、transport 和协议模式与首轮一致；
- 每次实际派发前、账号槽位刷新后都重新核对上述条件；
- 首次派发之后最多执行 2 次有界重试，超出后结束请求；“2 次”不包含首次派发。

`WithOpenAIManagedRetryAccount` 只能表达调度偏好，不能作为同账号保证。调度器选不到满足约束的账号时，必须记录 `route_unavailable` 并停止，不得落入普通调度选出其他账号。

首轮请求的既有选路和提交前安全 failover 仍按原产品行为执行；本次产品承诺覆盖的是受管恢复阶段的硬路由边界。若实现核对发现首轮 failover 会跨账号，必须在开发验收中显式记录，不得静默削弱该既有能力，也不得把它误报为密文受管恢复成功。

### 3.3 明确拒绝

上游返回 `invalid_encrypted_content` 或等价的上下文不兼容错误时，系统应：

- 保留原始错误语义；
- 记录可查询的停止原因，例如 `opaque_context_rejected`；
- 不删除密文后重放；
- 不把失败请求标记为 recovered。

跨账号携带密文上下文属于第二阶段能力。只有在真实协议、真实密文和真实账号池验证通过后才可单独评估开启，mock 或普通文本测试不能作为开放依据。

## 4. 首字与性能目标

本次方案的性能承诺是可验收目标，不是“绝对零开销”承诺：

- 正常受管请求在首个真实文本增量前不新增 Redis/history 网络等待；
- 不等待完整响应、不做整段响应缓存、不因预留恢复而主动截断健康首轮；
- 成功请求只进行一次正常 upstream dispatch；
- 首个真实增量继续即时透传；
- 完成阶段允许已有的别名/history 写入，不把它移到首字之前；
- 未启用受管恢复的渠道行为不变。

受管流仍需逐帧解析 SSE、维护少量状态并在完成阶段写入诊断，因此 CPU、内存分配和完成延迟可能有可测增量。验收比较同一上游、同一 payload、开关前后的首字 P50/P95、完成延迟、CPU/alloc 和 Redis alias publish error；结果须在可接受范围内，不能用本地小样本宣称生产零开销。

## 5. 计量与错误语义

- 一个客户端请求只保留一个最终逻辑终态。
- 受管重试的失败尝试不能重复结算为最终成功；沿用现有有效尝试计量规则。
- 工具事件已经公开后失败，不能记为成功，也不能通过第二次模型派发生成重复工具调用。
- `recovered` 只表示确实发生同账号重试或账号切换，并最终得到无协议错误的 `completed` 消费终态；普通一次成功不算救回。
- 诊断计数缺失或无法关联时标为 unknown，不能按零次重试统计。

## 6. 可观测性

管理员需要能够在既有日志中查询功能是否生效，但终端用户不需要看到这些字段，也不新增管理页面或专用接口。复用 `logs.other.admin_info` 保存结构化入口和终态摘要：

- 入口：握手成功、JSON/密文/不可重放体排除、能力降级及握手前错误；
- 终态：同账号重试次数、账号切换次数、`completed/incomplete/failed`、救回判定和停止原因；
- 密文正文、账号凭据、完整请求体和逐帧内容不得写入诊断。

管理员按渠道、分组和 UTC 时间窗口使用现有查询说明和脚本查看聚合结果。查询只输出分类与数量，不输出客户正文、密钥或可复用的密文。受管链路断开且没有终态时，必须保留为 incomplete/失败诊断，不能算作救回。

## 7. 开关、发布与回滚

受管恢复继续使用现有渠道级 `managed_recovery_v1` 开关。本需求不授权直接修改线上开关或部署。

重新开启渠道 31 前必须满足：

1. NewAPI 与 Sub2API 使用匹配的协议实现和兼容制品；
2. 定向测试覆盖普通文本、密文原样重放、同账号/同出口约束、`previous_response_id`、工具边界和显式 JSON；
3. 首字、计量、诊断和回滚检查通过；
4. 先以小范围流量观察重试、切号、route unavailable、invalid encrypted content 和 recovered 聚合。

发现正常请求首字受阻、密文被修改、错误账号被派发、重复计量或诊断串线时，应先关闭该渠道受管开关或按发布手册回到已验证版本，并保留上一组可回滚制品。回滚操作不删除历史诊断。

## 8. 非目标

本期不做以下事项：

- 不实现跨账号 encrypted_content 恢复；
- 不解密、持久化或展示 `encrypted_content`；
- 不新增客户端协议、数据库表、管理页面或专用查询 API；
- 不把所有 JSON、工具请求统一改成可输出后重试；
- 不改变普通请求的账号计费、公开错误格式和既有首轮选路；
- 不承诺绝对零 CPU、内存或完成延迟开销；
- 不为极端协议组合建立独立框架，发现实际阻断正常请求或计费正确性的缺陷仍需修复。

## 9. 产品验收标准

以下条件全部满足后，产品层才可认为本需求完成：

1. **正常流式**：普通文本和含密文 Responses 流的首个真实文本增量早于终态，密文字节与 `previous_response_id` 保持不变，成功请求只派发一次。
2. **密文恢复**：可控 429/502 场景下，同账号、同出口、同协议重试可成功；账号或出口不一致时不 Forward，并记录 `route_unavailable`。
3. **普通恢复**：无密文文本继续保持现有同账号重试后切号能力。
4. **协议边界**：显式 JSON 保持原路径；工具事件公开后不重试、不切号、不重复工具帧；`invalid_encrypted_content` 不删除密文伪装成功。
5. **续聊安全**：`previous_response_id` 的绑定不漂移；没有可迁移历史时不会通过文本化重建跨账号续聊。
6. **性能**：开关对照显示首字前没有新增远程等待或整段缓存；首字 P50/P95、完成延迟、CPU/alloc 和别名发布错误均有记录，结果在发布门槛内。
7. **计量与诊断**：每个请求只有一个最终逻辑终态，失败尝试不重复结算；管理员能按现有查询脚本区分 handshake、重试、切号、救回、unknown 和停止原因。
8. **回滚**：保留已验证回滚版本，渠道开关关闭或按发布手册回滚后，普通请求恢复原行为且历史诊断仍可查询。

文档验收只确认需求边界和可执行标准；代码、定向测试、生产发布及线上效果必须分别以开发文档、测试结果和发布记录为证据。

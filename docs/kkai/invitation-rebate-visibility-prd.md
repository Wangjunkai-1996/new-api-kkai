## 1. 用户问题与产品决策

用户在复制邀请链接前，需要回答两个问题：**好友做什么，我才有返利？返多少，按什么算？** 目前「我的邀请」能复制邀请码、链接和二维码，也能看邀请人数及返利汇总，但没有当前比例。即使已经有订单，返利明细也只列金额和状态，没有展示接口已返回的订单比例。

**首期做两处改动：邀请页首屏写清「好友充值返利 X%，按好友实际到账额度计算」；返利记录在金额旁写清「本笔比例」。** 前者帮助用户决定是否分享，后者让用户能核对一笔具体订单。两处的数字允许不同，不用当前规则解释旧订单。

| 读者／场景 | 用户应该能做到 |
| --- | --- |
| 第一次邀请、尚无订单的普通用户 | 打开「邀请返利」就看到与自己有关的充值规则，不用先邀请一个人、展开说明或询问客服。 |
| 销售账号 | 从默认的「受邀客户」进入也能看到同一条规则；销售身份变化后，不把旧比例当成新订单待遇。 |
| 已有返利的用户或客服 | 从「返利记录」辨认该笔是按比例还是固定奖励；能解释为什么历史订单与今天的比例不同。 |

**不做：** 不更改返利比例、计费基数、冷却期、申请门槛、审批或发放；不重算或补发历史订单，不做数据库迁移。侧栏菜单名称、钱包、注册页、Classic 主题、管理端规则编辑器均不改版；不新增规则中心、试算器或营销弹窗。

## 2. 页面设计与文案

### 2.1 邀请首屏：先看到规则，再复制链接

在 `/invitations` 的页面标题下、现有标签栏上方增加一条规则摘要。普通用户默认停留「我的邀请」，销售默认停留「受邀客户」；**不改变默认标签，也不要求销售切回「我的邀请」**。摘要不塞进累计返利金额那一排，避免把比例看成历史平均值。

示意（**7.5% 仅为测试示例，不是本站或任何用户的实际比例**）：

```text
邀请返利                                          刷新
好友充值返利：7.5%  ｜  按好友实际到账额度计算
其他奖励规则 ▾

我的邀请    返利记录    转入余额
邀请码、邀请链接、复制按钮、二维码保持原位
```

- **首屏正文**固定呈现「好友充值返利：{比例}」「按好友实际到账额度计算」。例如，测试订单实际到账 100 个额度单位、适用比例为 7.5%，则返利为 7.5 个额度单位。这里的 100 是到账额度，不是付款金额；页面不承诺现金返还或可立即领取。
- **「其他奖励规则」**为次要展开项，只放适用的说明：「订阅或兑换是否返利、返多少，以该笔记录为准。」「注册奖励为固定额度，不按充值比例计算。」注册奖励关闭时不展示注册说明；无补充内容则不显示展开项。首屏比例不藏进这里。
- **移动端**比例和计算依据可自然换行，紧邻标题。桌面、手机均不依赖鼠标悬停、颜色或图标表达状态。展开与重试可用键盘操作。沿用现有六种语言，按当前界面的七个选项分别验收：简体中文、繁體中文、English、Français、Русский、日本語、Tiếng Việt。百分比使用用户所选语言的格式。

### 2.2 返利记录：金额旁显示本笔比例

沿用现有桌面表格和手机记录卡，不增加必须横向滚动的新列。桌面在「返利金额」下加一行，手机在同一金额项旁或下方显示。金额、币制、订单状态和申请入口保持不变。

| 这笔记录是什么 | 金额旁的文案 | 取值原则 |
| --- | --- | --- |
| 订单返利，已记录比例 | `本笔比例：7.5%` | 直接展示该记录的 `rebateRatio`；当前仍在确认时保留现有状态，不将比例解读为已发放。 |
| 订单返利，明确记录为零 | `本笔比例：0%` | 数值零是有效结果，不等于缺失。 |
| 订单返利，比例为空 | 确认或待计算时显示 `比例待核定`；其余历史记录显示 `暂无比例记录` | 不根据金额相除、不用今天的比例填补，也不把历史缺失说成将来一定会补算。 |
| 邀请人或被邀请人的注册奖励 | `固定奖励（不按比例）` | 先识别奖励类型，再判断比例；固定奖励没有百分比是正常的。 |

## 3. 哪些比例可以承诺展示

| 类型 | 首页如何说明 | 结算依据与边界 |
| --- | --- | --- |
| 符合条件的好友充值 | 展示当前登录邀请人此刻适用的充值比例 | 复用结算匹配顺序：已生效且该时点销售身份有效的充值专属规则 → 邀请人分组规则 → 通用规则。计算基数是充值事件的实际到账额度，不是支付渠道实收、标价或客户日后消费额。 |
| 订阅订单 | 不承诺邀请人统一百分比，具体看该笔记录 | 现有订阅同步路径按下单好友的分组入账。即使邀请人不变，不同好友也不一定适用同一比例。 |
| 兑换 | 不承诺所有兑换均按首页充值比例，也不一律写「无返利」 | 兑换来源存在不同处理路径：充值事件可按充值规则处理，独立兑换记录有自己的订单类型和分组。以已记录结果为准。 |
| 注册奖励 | 启用时说明是固定额度 | 不是订单比例。邀请人与好友的奖励可能不同，本期不新增固定金额承诺或「注册即到账」文案。 |

**时间口径：** 首页回答「如果现在发生一笔符合条件的好友充值，按哪条规则算」；订单记录回答「这笔实际记了多少」。以服务端时间判断，不由客户端时钟、销售标签或历史最高值决定。与结算一致：销售规则或身份在某一秒变更，选规从下一秒起计入这次变更。停用当秒可能仍看到原比例，但不能再提交新申请；其后按现行匹配结果展示，保留原历史可见性。现有人工调整以订单已记录结果为准，本需求不新增调整行为。

## 4. 开关、缺失与异常

| 用户所处状态 | 首屏表现 |
| --- | --- |
| 按现有权限不可进入邀请页 | 保持现有入口与权限行为，不从钱包或公共接口泄露个人费率。 |
| 订单返利已开放，有匹配规则 | 展示实际百分比；显式配置为零则显示 `好友充值返利：0%`。 |
| 订单返利已开放，没有匹配规则 | 显示 `当前暂无适用的充值返利规则`；不显示 `0%`，也不暗示已有订单以后会补发。 |
| 订单返利关闭，但仍可进入邀请页 | 显示 `订单返利未开启`，不展示历史缓存的当前比例。若仅启用注册奖励，仍单独说明固定奖励。 |
| 首次加载、规则读取失败、旧服务不支持新字段 | 加载时不闪现数字；失败或字段缺失时显示 `暂时无法显示充值返利比例`，可用页面刷新重试。不要伪装成「未配置」或 `0%`。 |
| 已展示的规则刷新失败，或用户切换账号 | 失败时移除过期数字，不继续标成当前比例；切换账号不显示上一个账号的比例或邀请码。 |

判断顺序是先看访问权限，再看已确认的订单返利开关，最后读个人规则。开关明确关闭时，即使旧接口缺字段也显示「订单返利未开启」；开关开启但个人规则未知时，才显示「暂时无法显示充值返利比例」。只有「转入余额」关闭，或发放功能处于维护时，不据此把费率改为零。

**规则读取失败不等于已有邀请功能失败**：邀请码和汇总已成功获取时，仍允许复制和查看；若整个邀请接口失败，保留原有错误和重试体验，不绕过登录或权限校验。

## 5. 数据契约与实现范围

**Invitations 服务。** 扩展现有登录接口 `GET /invitations/api/invitations/my-code`，增加可选字段 `topupRebatePolicy`；不新建用户查规则接口，不让前端读取管理员规则列表。服务端从当前会话读取邀请人身份，从 NewAPI 获取实际分组，复用现有规则选择函数与服务端时刻，仅读取，不生成返利记录。对外只返回该用户的结果，不返回分组表、销售规则 ID 或其他用户的比例。

以下仅为**拟新增字段**的示例，不是现有接口实测响应：

```json
{
  "topupRebatePolicy": { "state": "available", "ratio": 0.075 }
}
```

| `state` | `ratio` | 契约 |
| --- | --- | --- |
| `available` | 必须是 0 至 1 的有限数，含两端 | `0.075` 显示 `7.5%`，`0.0001` 显示 `0.01%`，`1` 显示 `100%`。只做一次百分比换算。 |
| `not_configured` | 不返回 | 成功读取规则，但未匹配任何一条。匹配到零值规则不属于此状态。 |
| `disabled` | 不返回 | 服务端确认订单返利开关关闭。 |
| `unavailable` | 不返回 | 基础邀请信息可用，但本次无法读取个人规则。旧服务缺少整个字段、未知状态、无效比例亦按不可用展示。 |

**默认前端。** 首屏和已有「我的邀请」共享按登录用户隔离的 `my-code` 查询；核对复用该查询的调用方，避免一页多发相同请求或账号间复用个性化结果。复用页面刷新，不加轮询。明细仅使用 `GET /invitations/api/invitations/rebate-records` 返回的 `orderType`、`rebateRatio` 和已有状态，不给每笔订单追加请求。

**本地源码依据：** NewAPI 的[邀请页签与默认落点](../../web/default/src/features/invitations/index.tsx)、[邀请码摘要](../../web/default/src/features/invitations/components/user/invitation-summary.tsx)、[桌面及手机返利明细](../../web/default/src/features/invitations/components/user/rebate-records.tsx)、[用户接口类型](../../web/default/src/features/invitations/types/user.ts)、[充值事件及到账额度](../../model/topup_finalize.go)。独立 Invitations 仓库对应 `src/routes/user.rs`（个人摘要、记录比例）、`src/rebate_lifecycle.rs`（`selected_rebate_rule`）、`src/rebate_source_events.rs`（充值基数、快照）及 `src/routes/system.rs`（订阅与兑换同步）。这些是本地实现依据，不是线上账号费率证明。

## 6. 验收清单

以下费率和订单均为隔离环境测试数据，不在生产创建订单或改动用户配置做验收。

| 编号 | 场景与输入 | 必须看到的结果 |
| --- | --- | --- |
| A01 | 普通账号零邀请、无记录；分组充值规则 7.5% | 打开默认页，不点击、不滚动即看到 7.5% 和到账额度说明；邀请码仍能复制。 |
| A02 | 同时配置销售专属、分组、通用三条不同费率 | 生效的销售账号看到专属值；普通账号看到分组值；移除分组匹配后显示通用值。销售默认「受邀客户」同样可见。 |
| A03 | 销售规则或身份变更尚未生效、刚生效、随后停用 | 与同一服务端时刻的结算规则选择一致；停用后不借展示恢复申请权限。 |
| A04 | 分别返回显式零、未匹配、开关关闭、超时、旧服务缺字段 | 分别呈现 0%、暂无规则、未开启、暂不可用、暂不可用；无一种情况沿用上次的非零比例。 |
| A05 | 先有一笔记录 5%，后将当前规则调至 7.5% | 刷新后首页为 7.5%，原订单仍为 5%，金额及状态不变；下一笔符合新条件的充值按实际记录显示。 |
| A06 | 同页含已确认订单、未核定订单、历史无比例订单、注册奖励 | 分别显示本笔比例、待核定、暂无比例记录、固定奖励；不会把注册奖励当成 0%。 |
| A07 | 两名下单好友分组不同，或明细包含不同来源的兑换 | 首屏不把充值比例承诺给所有订单；有比例的订阅和兑换记录各自显示本笔值。 |
| A08 | 只开注册奖励；或开订单返利但关闭转入余额 | 前者仍能区分固定奖励与未开启的订单返利；后者不改变充值比例，原入口权限不变。 |
| A09 | 账号 A 退出后登录 B；再模拟只查个人规则失败 | B 不闪现 A 的邀请码或费率；规则区可重试，成功返回的邀请码、记录和复制功能不受影响。 |
| A10 | 桌面、360px 宽手机，逐一切换七个界面选项（含简中和繁中），使用键盘操作 | 无需悬停即可读懂比例及其基数；长文案换行，不遮挡复制、筛选或金额；明细无需增加横向滚动。 |
| A11 | 精度边界 0.0001、0.075、1；异常数据为空、负数或大于 1 | 三个合法值分别显示 0.01%、7.5%、100%；异常不输出百分比；旧前端仍可读取新服务的原字段。 |

## 7. 交付顺序、效果与工单反馈

1. **服务端先交付可选字段。** 用普通、销售、分组回退和零值规则比对结算选择。旧前端忽略新字段；不修改 Go 主服务、数据库、既有账本或发放流程。
2. **默认前端再交付两处展示。** 用新旧接口各验一次，覆盖手机、桌面、全部七个界面选项及切换账号。若服务端暂时回退，首页降级而历史比例仍可读；若前端回退，只撤回展示，无需数据回滚。
3. **完成标准。** A01 至 A11 在相应测试环境验收完成，特别是「新用户无需首单即可看到比例」和「改价不改历史显示」。用户可用版本验证前，不在工单里写「已上线」。
4. **效果观察。** 建议客服在上线前后各取连续 14 天，按相同口径统计「找不到邀请比例／不清楚按什么算」的去重工单数；有现成的邀请页访问人数时，再比较每千位访问用户的咨询数。没有分母则只报件数，不宣称转化提升；不为此新增用户级追踪。

**待排期回复草稿：**「已采纳。我们会在邀请返利页直接展示您当前适用的好友充值返利比例，并说明按什么额度计算；在返利记录里也能核对每笔订单的比例。」

**上线并验收后才使用：**「现在打开『邀请返利』（销售账号为『销售邀请』），在页面顶部即可看到好友充值的返利规则。查看『返利记录』，可以核对每笔订单记录的比例；注册固定奖励会单独标明。」

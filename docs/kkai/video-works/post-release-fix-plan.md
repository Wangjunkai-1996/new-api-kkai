# 视频作品上线反馈修复方案

日期：2026-10-28。本文件记录修复依据、实现范围和验收标准；具体发布结果以对应版本的发布记录为准。

目标：修复用户截图中的宽屏留白、成功作品没有真实封面、失败原因丢失三个问题。覆盖工作室和普通 API 视频，保留现有模型、扣费、分页及权限能力。

初版方案依据用户截图和本地源码审查。后续已完成下述生产只读聚合统计；仍不声称截图中每条任务的原始响应存在。

2026-10-28 补充：用户已授权实施及上线。对生产视频任务执行一次只读、按类型聚合统计，输出仅包含数量，不导出原始错误、用户资料或凭据。留存任务中成功 511、失败 964、状态未知 85。失败记录按现有任务字段作初步归类：笼统提交失败 742、未分类 104、真人/隐私限制 51、版权限制 35、媒体不可用 7、输入无效 4、上游额度 6、临时故障 8、格式不支持 1、任务过期 6。该统计为调查分组，不代表所有记录已能生成可公开详情；同请求、同用户、租户、渠道和模型初步找到单条错误日志的只有 25 条，仍需验证最终重试/请求路径/日志策略后才能恢复。其余 939 条没有符合初步条件的错误日志。状态未知的 85 条不擅自划为失败或退款。

这次调查还发现 240 条失败任务保存了 `Task.Data`，但未逐条按新披露规则验证其中是否有可展示的结构化业务 message。上述 25 条日志初筛候选也可能与这 240 条重叠，且尚未通过最终重试归属校验。因此目前不能可靠给出“可显示详情/不可显示详情”的总数或恢复率；页面会对每条记录按安全投影实时判断，缺少可信原文时明确说明历史详情不可用。

## 1. 已确认的根因

| 问题 | 代码事实 | 结论 |
| --- | --- | --- |
| 左右留白过大 | `video-works.css` 的 `.video-works-page` 设置 `max-width:1600px` 并居中；外层 Main 已默认 fluid | 本页宽度限制叠加固定边距，超宽屏不能利用侧栏右侧空间 |
| 列表内容集中在两端 | 行布局只让模型列伸缩，状态/时间/费用/操作列分别约 72/80/90/82px；封面 144×81px | 仅删除 max-width 会进一步拉大中间空洞，需要同步重分配信息列 |
| 成功作品没有封面 | `LoadTaskVideoOutputs` 仅从 Studio generation/output asset 取得 poster；普通 API 任务没有这条关联时省略 media；前端只认 `media.poster_url` | 缺少普通任务封面链路，不能仅靠 CSS 修复；Sora/Seedance 当前插件投影只提供 video，不能假设上游已经给了 thumbnail |
| 只显示 task submission failed | `executeTaskSubmission` 的失败收尾传入固定字符串；已拒绝提交的响应正文没有在这条路径写入 Task.Data；前端只读 fail_reason | 必须在失败发生时保留有用信息，再投影给界面 |
| 托管任务错误过于笼统 | `PublicFailureReason` 为防止上游诊断泄漏统一返回 video generation failed | 应增加安全的结构化错误投影，保留当前泛化作为兜底 |
| 失败详情视觉重点不对 | 失败复用成功播放器布局，大幅插画排在具体原因之前 | 失败详情需要独立的信息布局 |

旧文档允许普通 API/历史任务一直使用占位图，因此此前的封面验收覆盖不足。修订后，普通 API 成功任务也必须有真实封面闭环；只有确实不可恢复、受限或处理失败的记录才允许明确降级。

## 2. 页面布局

保留作品列表，不另建一套页面。取消本页固定最大宽度，使用侧栏右侧的完整可用区域。

| 项目 | 设计要求 |
| --- | --- |
| 页边距 | 常规桌面 24px，超宽屏 32px，平板 20px，手机 16px；极窄屏 12px。按可用内容宽度而非屏幕物理像素判断 |
| 顶栏 | 标题、简短说明、作用域切换；高度约 80–88px，装饰图缩小到约 64px，不挤占作品空间 |
| 封面 | 大屏 192×108px，中屏 160×90px；稳定 16:9 容器，图像裁切仅用于缩略图，完整预览保持原比例 |
| 列结构 | 封面、作品/模型、状态、提交时间、费用、操作；表头和行共用 grid 规则 |
| 大屏参考列宽 | 192px / minmax(260px,1fr) / 112px / 152px / 128px / 144px，列间距 16px。容器不足时先切换中屏或卡片布局，不强塞横向滚动 |
| 字号 | 模型名 15–16px，辅助信息 12–13px，主要费用与操作保持清晰；任务 ID 降为辅助信息，支持复制 |
| 失败列表行 | 模型下直接显示一行具体原因摘要；长文截断，详情可见全文 |
| 手机 | 使用现有卡片分支，原因与费用不隐藏；关闭、预览、下载和复制均可键盘访问 |

保持全宽的同时控制各字段的阅读宽度；不要简单拉伸全部文字，也不要增加新的装饰栏去填空白。

## 3. 全来源真实封面

### 3.1 推荐链路

1. 复用已经生成并授权可读的真实 poster。
2. 适配器若明确提供输出视频对应的 thumbnail/poster，经过现有可信来源检查后纳入同一投影。不能从任意 image 字段猜测；输入参考图、尾帧和演示图不得冒充输出封面。
3. 没有可用 poster 的成功视频，后台从实际输出视频提取一张画面并缓存。复用现有 `FFmpegVideoMediaProcessor.CreatePoster`、安全媒体读取、对象存储及 outbox 基础能力，增加普通任务封面的窄用途处理路径。
4. 前端仅懒加载缩略图。封面状态与视频可播放状态分开，封面失败不能让原本可播放的视频被误判为不可用。

这是完整修复的一部分，不应以永久播放占位图作为普通 API 任务的最终交付。

### 3.2 实现约束

- 新任务成功后异步调度；旧任务按近期记录分批补齐，并为当前可见页提供去重的异步补齐入口。列表 GET 只读状态，不能同步下载视频或运行 FFmpeg。
- 缓存身份使用内部任务 ID、制品 key 和稳定的结果版本；不能把会变化的签名查询参数当成新视频。多制品逐一对应，列表选择确定的主视频，预览切换后使用对应封面。
- 初始并发上限建议 2，任务去重、有超时、字节上限及失败退避。提取可能需要下载视频，不能假设 Range 一定可用；流量和临时空间均应有界。
- 沿用现有图片体积上限作为起点（当前处理器 JPEG 最大 120 KiB），缓存处理完成后再返回可读地址。确需其他编码时再评估，首轮不新增图片依赖。
- poster 地址遵守任务所有者、租户和管理员授权边界，短链接到期可续签；不暴露上游凭据、源地址或对象存储私有 key。
- 通用 TaskArtifactStore 当前为 disabled，不能假装已可直接存储。需明确接通窄用途的 poster 缓存和生命周期，不能为此启用整个通用制品归档系统。
- 不创建伪造 Studio generation，也不自动调用一次性归档工具；这些路径可能改变原始媒体保留方式。
- 复用基础设施前核验实际安装版本、存储及 worker 能力。源码存在不代表生产已启用；若实现确需 schema 变更，须单列设计和迁移，不夹带到普通应用发布。
- 历史视频源已失效时显示“原视频不可访问，无法生成封面”；只缺封面而视频可用时显示“暂无封面”，保留播放。只有已入队且可处理才显示“封面生成中”。

## 4. 失败信息与详情界面

### 4.1 信息保存与公开投影

在现有任务私有 JSON 元数据中增加窄范围 failure snapshot，统一覆盖提交被拒绝、响应立即失败、轮询失败三个入口。保存阶段、错误分类、上游业务错误码、脱敏后的业务 message、请求关联和最终失败时间；此改动优先不新增表。

公开 DTO 返回分类、可展示原文及明确的来源状态。中文摘要和处理建议由稳定分类映射并走 i18n，不能把翻译后的解释伪装成上游原文。复用已有 `videoGenerationFailureCode` 分类能力，补齐任务列表的投影；保留 `fail_reason` 兼容旧客户端。

仅提取已识别错误结构中的业务 message/code，不把整个响应正文、Task.Data 或内部异常直接发送给前端。现有 `MaskSensitiveInfo` 不能单独证明所有认证信息安全：需覆盖 Authorization、Bearer、Cookie、API key、签名 URL、内部地址等，并设置长度限制。对无法安全公开的诊断仍使用明确的安全兜底，管理员额外信息继续受权限控制。

仅在终态失败时确定最终原因，不能把早期重试错误覆盖到最终成功任务。更新 JSON 必须在既有锁/合并更新边界进行，不能覆盖并发写入的 billing/private_data。未知提交结果仍保持 unknown，不能因为有报错文本就改成失败或退款。

### 4.2 用户这条错误的目标展示

**生成失败 · 输入图片触发真人限制**

上游判断输入图片 `content[1]` 可能包含真人，因此拒绝生成。

**上游返回**（全文可见、可复制）：

> The request failed because the input image 'content[1]' may contain real person.

**处理建议**：检查该输入图片，更换符合当前模型要求的素材后重新提交。

`content[1]` 原样保留；它可能是请求内容数组中的位置，不能直接解释成“第 2 张图片”。使用“上游判断可能包含”，不把上游审核结果写成已确认事实。

费用区域显示账单数据证明的实际扣费、退款状态和计费详情。截图的 $0/已退款只有在对应记录账单确认后才沿用，不能从失败状态推导。

### 4.3 弹窗结构

成功记录继续以视频播放器为主。失败记录使用约 680px 的单列详情，随屏幕收缩：

1. 小型失败图标（32–48px）、标题、中文摘要。
2. 上游业务错误原文与复制入口，默认展开，不藏在“技术详情”。
3. 处理建议；仅有完整输入可恢复能力时才提供“修改后重新生成”，不能生成一个无效重试按钮。
4. 扣费/退款摘要及计费详情。
5. 模型、时间、任务 ID，管理员可见的渠道及其他技术信息。

失败状态不再保留占据半屏的播放器占位和大插画。现有切图可缩小复用；这轮的重点是内容与真实数据，不需要额外生图。

### 4.4 历史失败记录

- 优先读取任务已保存的结构化错误或响应中的有效错误信息。
- 对固定 `task submission failed` 的老记录，错误日志在记录开关允许且未被清理时可能保留原文。按 `execution.request_id = logs.request_id` 关联，并校验用户、渠道、模型和请求路径。
- 一个 request ID 可能对应多次重试，必须确认最终失败的归属；不能按相近时间随便匹配一条，也不能无条件取最新日志。
- 有唯一可信关联才补齐；没有证据则明确显示“该历史记录未保存详细失败原因”。不承诺所有旧记录都能恢复。
- 当前实现只在已授权的列表页只读投影可验证的历史详情，不回写旧任务。日后若需要持久回填，应另行审查候选清单和匹配依据，再执行有条件的幂等更新；不能通过列表浏览隐式回写，也不能修改任务状态、扣费或重复退款。

## 5. 开发顺序与验收

交付顺序：先完成布局和失败详情设计确认，同时落地失败 snapshot 与公开 DTO；随后接通普通任务封面处理、缓存和历史兼容；最后用真实结构的样本做端到端验收。三项共同构成这次完整修复，不能只改页面宽度就宣布完成。

| 范围 | 必须通过的验收 |
| --- | --- |
| 布局 | 1280/1440/1920/2560 CSS px，侧栏展开/收起；页边距正确、表头行对齐、无横向滚动；320/375px 手机可用 |
| 普通 API 视频 | 没有上游封面的成功视频，经后台处理后显示自身画面；刷新、换页后仍可复用缓存；测试不能只提供自带 poster 的 mock |
| Studio 视频 | 已有正常海报继续可读，签名到期续签；受限、删除和处理异常不泄漏媒体 |
| 多制品及异常 | 封面和选中的视频一一对应；源失效、缺封面、封面失败与视频失败清楚区分；不无限重试 |
| 具体失败 | 用户提供的 real person / content[1] 原文完整可见、可复制；中文解释准确；普通用户也可看到安全业务原因 |
| 各失败入口 | HTTP 拒绝、HTTP 200 内嵌失败、立即失败、轮询失败、先失败后重试成功、结果 unknown 都有回归覆盖 |
| 权限与脱敏 | 普通用户、管理员、跨租户、禁用用户边界保持；敏感响应字段不进入公开 DTO；仅靠前端隐藏不算通过 |
| 账单 | failure snapshot 和历史补齐不改变收费/退款结果，不覆盖并发账单字段；无法确认的费用保持未知 |
| 历史数据 | 可唯一关联的记录恢复正确原因，多次重试歧义和日志缺失有明确降级 |
| 性能 | 列表不拉完整视频、不逐行查库；后台抽帧限流去重；封面缓存稳定，不因地址续签重复抽帧 |

实施时只运行受影响包/模块的测试、相关 lint/typecheck 与实际浏览器交互；发布按既有 runbook 单独执行必要检查。重点增加上述缺失的契约测试与真实数据形状验证，不以堆叠测试数量代替覆盖。

实现范围：提交拒绝、立即失败和轮询失败的安全诊断快照，历史列表只读恢复，普通任务真实视频抽帧封面，以及宽屏和移动端布局。上述生产统计是只读调查，不代表历史错误已持久回填；构建、灰度和生产验收以对应发布记录为准。

## 6. 主要代码落点

- 页面宽度/列布局：`web/default/src/features/usage-logs/video-works/video-works.css`。
- 列表封面/摘要：`video-work-item.tsx`；失败详情：`video-work-preview.tsx`、`video-work-details.tsx`。
- 列表媒体投影：`controller/video_works.go`、`service/task_video_media.go`、`dto/task.go`。
- 通用制品识别/读取：`controller/task.go`、`controller/task_media_proxy.go`、相关 provider 适配器。
- 可复用抽帧：`service/video_media_processor.go`；安全读取/任务基础设施：现有视频资产与 outbox 实现。
- 提交错误：`controller/task_submission.go`、`relay/relay_task_policy.go`；终态轮询：`service/task_polling.go`。
- 失败披露边界：`model/task_result.go`；已有分类：`service/video_generations.go`。
- 精确日志关联：`model/task.go` 中 execution.request_id、`model/log.go` 中 request_id；历史修复必须单独实现和审查。

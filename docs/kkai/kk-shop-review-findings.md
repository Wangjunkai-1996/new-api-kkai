# KK 商城多角色复审与修正记录

日期：2026-10-27。范围：产品文档、独立交互原型及必要的本地源码核对。

本轮结论：保留“现有 KKAI 内增加独立商城模块、复用渠道能力、商城交易与充值分开核销”的方案。发现的问题集中在异常资金处理、订单生命周期与设计原型的状态一致性，不需要引入另一套商城后端或扩大首版业务范围。

这里的“修正”指产品规格或本地设计原型已修正，不表示相应服务端能力已经开发、上线或完成真实资金验证。

## 参与视角与分工

| 视角 | 重点 |
| --- | --- |
| 虚拟商品产品与运营负责人 | 售后闭环、查看期限、风险处理、无法匹配的收款 |
| 支付与交易安全架构师 | 重复退赔、退款失败、额外款与商品款隔离、补发防重 |
| 应用架构与 QA 验收负责人 | 现有账户删除入口、充值回归、需求到验收覆盖、订单快照 |
| 主审与交互审查 | 跨文档一致性、访客路径、草稿输入、原型修正与浏览器验证 |

三个角色独立只读提出证据，主审去重并确认修正范围，再分别修改文档和原型；未将已声明的静态原型限制当作服务端缺陷。

## 发现与处理

P1 表示实施前必须消除的交易、权限或核心流程歧义；P2 表示需要补齐的交互和回归覆盖。

| 编号 | 级别 | 原问题及触发条件 | 修正与验收依据 |
| --- | --- | --- | --- |
| R-01 | P1 | 渠道已有拒付或外部退款，本地仍可能按原全额再退款 | 保留独立后续资金事实；执行前核对已退、在途、争议金额，争议未决停止新增退款和相关履约。AC-21 / BR-37 |
| R-02 | P1 | 收款无法匹配订单或金额/币种异常，只有异常数量，没有可执行结案流程 | 按渠道收款身份独立定位、保存证据及责任；恢复原映射后重新校验，不能把短款人工改成成功；否则按原收款差错退款。AC-19 / BR-35 |
| R-03 | P1 | 买家有风险暂停状态，管理员却缺少明确暂停和复核恢复入口 | 增加订单级独立风险控制、原因与公开说明；解除暂停仍校验退款、争议和查看期限。AC-18 / BR-34 |
| R-04 | P1 | 主站账户删除可能让未结商城责任失去买家关联 | 增加软/硬删除与并发下单保护；禁用沿用认证限制，由管理员承接责任；交易引用不级联删除。AC-22 / BR-38 |
| R-05 | P1 | 原凭据已经到期，补发的新版本可能刚交付就无法领取 | 新版本沿用订单快照查看时长，从自身交付完成起算；旧凭据不恢复，权益与质保不因此延长。AC-17、24 / BR-33、40 |
| R-06 | P1 | 同单额外款提示只依赖一个主状态，发起售后或原款退款后消失 | 额外收款使用独立记录，允许与售后、原款已退款并存；额外款退款完成有独立结果。BR-31 |
| R-07 | P2 | 同一售后补发完成后，返回后台仍可再批准补发 | 保存该售后的补发完成结果，重复操作读取原结果；需要新的补发时另有处理决定。BR-26 |
| R-08 | P2 | 退款核实原型只有未知/不匹配/成功，没有已确认失败路径 | 增加失败原因、同一责任下继续处理；排除旧尝试成功/在途和拒付冲突后才能登记关联重试。AC-20 / BR-36 |
| R-09 | P2 | 只验证商城不增加额度，无法发现共享支付改造破坏充值 | 增加同渠道充值和商城的正常、重复、交叉回调验收；充值按原规则入账/返佣，商城仅履约。AC-23 / BR-39 |
| R-10 | P2 | 访客直接进入结账或订单页时，原型未保持登录边界 | 受保护页面与付款动作都校验演示登录状态；登录后重新确认，不自动创建付款。AC-03、06 |
| R-11 | P2 | 商品草稿预览把名称/规格当 HTML，且描述保存后重复追加说明 | 自由文字按文本输出；默认说明只初始化一次，保存不重复追加。REQ-16、17 |
| R-12 | P1 | 从订单离开浏览另一商品，再返回时，订单金额和领取类型跟着变化 | 当前浏览商品与选中订单分离；订单详情、领取和售后使用固定订单商品上下文。AC-02 |
| R-13 | P2 | 草稿提示保存成功，但类型、人工 SLA 和容量恢复旧值；查看期限只藏在文案中 | 已展示字段保存并回填；查看时长与版本起算方式独立呈现。REQ-10 / AC-15 |

完整行为以 [PRD](./kk-shop-prd.md) 和 [业务规则](./kk-shop-business-rules.md) 为准。当前 PRD 有 18 项稳定需求、11 个页面、24 条产品验收；业务规则有 40 条 Given/When/Then 验收。

## 与现有代码有关的实施接点

- `model/tenant_consumption.go` 的 `checkTenantUserDeletionTx` 对主站直接放行。因此账户保护是商城开发必须补的集成点，不是已存在的商城能力。
- `service/wallet_payment_gateway.go` 的支付创建仍接受 `TopUp`，有充值幂等前缀与 `Wallet recharge` 描述。渠道调用可提取，充值业务参数不能照搬给商城。
- 原充值定向回归入口包括 `service/wallet_payment_gateway_test.go`、`model/topup_finalize_test.go`；真实实施时按实际改动选取相关测试，不默认执行全仓测试。

## 尚需运营确定的事项

首批真实商品与可交付资料、价格/币种、首发渠道及其退款核验能力、人工服务时段/容量、质保/退款/查看期限和资料保留政策仍待确定。它们是开业前的经营输入，不阻塞本轮文档与设计审查；未确定时保持草稿和关闭真实购买。

补发新版本的查看窗口沿用原快照时长，是本轮明确提出的首版规则建议。具体时长继续等待运营确定，并应在售前说明中披露。

## 验证与边界

本轮定向验证结果及设计截图见 [UI 规格的验证记录](./kk-shop-ui-spec.md#10-验证记录)。没有运行全套应用测试，没有修改生产业务代码、数据库或部署配置，没有创建真实订单或操作资金。

这些文档验收是后续实现的要求。静态设计稿和本地状态检查不能证明服务端鉴权、验签、库存并发、退款证据、数据库兼容及账户删除事务已经正确实现。

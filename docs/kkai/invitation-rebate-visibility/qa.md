# 邀请返利比例展示：测试与需求追踪

依据：[工单 #28 产品需求文档](../invitation-rebate-visibility-prd.md) §2–7。**所有用例待执行。** 本次只核对本地源码、测试文件和过滤名；下文建议新增或补充的测试均尚未编写。既有测试是回归基线，不是本需求已通过的证据。

两条独立的验收依据：**首屏**与同一登录邀请人、同一服务端时刻的充值结算选规比对；**明细**与该条记录的 `orderType`、`rebateRatio` 和状态比对。不能让首屏和明细互相充当预期值。

## 未编号承诺（均待执行）

- **访问与披露（A02、A04、A09；后端）。** 分别以未登录、已登录无权限普通账号、已授权 A 请求个人摘要。前两者维持原拒绝／入口行为；A 的结果只来自会话身份和服务端实际分组，客户端自报别的账号或组不能改变结果。对比脱敏响应：只在登录的 `my-code.data` 增加可选 `topupRebatePolicy`；`available` 只有 `state` 和有限数值 `ratio`，另外三态均不带 `ratio`（不是 `null`）。公共 `status` 无个人比例；个人响应不含规则 ID、分组表、销售事件、他人比例、原始数据库错误。鉴权、基础资料或原汇总整体失败不能包装成局部成功。
- **查询和资金流程（A01、A05、A06、A08；后端与前端）。** 网络计数：同账号一次首屏或一次手动刷新，摘要与「我的邀请」共用一个 `my-code` GET；不为首屏预取记录，不加轮询、新规则端点或管理端请求；一页十笔记录只取一次分页列表，无逐笔补查。固定隔离数据前后对照：反复读摘要不新增／修改返利记录、快照、申请、发放、余额、出账任务；不要用已有明细接口代算首页，它原有注册奖励解锁检查。确认期、金额门槛、审批与发放仍按原流程；只看摘要或展开不触发写请求。普通记录订单金额列／美元、销售 `legacy_075` 无美元符号、`usd_credit_v1` 仍按美元；分页、筛选、批准待发与已发状态都不变。
- **钱包与范围（A08、A09；前端与评审）。** 从邀请页切到钱包再换账号。钱包卡本就复用 `my-code`，有权时仍显示本人的链接、汇总和返利中心入口，不新增比例；身份查询错误时仍可重试、不发个人摘要请求、不露普通转账回退。记录网络和 DOM，与基线比较。核对实现 diff：不改 Go 主服务、迁移、费率、冷却期、侧栏名称、注册页、Classic、管理端规则编辑器；不新增规则中心、试算器、弹窗或个人追踪。
- **版本搭配（A04、A05、A11；QA）。** 同一夹具先留旧前＋旧后基线。旧前＋新后：先验旧字段和旧功能不变；新前＋新后：走矩阵；新前＋旧后：开关开且缺字段仅首屏不可用，明确关闭则显示未开启，历史有值仍显示，码仍可复制。分别回退一侧复验对应组合，不能要求回滚数据。留两端版本及契约／页面对照，不能仅凭类型可编译签收。
- **工单与效果（产品／客服）。** 用户可用版本通过验收后才可反馈「已上线」。上线前后各连续 14 天按同口径统计「找不到比例／不清楚基数」的去重工单数；仅有既存访问人数时才报每千人咨询数。不新增埋点，不推断转化提升；此观察不阻塞功能验收，本轮不更新工单。

# 工单 #28：邀请返利比例展示开发手册

**交付范围：** 独立 Invitations 服务为登录用户返回当前充值规则；NewAPI 默认前端在邀请页首屏展示这条规则，在返利金额旁展示该笔记录的比例。本文是开发交接，不是实施或上线记录。

本次核对的本地源码：NewAPI `642c05b60`、Invitations `ddad789`。版本用于开发定位，不代表生产版本。交付时先由后端提供脱敏接口样例，前端可并行按样例开发，最后由 QA 用两端实际版本逐项签收。

## 先对齐两份数据

| 用户问题 | 唯一数据来源 | 实现时不能这样做 |
| --- | --- | --- |
| 我现在邀请好友充值，返多少？ | `GET /invitations/api/invitations/my-code` 的新增可选字段 `topupRebatePolicy`，以服务端当前时刻选择充值规则 | 不能从最近一笔订单、销售标签、客户端用户分组或运营示例推断；也不按实付现金展示。 |
| 这笔记录按多少返？ | `GET /invitations/api/invitations/rebate-records` 中该条记录的 `orderType`、`rebateRatio` 和状态 | 不用首页比例回填历史，不用金额相除；比例未知不等于零，固定注册奖励没有比例。 |

后端是规则的唯一解释方；前端只负责展示。`available` 携带 0 至 1 的数值型 `ratio`；`not_configured`、`disabled`、`unavailable` 均不带 `ratio`。不开新接口、不读管理员规则、不改 Go 主服务、账本、数据库或发放流程。不要为了首屏读历史列表：它不能回答当前规则，现有明细处理还会检查注册奖励解锁。

## 开发顺序与覆盖

| 工作项 | 完成条件 | 对应验收 |
| --- | --- | --- |
| 1. 后端冻结契约 | 完成个人规则成功／零值／未匹配／关闭／局部失败的样例；说明同秒生效边界，以及原有访问错误不能当成功响应。 | A02、A03、A04、A08、A11 |
| 2. 前端完成两个默认入口和历史明细 | 可先按样例并行开发。一个账号一次摘要读取；个人规则查询失败不妨碍已成功取得的邀请码。桌面、手机、普通与销售共用判定口径。 | A01、A02、A04、A05、A06、A07、A08、A09、A10、A11 |
| 3. QA 联调并提交证据 | 以 [QA 矩阵](./qa.md) 为唯一逐项签收表；各项均需有结论，不能用「页面能打开」代替规则比对。 | A01 至 A11 全部 |

交叉验收优先走这一条：测试账号尚无订单时首屏已能显示比例；一笔订单记为 5%，再将该账号适用规则改成 7.5%；刷新后首屏为 7.5%，原记录仍是 5%，金额、状态与可申请性不因展示变化。两者都用隔离数据，不创建生产业务记录。

## 质量与交付条件

- **代码评审：** 后端须指明复用的结算选择函数和只读查询边界；前端须指出按账号隔离的查询键、后台刷新失败的渲染分支和百分比单位。若新写了一套规则匹配、引入依赖或改了转余额／发放逻辑，退回拆分，不并入本需求。
- **隐私与错误：** 未授权必须继续拒绝；仅规则查询失败可以降级。响应和客户端缓存不得让 B 看到 A 的邀请码、费率或订单；交付证据使用测试账号并脱敏，不留令牌或真实客户记录。
- **验证：** 开发者提交受影响路径、定向验证命令及实际结果。QA 区分「已通过」「未执行」「阻断」，关键测试无有效断言、匹配到零个用例或依赖数据库却被跳过，都不能算通过。仅文档交接不跑应用全量测试。

## 交付与回退

| 组合 | 应有行为 |
| --- | --- |
| 旧前端＋新 Invitations | 旧前端忽略可选字段，保留原邀请码、汇总和记录行为。先交付服务端并验此组合。 |
| 新前端＋新 Invitations | 执行完整矩阵；当前规则与单笔历史各自可核对。不得用版本号代替业务验收。 |
| 新前端＋旧 Invitations | 开关已确认关闭时显示「订单返利未开启」；开启且缺字段时仅规则区显示暂不可用。历史有 `rebateRatio` 的记录仍能显示，复制与原权限不变。 |
| 单侧回退 | 前端回退撤掉新展示；服务端回退等同上一行。不迁移或回滚业务数据。 |

**停止交付的条件：** 出现跨账号串数据、未知显示成零、历史比例被当前值覆盖、查询触发新的资金操作，或两个版本组合破坏已有邀请功能。完成 A01 至 A11 后再按正式流程申请发布；本文不授权上线或变更工单。上线效果按 PRD 的 14 天客服口径回看，不新增个人跟踪。

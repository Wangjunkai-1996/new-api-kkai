# KK 商城 UI 设计与交互规格

版本：V2 · 2026-10-27。状态：原创美术与界面升级，待用户审核，独立设计原型，未接入业务代码。

设计依据：[产品需求文档](./kk-shop-prd.md)、[交易与售后业务规则](./kk-shop-business-rules.md)。
预览入口：[高保真交互设计稿](./kk-shop-design-preview.html)。总审核入口：[审核说明](./kk-shop-review.md)。

## 1. 设计目标与范围

设计方向为“纸艺数字陈列室”：奶油白画布、钴蓝主动作、纸艺静物插画与编辑式排版共同建立识别。首页与商品页强调选物和浏览乐趣，交易页面强调金额、条件和下一步。付款前展示买到什么、适用条件、交付方法与售后范围。方向决策与图像规范见[美术方向](./kk-shop-art-direction.md)。

买家使用现有 KKAI 公共页面框架，管理人员进入现有后台的商城工作区。商城复用账号、主题与组件语言，并保留独立于 API 充值的购物心智。

本次交付覆盖 PAGE-01 至 PAGE-11。HTML 内嵌样式和交互，图片保存在同目录 `kk-shop-assets/`，离线预览时须一并保留该目录。不依赖网络字体、第三方 CDN 或真实业务 API，不引入应用依赖。9 张原创图由 KKAI / KKRICH 的 `gpt-image-2` 生成；页面只读取本地优化后的 WebP。初版保留为 [V1 对照稿](./kk-shop-design-preview-v1.html)。

## 2. 视觉体系

### 2.1 布局与视觉取舍

- 奶油白页面画布配墨色文字，钴蓝用于主要动作和选中项；商品封面以纸材、折面和柔和投影建立统一系列。
- 中文使用清晰的系统无衬线字体；辅助英文与编号作为编辑式节奏。六款商品各自拥有独立图像主体，不再以单字母替代商品视觉。
- 主要信息由排版、间距和细边框组织，不用多层阴影、大面积渐变、玻璃卡片或无依据的统计制造质感。
- 状态由图标、文字和颜色同时表达，不能只通过红绿区别。
- 首页只出现真实有业务意义的交付与售后提示，不展示销量、评分、倒计时促销、虚假热度或“保证秒发”。
- 商品名称均为虚构通用示例；没有借用未确认销售授权的第三方品牌。

## 3. 与现有 KKAI 的融合

- 公共页头沿用 KKAI 品牌、现有主导航、登录/账户、主题和通知结构，增加“KK 商城”。页面级次入口为“我的订单”。
- 商城与订单页面使用公共布局，不强制买家先进入技术管理控制台。
- 后台沿用顶栏、侧栏与下钻工作区方式；商城下设运营概览、商品、库存、订单处理、售后退款。
- 首版不新建身份系统、商城钱包、独立客服聊天窗口和供应商后台。
- 已有项目标识与归属保持，原型页脚包含 `new-api / QuantumNous`。
- 正式 UI 使用现有 `Button`、`Dialog`、`AlertDialog`、`Sheet`、`Field`、`Input`、`Select`、`Badge`、`Tabs`、`Table` 与 `Empty`；文案通过现有 i18n 维护全部实际启用语言（当前仓库也包含 zh-TW）。原型是中文设计素材，不直接作为最终生产组件代码。

## 5. 响应式规格

| 尺寸 | 结构 |
| --- | --- |
| 桌面 1440px 及以上 | 居中宽画布；首页不对称主视觉与商品网格；详情大图与购买摘要；订单和后台保持高效率信息分区 |
| 中间宽度 | 保持内容可用空间；主内容能自然收缩，文本允许换行；管理表格仅自身容器水平滚动 |
| 手机 390px | 主视觉使用适配裁切，保留纸艺插画；主站简化为品牌、头像和菜单；分类横滑；两列商品；详情、结账、订单变单列；主要触控目标约 44px |
| 窄屏 320px | 商品卡改单列；关键事实与表单改单列；按钮可换行；正文与凭据按字段断行 |
| 原型手机预览 | 工具条“手机预览”把产品画布限制为 390px，评审工具留在画布之外；正式窗口窄屏仍以 media query 为准 |

移动端详情购买栏只显示当前商品金额与购买动作；正文仍提供完整交付与售后规则。长表格允许局部滚动，不应造成整个页面横向溢出。后台小屏顶部变为横向工作区导航。

## 6. 核心组件与交互

### 商品卡与购买摘要

商品卡呈现名称、规格、价格/币种、交付方式、库存状态。卡片整体可打开详情；缺货仍可查看详情，但无法下单。只有一种规格和数量 1，不出现购物车或无后端能力的规格选择器。

购买摘要区强调金额、数量、交付方式与库存。所有价格、库存和演示条款持续有“演示”标识，不把示例当作真实承诺。

### 付款

主按钮提交当前订单并进入本地演示入口；不会调用渠道或生成可收款二维码。用户返回只进入“付款核实中”。买家界面的“刷新付款结果”只显示查询状态，不会把订单改成已付。

仅产品外的审核工具条可以切换“服务端确认 → 自动交付”等付款结果场景。该工具条不属于正式产品，不得移植进买家界面。

### 安全查看

订单默认遮罩；用户点击查看后分字段展示，无效演示域名使用 `example.test`。复制按钮捕获浏览器剪贴板结果，失败提示手动复制，不假报成功。离开页面、切换场景、退出演示账号后收起内容。人工交付表单填写的演示结果保存在当前页面内存，买家领取时展示该开通结果和指南，不被替换为固定账号密码。无 `localStorage`、`sessionStorage`、网络请求或浏览器持久化。

正式实现必须由领取接口逐次校验登录、订单归属、退款/暂停及查看期限；原型中的状态按钮不能证明加密、鉴权、审计、缓存控制已实现。

### 表单与弹层

表单都有可见标签、输入说明和必要的错误提示。重要操作采用原生 `dialog`，保留标题、关闭按钮、Esc、焦点管理等浏览器行为；正式版映射现有 Dialog/AlertDialog。主要提交要求必要输入，危险或影响交付的动作要求说明理由。

补发、隔离、退款审批和人工交付均需显式确认。售后公开说明和管理员内部备注分开，普通备注不得承载凭据。售后申请与是否已交付分开记录：人工待交付、待补资料、迟到款缺货提交申请后仍无秘密可领；暂停与查看到期不会因申请售后解除。退款、暂停和到期仍保留原有已交付时间线。

## 7. 状态与动作规则

| 状态 | 主要动作 | 必须避免 |
| --- | --- | --- |
| 待付款 | 继续付款、结束本次购买 | 展示凭据、使用浏览器状态认定付款 |
| 付款核实中 | 刷新结果、查看订单 | 再付一次、盲目创建第二笔交易 |
| 已关闭 | 重新购买、查看原记录；已付可查看核实 | 复活旧价格、声称外部渠道绝不再收款 |
| 人工待交付 | 查看截止时间、申请售后 | 重置已经开始的承诺时限 |
| 待补充信息 | 只收集约定必要字段 | 要求密码/验证码；资料未齐全却展示已启动倒计时 |
| 迟到款且缺货 | 承认已收款、查看处理、申请售后 | 让买家重复购买或重复付款 |
| 已交付 | 查看内容、复制字段、申请售后 | 每次查看分配不同库存 |
| 普通售后 | 查看售后、补充说明；原内容仍可看 | 因发起售后自动剥夺查看权 |
| 明确风险暂停 | 查看进度、申请/继续售后 | 通过复制入口绕过暂停 |
| 查看期限已结束 | 查看历史、继续售后 | 返回过期凭据、删除已付款和交付历史 |
| 原商品款退款待核实 | 查看退款进度 | 新交付、秘密展示、当作已退款 |
| 原商品款已退款 | 查看退款记录、重新购买 | 原凭据自动回售或重新领取 |
| 额外重复款 | 保持正常交付，独立展示额外款退款 | 把整单标为已退款、暂停合法商品交付 |
| 补发完成 | 查看新版本、查看处理关系 | 覆盖旧交付证据、收取第二笔商品款 |

人工时限从“可信付款确认”与“必要资料齐全”中较晚者起算。设计样例使用 24 自然小时、Asia/Shanghai；缺资料只说明起算条件，不虚构绝对截止时间。生产值须按真实商品确定。

只有有效商品款退款批准才暂停新的交付/查看。管理员先批准并生成唯一退款责任，再到渠道操作，最后回到同一记录登记证据和核实；未知/不匹配结论不变成成功。额外款独立退款不暂停正常履约。

## 8. 原型操作指南与演示场景

页面顶部黑色栏是独立审核工具。页面切换覆盖 11 页，场景切换覆盖以下状态：

`normal`、`guest`、`soldout`、`empty`、`error`、`pricechanged`、`nochannel`、`pending`、`checking`、`delivered`、`manual`、`missing`、`closed`、`late`、`duplicate`、`after`、`paused`、`expired`、`refund`、`refunded`、`reissued`、`refund_failed`、`extra_failed`、`payment_exception`、`payment_unmatched`、`payment_currency`。

也可用 `?scene=delivered#order`、`?scene=manual#order`、`?scene=expired#order` 等链接加载场景。页面由 hash 确定，场景由 query 确定，两者独立，适合固定截图。工具条手动选场景时会跳到对应典型页面。

### 复审补充的交互

- PAGE-08：草稿保存名称、类型、价格、规格、说明、人工 SLA/容量和凭据查看时长，并原样回填；自由文本按文字呈现。查看起点以每个交付版本完成时间为准。演示保存不会发布商品。
- PAGE-10：增加订单风险暂停/复核恢复入口和处理记录。恢复只解除风险标记，不解除退款、争议或查看到期限制。
- PAGE-10：付款差错明细以渠道收款身份独立定位，展示实收与预期金额币种、商户/环境、映射差异、责任和证据。只有原映射恢复且全部校验通过才能继续原单处理；短款与异币种不能手工标为成功。
- PAGE-11：已补发申请展示既有补发记录，重复操作不生成新的交付；补发版本独立计算查看截止，原版本不恢复。
- 退款核实增加渠道已确认失败；与未知结果区分。同一退款责任下先确认旧尝试无成功/在途/拒付冲突，再登记关联重试。普通商品款仍保持暂停交付；额外款失败不暂停合法交付。
- 订单详情的额外款提示不依赖单个主状态，能够与普通售后和原款已退款并存；订单内容读取固定快照，浏览其他商品不改变订单和领取字段。
- 访客直达结账、订单、领取或售后先显示登录边界；登录后重新确认，不自动生成付款。

新增覆盖 AC-17～24 / BR-33～40。其中账户删除、共享支付回归、渠道拒付事实与服务端权限属于实现验收，不由静态设计按钮证明；完整复审依据见[多角色复审记录](./kk-shop-review-findings.md)。

### 推荐的点击验收

1. `#home` 分类/搜索 → 商品卡 → `#product/1` → 立即购买 → `#checkout/1`。
2. 不勾条款尝试提交，确认阻止；勾选后进入演示支付入口；返回后确认仍为付款核实中。
3. 用独立工具条切到“服务端确认 → 自动交付”；主动查看、复制、收起；进入售后填写并提交，再追加说明。
4. 用工具条切“人工待补充信息”；补邮箱后转待交付；查看时限口径。后台 `#fulfillment` 提交人工交付时必须填写内容并确认。
5. `#inventory` → 导入库存 → 检查预置错误样例：重复/错误整批拒绝；点击有效示例，重新预览并确认，显示成功结果。
6. `#aftersales` → 批准补发，填写依据，买家看到新版本；重新选正常/售后场景可独立审核退款。
7. 退款路径：批准全额退款并填原因 → 登记渠道引用/证据 → 核实为未知、不匹配或成功；前两者始终保留待核实。付款差错队列使用独立额外款退款弹层与 `PAY-DEMO-EXTRA-0381` 记录，正常商品款不变。
8. 独立检查“额外重复收款”“风险暂停”“查看期限已结束”“原商品款已退款”；确认秘密入口符合矩阵。
9. 用手机、深色工具切换并在实际 390px、320px 窗口检查；移动端菜单可进入商城/订单/演示后台。

## 9. 本地演示边界

- 状态、订单、库存、交易、SLA、质保、查看期限、金额、统计与渠道身份均为虚构演示数据，刷新后重置；不代表运营默认值。
- 首页六款商品可筛选和搜索；订单列表与后台使用有限示例集，不实现真实分页、数据库查询、对账或多管理员并发。
- 商品编辑提供字段、卡片预览与校验反馈；发布检查明确阻止把示例配置真实上架。
- 库存预检按固定账号模板演示行数、重复和缺字段；不是生产导入解析器、密文存储或跨批次去重实现。
- 售后和备注只在内存中演示；敏感交付示例固定无效，不上传、不持久化。不提供附件真实上传或库存明文导出。
- 退款成功演示依赖明确的“匹配渠道成功结果”场景；真实证据核实、权限、交易身份匹配与资金状态在后端实施验收，原型不能提供实际退款保证。
- 主站非商城入口显示说明，不跳真实线上服务；管理员切换只是审核入口，不代表生产权限机制。
- 原型不是 React 生产代码，不修改现有路由、支付、schema、i18n 文件或部署配置。正式实现须复用现有组件，并完成全部实际启用语言的翻译、键盘/读屏与对比度验证。

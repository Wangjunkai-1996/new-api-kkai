# 钱包充值故障修复与体验改善方案

日期：2026-10-25。状态：A/B 修复已实施，发布证据另行记录；C 为后续独立改动。

## 目标与依据

用户完成支付后应能看到可信的订单结果与余额；正常报价、恢复和刷新不挤占登录、支付额度；暂时故障可在钱包内恢复。保留现有验签、收据幂等、行锁事务、订单版本检查和后台对账，不新增支付状态机、数据库迁移或消息基础设施。

本次事故已确认两项独立根因：

- 网关纯数字 `trade_no` 经路由自动解析后变成 number，钱包要求 string，导致前端错误页默认显示 500；同时该字段是网关流水，站内订单应取 `out_trade_no`。
- 北京时间 09:30:08，报价接口返回 429。对应匿名客户端此前 5 次登录续期、3 次恢复、6 次报价、2 次创建、2 次继续支付、2 次确认结果共用 CT/IP 桶，20 次成功后第 21 次被拒绝。同期站点配置为 200，用户确认余额到账。

以上为本次调查证据，不代表未来上线时的实时状态。具体复现命令和脱敏计数见本次审查记录 `/tmp/newapi-wallet-review-20261025.md`。

## 三个角色的交叉评审决策

| 角色 | 主要结论 | 讨论后取舍 |
| --- | --- | --- |
| 支付系统架构 | 回跳展示与账户当前充值流程必须分离；支付结果以服务端为准 | 使用现有订单详情 GET 展示回跳单，不为看结果强制 restore，不抢占其他标签页的当前订单 |
| 产品体验与前端架构 | 余额始终可见；自动确认状态；成功后能明确再次充值 | 保留自动报价；保留用户点击“再次充值”时的 acknowledge；不在看到成功时自动清除账户流程 |
| 可靠性、安全与验收 | 自动报价不能耗尽认证/交易预算；错误不能驱动请求循环 | 钱包使用按租户、用户和操作分类的预算，保留全局 IP 防护；不新增更严格的钱包 IP 共用桶 |

明确否决：仅 `z.coerce.string()`、仅调高全局限额、关闭所有限流、每次查看订单都 POST restore、到账后自动 acknowledge、浏览器回跳宣称支付成功、用前端无限轮询代替后台核实、为这次故障重写支付或全站限流系统。

## 用户最终看到的流程

```text
钱包：余额与充值记录始终可见
  → 选择金额与支付方式，显示服务端报价
  → 点击“立即支付”，创建一次订单并打开支付页
  → 支付返回，自动读取本次订单
      ├─ 服务端确认成功：显示到账凭据并更新余额，可“再次充值”
      ├─ 尚未确认：显示“正在确认支付结果”，保留订单与历史入口
      ├─ 待核实：明确暂未完成入账，给出可用的查询/支持入口
      └─ 请求失败或限流：就地提示与恢复，保留余额、订单和已选金额
```

只有服务端 `success` 表示已到账。`credit_review` 涵盖时间证据不足、金额异常、额度容量等不同原因，不能统一承诺“马上到账”。120 秒只是前台自动查询窗口，不是支付失败期限；后台核实继续运行。

## A. 首批必须修复的根因

### A1. 支付回跳与站内订单链接规范化

涉及 `web/default/src/routes/_authenticated/wallet/index.tsx`、根路由的入口处理，以及已有 `/console/topup` 兼容入口。

1. 从共享 router history 的原始 `location.search` 用 `URLSearchParams` 读取订单标识，避免长数字失精；不改变全站默认 search parser。真实路由回归确认 TanStack 的 ParsedLocation.searchStr 已经过 parse/stringify，不能作为原始输入。
2. 识别网关回跳时只使用合法、唯一的 `out_trade_no`，忽略支付方 `trade_no`。缺失、重复、非法参数不能回退为支付方流水。
3. 普通站内链接继续兼容现有 `trade_no`，遵循已有字符/长度契约，不新加 WT/USR 前缀限制破坏历史订单。
4. 规范化为只含受控站内订单号和已有历史筛选参数的 URL；使用 replace 清除 `sign`、`pid`、`money` 等外部参数。保留站内订单号，使刷新后仍能查询已确认的历史订单。
5. 规范化必须覆盖冷启动、SPA 导航、前进后退和未登录回跳。为避免把支付签名带入登录 redirect，在根路由认证前仅处理上述钱包路径；子路由搜索参数校验仍须容错。规范化具有幂等性，不能产生重定向循环或重复初始化。
6. 参数不合法时打开钱包并提示可查充值记录，不把输入错误提升为全页 500。URL 的 `trade_status`、金额等不能作为支付成功证据。

### A2. 钱包频控与认证隔离

涉及 `router/wallet_payment.go`、旧充值端点的路由注册、`middleware/rate-limit.go` 或钱包专用薄封装。

所有实际钱包购买路径，包括保留的 legacy `/pay`，从共用 CT 桶移入明确的钱包 scope；登录/续期的原有防护不扩大、不删除。用户 key 必须包含 tenant、authenticated user、scope；同一用户多标签页共用预算，不同用户/租户隔离。保留现有 GA/IP 粗防护，因此没有承诺消除所有共享网络的全局限流风险。

以下是根据当前交互次数提出的初始值，不是容量压测结论：

| Scope | 接口 | 初始用户预算 |
| --- | --- | --- |
| quote | 自动报价 | 60 次 / 60 秒 |
| checkout | 创建、继续支付、legacy 创建 | 30 次 / 10 分钟 |
| state | restore、acknowledge、end、cancel | 20 次 / 60 秒 |
| check | 用户手动 reconcile | 首批沿用现有 20 次 / 20 分钟，独立计数 |
| 只读 | current、订单详情、余额、记录 | 不占上述写操作预算；保留现有全局防护 |

当前 create 后仍需 resume 获取并校验支付入口，一次完整发起占 checkout 两次；30 次可容纳 15 次完整发起。用户与订单业务约束继续限制重复下单，频控不是账务正确性的唯一边界。

首批复用现有 user limiter 的可配置 scope/窗口，控制变更面。现有 Redis 检查与计数非原子，不应声称并发下严格保证精确次数。并发严格阈值与剩余冷却时间可在后续钱包专用可靠性改动中用小型原子实现补齐，不重写 GA/CT。

429 必须保留 HTTP 状态，尽可能提供稳定错误码与 `Retry-After`。未提供可靠剩余时间时显示“请求较频繁，请稍后重试”，不编造精确倒计时。有 header 时仅冷却对应操作；只读 GET 仍可用时继续读状态。全局/未知 GET 429 则停止触发它的轮询和焦点重试。支付写请求绝不因冷却结束、焦点变化或网络恢复而自动重发。

### A3. 删除全局 HTTP 500 导航循环

涉及 `web/default/src/main.tsx`、`lib/query-client.ts`、`routes/__root.tsx` 和错误展示。

- 删除“任意 Query HTTP 500 自动导航 /500”的全局副作用。根加载失败使用现有路由错误边界；业务请求失败由所在区域处理。
- 租户不存在、禁用、维护等隔离规则仍然 fail-closed；不能为显示缓存内容绕过 Host/租户校验。
- 默认查询不自动重试 429；钱包显式 `retry:false` 继续保留。限制网络/5xx 重试，不用无限导航或即时循环制造新请求。
- `WalletPaymentError` 保留原始 HTTP 状态和可用冷却信息，避免转换成通用“状态不可用”而丢失恢复依据。局部提示与全局 toast 只由一个责任方展示，避免重复报错。

## B. 同一轮体验修复的完整目标

### B1. 查看状态不默认改变流程

- 普通进入、刷新、轮询使用 `GET current`。
- 若 current 明确返回“空闲且存在可恢复订单”，自动执行一次受控 restore，让用户无需额外点击。按身份与 flow revision 去重，失败停止自动恢复，提供重试。使用已有 `RECOVERABLE_ORDER_EXISTS` 语义，并兼容旧返回组合；不能对任何 `can_create=false` 都恢复。
- 支付回跳指定订单使用已有 `GET orders/:trade_no`，后端继续校验租户与用户归属。
- 回跳单与 current 相同：复用正常操作。回跳单是旧订单、current 为另单：显示回跳单结果并提供“返回当前订单”，禁止自动切换或确认另单。
- current 为空、目标订单可恢复时，用户一次“继续支付”手势串联 restore→resume；已有别单则不抢占。
- create→resume 保留：resume 负责新鲜 flow/revision、支付凭据与入口有效期校验，不能仅为减少一个请求绕过。

### B2. 钱包余额始终可见，结果留得住

- 将 `WalletStatsCard` 从仅 idle 的分支移出；充值中、确认中、成功、错误时都保留余额和记录入口。余额请求失败时标记更新失败，不能把旧值伪装成已刷新。
- 服务端成功后立即刷新余额、资金摘要与订单历史。刷新失败不撤销已确认的订单成功状态，而是显示余额待更新。
- 成功页主动作“再次充值”，由该用户动作调用现有 CAS acknowledge，成功后开放表单；返回钱包或查看记录不偷偷确认流程。
- 已有用户明确确认“结束本次充值”后的 end→ack 串联保留，无需再追加一层确认。明确本地结束不等同支付平台撤单，迟到支付仍需核实入账。
- 支持已由其他标签页 acknowledge 的结果只读展示；不把“不是当前订单”误报为付款失败。
- 用户文案新增/修改时按项目 i18n skill 同步六种语言，键盘与移动端操作保持可用。

### B3. 保留自动报价，消除重复等待

- 保留现有 300ms 防抖和服务端签名报价；按完整身份、金额、方式等输入复用未过期报价，切换 A→B→A 不重复获取仍有效的 A。
- 使用现有 AbortSignal 取消已过时查询；旧响应不能覆盖当前输入，不引入另一套请求状态管理。
- 报价未变且有效时，一次点击打开支付。报价过期则在同一用户手势预开占位窗口并更新一次：实际支付额、币种、到账量/单位、渠道及计价方式均相同时继续；有实质变化则关闭空窗口、展示新报价，要求重新确认。
- 已发出创建但结果不明时，保持原幂等 key 和原请求内容，查询当前状态或允许原请求重放；不因刷新报价创建新的支付意图。
- 弹窗被拦截时订单仍可恢复，显示“继续支付”，不悄悄创建第二单。原有 operationBusy、revision 和幂等保护保留。

### B4. 有界自动核实和可恢复故障

- 保留前台每 5 秒、最长 120 秒的只读轮询，隐藏页停止；回焦与手动刷新重新开启一个窗口，避免重复 focus/visibility 触发重复请求。
- 窗口结束仍 pending 时显示“尚未确认，可稍后在充值记录查看”；不变成失败、不自动创建新单、不自动 POST reconcile。
- 余额/历史/报价/订单状态各自失败只影响相关区域。订单已知时保留内容并标记可能不是最新状态；状态不确定时禁止危险的新增支付动作，但允许安全查看与重试。
- 冷却提示按实际响应控制；没有可靠时间时不显示虚假倒计时。正常确认查询与后台对账相互独立。

## C. 后续性能与可靠性修复

此项独立提交、验证，不阻塞 A 的紧急修复。

1. 删除 controller 在 canonical readiness 前的重复物理结构探测；model 层仍保留物理 fail-closed，但为五表探测增加有界、合并并发的缓存。初始采用已有成功 30 秒、失败 5 秒 TTL，缓存须绑定 DB 身份，测试更换 DB 或 schema 时明确失效。
2. controller/service/job 的 canonical gate 继续保证版本、digest、receipt。保留 legacy 写入兼容探测和必须新鲜校验的路径。
3. 共享探测自身有时间预算，等待者可在请求取消后退出；取消一个浏览器请求不能污染其他用户 readiness。
4. 不把 model 直接依赖 service/kkaimigrate：当前 kkaimigrate 已依赖 model。彻底统一结构探测需要另外评估依赖拆分，此处不声称完成单一检查器。
5. 如补钱包专用严格频控，用一个小型原子 Redis 操作加等价内存实现，统一检查、计数与剩余时间；存储失败返回可恢复错误，不放开交易保护。按并发行为与窗口边界测试，不扩大为全站限流重构。

## 必须通过的验收场景

1. 原始支付宝长数字流水 + out_trade_no 返回正确本地订单，无搜索参数异常、无精度损失；未知、重复、缺失参数不崩页。
2. 未登录回跳先清理外部参数，登录后仍能打开正确订单；SPA/刷新/前进后退行为一致。
3. 重放本次 21 次操作序列，第 21 次正常报价成功；登录预算只消耗 5 次，报价不耗交易预算。
4. 仅 quote 超限时 current/订单详情、认证和确认结果仍正常；不同用户与租户隔离，legacy 入口不能绕过交易预算。
5. 双击、两标签页、网络超时和创建结果未知均不创建重复支付意图；重复 notify/重放不会重复加款。
6. 已到账成功立即显示可信凭据并刷新余额；余额刷新失败不将支付成功改成失败；待核实不冒充到账。
7. 旧订单回跳不覆盖新 current；其他标签页已确认的订单仍可读；“再次充值”CAS 冲突刷新真实状态，不确认错单。
8. 报价过期且金额不变一次操作可继续；金额变化必须确认；创建未知结果不能换 key 重建。
9. 站点配置持续 HTTP 500 不产生导航/请求循环；功能区 429 不跳全页，租户隔离仍有效。
10. 120 秒停止前台轮询后订单不被判为失败，恢复页面可继续读；后台核实不依赖页面在线。
11. 性能阶段：重复 current 不再反复全量查五表；schema 未就绪仍拒绝危险操作，取消等待及时退出，SQLite/MySQL/PostgreSQL 语义兼容。

验证采用路由解析、React Query 交互、钱包 hooks/API、限流中间件与钱包路由的定向回归。新增 Go 测试使用 require/assert，避免随机压力循环和时间 sleep；并发测试用确定性同步。前端用 fake timers/明确网络结果验证行为。实施时对受影响文件做 scoped lint/typecheck；无合适定向检查则记录缺口，不能未经批准替换成全量命令。发布阶段执行实际适用的手册强制门禁。

## 实施与交付顺序

1. **前端止血提交**：回跳规范化、订单只读展示、删除全局错误导航、局部错误/429处理。兼容现有后端，可先发布。
2. **后端限流提交**：钱包分 scope、legacy 对齐、明确错误响应，回放事故序列。前端止血不算 429 根因已修复，此步骤必须完成。
3. **体验完善提交**：current GET/条件 restore、余额常驻、报价有效期复用、跨标签页结果与一次点击恢复。可以同轮验证交付，但保持独立可审查改动。
4. **性能可靠性提交**：结构探测缓存、可取消等待以及需要时的钱包原子频控，单独评估与验证。

不创建新分支或 worktree，不扩大为支付重构。是否提交、构建和生产上线按后续明确的执行范围办理。

生产发布前重新核实实际前后端和 controller 格式能力，不复用事故时的颜色或版本。format 2 前端按 runbook 21 独立发布；后端遵循 external 构建、schema 契约核对、stage、10%/50%/100% 各至少 120 秒、promote、即时/延迟状态、错误窗口与回滚门禁。legacy format 1 则继续精确配对。前后端兼容修复可分别回退；本计划不需要数据库迁移。

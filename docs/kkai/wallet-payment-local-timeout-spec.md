# 钱包本地超时与废单修订规范

日期：2026-10-24。依据用户最新确认：主动结束成功后直接返回充值，无需再次点击；自动超时仍提示超时并提供“返回充值”；很久的 pending 不提供补单按钮或入口，按本站超时逻辑作为废单。

本规范修订此前 PRD、UI、前后端与验收文档中的“未知或仅本地超时不得返回充值”规则。涉及本地结束、期限、恢复、废单及补单入口时，以本规范为准；其余资金、权限和互斥布局规则继续有效。[实施记录](./wallet-payment-implementation.md)单独记录实际代码和验证结果。

## 1. 产品行为

- 一个用户在同一租户只有一个前台当前流程。一笔订单只有一个原支付会话；用户主动结束并完成精确返回，或明确点击返回充值后，重新购买才产生新订单。
- 本站充值操作期限为创建后 30 分钟；已确认的渠道截止时间更早时取更早值。服务端时间为准，客户端只显示倒计时，不能自行延长或解除订单门禁。Pancake 等渠道自己的期限保持原事实，不能把本站 30 分钟说成渠道期限。
- 关闭外部支付页不结束当前操作。期限内仍能在钱包查看原单、继续支付或选择“结束本次充值”。创建正在提交时禁用重复操作；创建结果未知仍保留同一订单，可结束本站操作但不能重建同单支付会话。
- 用户主动确认结束后，前端在同一操作内先调用 end，再对该当前订单的 ended 结果串行调用精确 acknowledge；成功立即恢复充值表单，无需再点“返回充值”。acknowledge 失败则保留 ended 结果、错误和“返回充值”重试入口，不本地解锁。
- 本站自动到期仍在原位置显示超时结果，主按钮“返回充值”、次入口“查看订单记录”；用户点击并由后端确认精确流程后才恢复表单，不自动跳回。订单和购买模块不同时显示。
- 本站超时显示“本次充值已超时”；主动结束的只读记录或尚未确认结果显示“本次充值已结束”。结束确认和保留结果说明原支付页可能仍可付款，已付款会继续核实，请关闭旧支付页并避免重复支付。不把本地结束描述为“渠道已取消”或“原链接已失效”。
- 超时废单和主动结束单均不可继续支付、恢复、再取消或人工补单。列表、详情、钱包、管理员界面与旧入口一致；保留只读详情、订单号、证据及客服入口。废单不能重新自动绑定为当前流程。
- 很久的原始 pending 按相同期限投影为“已超时”，保留在历史范围的“已结束”分组，不再计入其他未完成数。不靠隐藏或删除历史订单消除 pending。
- 已确认收款、正在到账核实的事实优先于账龄，不能把已收款单显示为未付款废单。渠道已可靠关闭的 cancelled/expired 仍保留其原始事实。

## 2. 状态、接口与并发

新增本地操作事实 `local_ended_at`、`local_end_reason`（`user_ended` 或 `timeout`），独立于渠道的 `closed_at`、`close_reason` 和关闭证据。到期计算可即时阻止旧 pending 的操作，不依赖后台扫描已经运行或历史已批量写回。

| 事实 | 对外状态与动作 |
| --- | --- |
| 期限内原支付可用 | pending；resume、end、按渠道能力 cancel、reconcile |
| 主动结束本站操作 | ended；closed 分组；本次 end 成功后前端串行精确 acknowledge，成功直接回充值，失败保留结果与重试；历史只读／客服 |
| 本站期限到达 | timed_out；closed 分组，当前 result 提供 acknowledge；历史只读／客服 |
| 可信付款未完成入账 | credit_review；保留实际收款、处理责任和后台补偿，不能显示成未付款废单 |
| 已到账 | success；显示实际到账，当前流程精确确认后返回充值 |
| 渠道可靠取消／过期 | cancelled/expired；保留原渠道关闭证据及结果确认 |

`OrderDTO` 新增 `local_ended_at:number|null`、`local_end_reason:user_ended|timeout|null`，`display_status` 增加 ended/timed_out，`allowed_actions` 增加 end。原 `deadline_at` 由服务端返回有效本站截止，`deadline_source` 明示 local_policy 或更早的 provider。

新增 `POST /api/user/topup/orders/:trade_no/end`，正文 `{expected_order_version:string}`，返回 `{wallet,order}`。复用本人鉴权、租户归属、wallet:write、Origin 与限流。结束本人历史单不得改变当前另一单。

`acknowledge` 可确认本地结束结果；不得因此放宽 `WalletTopUpReliableTerminal` 对渠道可靠终态的含义。原子校验 flow id/revision、订单归属及最新付款事实；旧响应和旧订单晚到账不能清除、替换新的当前订单。历史查看不触发确认。主动 end 的自动确认仅作用于响应和最新缓存仍一致的原身份、flow、revision 与订单，且实际状态为 ended、允许 acknowledge；超时、已到账、credit_review、另一当前流程和迟到旧响应均不触发自动确认。

本地已结束或已超时后，resume/cancel/end/reconcile/admin-reconcile 及旧 `/api/user/topup/complete` 均由后端拒绝，不仅隐藏按钮；人工历史批次同样跳过废单，报告后才到期的对象也不得穿透。正常自动对账与可信回调使用独立路径，不能复用人工门禁阻断收款处理。

## 3. 废单仍保留的资金责任

- 原订单、原商户凭据、付款证明与回调不删除。本地结束不等于渠道关闭，不能假造可靠关闭证据。
- 废单后来真实付款，仍按原订单的准确金额、币种、商户／环境、额度快照和原账务事务处理；证据不足或入账失败保留收据与负责人，不丢款。
- A 结束后建立 B，A 的晚到款只更新 A；不替换 B、不清 B 的流程。A、B 都实际付款则分别入账；A 的重复通知只入账一次，A 的第二笔不同交易保存异常，不算到 B，不自动退款。
- 租户资金批次、返利 outbox、发票证据及容量校验继续有效。废单不提供手工强制发额度入口。
- 自动核实保持租约、有限批量与退避，不因旧 pending 长期高频请求服务商，也不因用户返回或历史批次暂停而丢掉已验证收款。

## 4. 新增验收

1. 期限前可恢复原单；服务端到期即拒绝继续支付、补单与手工核实，客户端时间回拨、旧页面和直接 API 均无法绕过。
2. 老 pending 在列表、详情和计数一致显示 timed_out/closed，仍可查询；用户、管理员及旧补单入口均无可执行废单操作。
3. 主动结束成功后在同一次操作内串行精确确认并直接回充值；确认失败保留 ended 结果和可重试返回入口。自动超时及尚未确认的结果在刷新、重登后保留，主按钮“返回充值”明确可见；恢复不会重新绑定废单。
4. 当前 A 结束并确认后创建 B；A 晚付款只入账 A，B 当前不变；重复回调不重复额度／租户 lot／返利 outbox。
5. 已确认收款未到账不会因为超过 30 分钟变成未付款废单；存储失败不 ACK，缺可信付款时间仍先保存后自动核实。
6. 人工单笔／历史批次拒绝或跳过废单；自动可信付款处理继续工作。创建频控、幂等键、租户和跨用户权限保持。

本修订只授权本地应用和文档实施，不授权生产构建、部署、真实 schema 安装、历史数据批处理或代码提交。数据库扩展安装与渠道／三库验收仍遵循既有交付边界。
